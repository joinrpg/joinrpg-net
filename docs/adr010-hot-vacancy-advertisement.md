# ADR010. Реклама горячих вакансий

## Статус

Черновик. Требует согласования новых полей DataModel с @leotsarev (см. [CLAUDE.md](../CLAUDE.md)).

## Контекст

На сайте есть «горячие роли» — персонажи с флагом `IsHot`, которые организатор хочет срочно
закрыть игроками. Сейчас они видны только на странице
[`AdminHotRolesList`](../src/JoinRpg.Portal/Pages/Admin/AdminHotRolesList.cshtml.cs)
(`IHotCharactersRepository.GetHotCharactersFromPublicProjects()`), но нигде автоматически не
рекламируются.

Хотим регулярно и без ручного труда публиковать эти вакансии во внешних каналах (телеграм-каналы,
блоги в соцсетях), при этом:

- не спамить одну и ту же роль повторно в один и тот же канал;
- балансировать показ — давать эфир наименее часто рекламируемым играм и ролям;
- иметь возможность добавлять новые типы каналов (ЖЖ, другие соцсети) и разные форматы сообщений.

## Основные понятия

1. **Канал рекламы** (`AdvertisementChannel`) — один конкретный пункт назначения (телеграм-канал
   `@joinrpg_hot`, блог в соцсети). Может быть **общим** или привязанным к **одной игре**. В этой
   итерации настройка каналов доступна только администратору, но модель рассчитана на то, что дальше
   мастера будут заводить свои каналы и хранить в БД собственные секреты (см. §5).
2. **Вид канала** (`AdvertisementChannelKind`) — способ *технической доставки* сообщения. Пока один
   вид — `Telegram`. У каждого вида свои специфичные настройки (для телеграма: ИД бота, секрет бота,
   ИД целевого чата/канала).
3. **Способ рекламы** (`AdvertisementMethod`) — способ *формирования* сообщения. Три способа:
   `SingleHotRole` (реклама одной горячей роли), `HotRolesDigest` (дайджест горячих ролей разных
   игр), `OpenVacanciesDigest` (дайджест игр с открытыми вакансиями).
4. **Расписание рекламы** (`AdvertisementSchedule`) — связывает канал и способ и задаёт, *в какие
   дни* слать. Пока единственный тип расписания — по дням недели (например: Пн и Ср). Время суток не
   хранится: оно одно общее для всей рекламы и зашито в конфиге джобы, а `DailyJob` уже умеет
   запускаться в нужный час (см. §5).
5. **Запись об отправке** (`AdvertisementLogEntry`) — факт того, что конкретная вакансия/игра была
   отрекламирована в конкретном канале в конкретный момент. На основе этих записей строится выборка
   (см. ниже).

Разделение (2) «как доставить» и (3) «что написать» — намеренное: один канал (телеграм) можно
использовать и для рекламы одной роли, и для дайджеста; один способ (дайджест) работает в любом виде
канала.

## Решение

### 1. Доменные типы (`JoinRpg.DomainTypes`)

Новая папка `JoinRpg.DomainTypes/Advertisement/`.

Типизированные идентификаторы через существующий генератор `TypedEntityId` (как
`ProjectIdentification`):

```csharp
[TypedEntityId(ShortName = "AdvChannel")]
public partial record AdvertisementChannelIdentification(int Value);

[TypedEntityId(ShortName = "AdvSchedule")]
public partial record AdvertisementScheduleIdentification(int Value);
```

Перечисления:

```csharp
public enum AdvertisementChannelKind { Telegram = 1 }           // расширяется: LiveJournal, Vk...

public enum AdvertisementMethod
{
    SingleHotRole = 1,       // одна горячая роль
    HotRolesDigest = 2,      // дайджест горячих ролей разных игр
    OpenVacanciesDigest = 3, // дайджест игр с открытыми вакансиями
}
```

Настройки вида канала — иммутабельный полиморфный тип, который сериализуется в JSON (см. §2).
Базовый абстрактный тип + наследник на каждый вид:

```csharp
public abstract record AdvertisementChannelSettings(AdvertisementChannelKind Kind);

public sealed record TelegramChannelSettings(BotId BotId, BotSecret Secret, TelegramChatId ChatId)
    : AdvertisementChannelSettings(AdvertisementChannelKind.Telegram);
// Секрет бота хранится в БД вместе с остальными настройками — см. §5.
```

Иммутабельные «инфо»-снимки для сервисного слоя и UI (по образцу `ProjectInfo`):
`AdvertisementChannelInfo` (Id, `ProjectIdentification? ProjectId`, имя, вид, настройки),
`AdvertisementScheduleInfo` (Id, канал, `AdvertisementMethod`, дни недели).

Расписание — «по дням недели» (время суток не хранится, см. §5):

```csharp
public sealed record WeeklyAdvertisementSchedule(IReadOnlySet<DayOfWeek> Days);
```

### 2. Хранение в БД (`JoinRpg.Dal.Impl`, EF6)

DAL проекта — **EF6**, не EF Core (см. память проекта). Три новые таблицы.

**`AdvertisementChannels`**

| Колонка | Тип | Комментарий |
|---|---|---|
| `AdvertisementChannelId` | int PK identity | |
| `Name` | nvarchar | человекочитаемое имя для админки |
| `ProjectId` | int? FK Projects | `null` = общий канал; иначе привязан к 1 игре |
| `Kind` | int (enum) | `AdvertisementChannelKind` |
| `SettingsJson` | nvarchar(max) | сериализованный `AdvertisementChannelSettings` (включая секрет бота), десериализация по `Kind` |
| `IsActive` | bit | мягкое отключение канала |

Специфичные настройки вида храним **JSON-колонкой** (одна таблица на все виды): виды будут
добавляться, а нормализованная схема на каждый вид (TPH/отдельные таблицы) потребовала бы миграцию
на каждый новый вид. Ценой этого — отсутствие FK/типобезопасности на уровне БД; целостность
обеспечивает сервисный слой при десериализации. Секрет бота лежит здесь же (см. §5 про
чувствительность и никогда-не-логировать).

**`AdvertisementSchedules`**

| Колонка | Тип | Комментарий |
|---|---|---|
| `AdvertisementScheduleId` | int PK identity | |
| `AdvertisementChannelId` | int FK | канал назначения |
| `Method` | int (enum) | `AdvertisementMethod` |
| `DaysOfWeekMask` | int | битовая маска дней недели (время суток общее, в конфиге джобы) |
| `IsActive` | bit | |
| `LastRunDate` | date? | защита от повторного запуска в тот же день (идемпотентность джобы) |

**`AdvertisementLog`** — по одной строке на **каждую** отрекламированную роль/игру (не на отправку
целиком). Это принципиально для выборки «не повторять роль» и «наименее часто рекламируемые
игры/роли» — их считаем обычными `GROUP BY … COUNT`/`WHERE NOT EXISTS`, без разбора JSON.

| Колонка | Тип | Комментарий |
|---|---|---|
| `AdvertisementLogEntryId` | int PK identity | |
| `AdvertisementChannelId` | int FK | где рекламировали |
| `Method` | int (enum) | каким способом (для аналитики) |
| `ProjectId` | int FK | какая игра |
| `CharacterId` | int? FK | какая вакансия (роль); `null` для `OpenVacanciesDigest` |
| `SentAt` | datetimeoffset | момент отправки |
| `Status` | int (enum) | `Sent` / `Failed` — вести и провалы для диагностики |

Миграцию добавляем по [ef-migrations.md](ef-migrations.md). Новые поля/сущности DataModel
согласовать с @leotsarev.

### 3. Слои и проекты

Отдельный конвейер, **не** переиспользуем систему уведомлений (ADR003): у уведомлений получатель —
`UserId` с его каналами и подписками, а тут получатель — публичный канал; шаблонизация и выбор
получателя другие. Переиспользуем только низкоуровневый `JoinRpg.Common.Telegram` (отправка HTML в
конкретный chat).

Один новый сервисный проект (по образцу `JoinRpg.Services.Notifications`):

- **`JoinRpg.Services.Advertisement`** — доменный сервис.
  - `IAdvertisementChannelService` — CRUD каналов и расписаний (админ-операции: создание,
    редактирование настроек, включение/выключение). Проверка `IsAdmin`.
  - `IAdvertisementDispatchService` — ядро: для сработавшего расписания выбирает контент
    (см. §4), формирует сообщение (см. §6), отправляет через нужный `IAdvertisementSender`,
    пишет `AdvertisementLog`.
  - `IAdvertisementSender` — абстракция доставки по виду канала; реализация
    `TelegramAdvertisementSender` поверх `JoinRpg.Common.Telegram`. Диспетчеризация по
    `AdvertisementChannelKind` (легко добавить ЖЖ/соцсети).

Хранилище — **расширяем существующие репозитории в `JoinRpg.Dal.Impl`** (интерфейсы в
`JoinRpg.Data.Interfaces` / `JoinRpg.Data.Write.Interfaces`), без отдельного `Dal`-проекта: чтение
каналов, расписаний, лога и выборочные запросы. Мутирующие репозитории — через `IUnitOfWork.GetXxx()`
(см. память проекта «write-репозитории через UnitOfWork»), иначе `SaveChanges` на другом `DbContext`
потеряет изменения.

Источник горячих ролей — существующий `IHotCharactersRepository`
(`GetHotCharactersFromPublicProjects()`), возможно с новыми перегрузками (фильтр по игре для
канала, привязанного к проекту).

**Регистрация в DI** — по возможности через стандартный `Microsoft.Extensions.DependencyInjection`
(метод-расширение `AddAdvertisement(this IServiceCollection)`), а не через Autofac-модуль. К Autofac
привязываемся только там, где иначе нельзя (интеграция с уже автофаковой частью графа).

### 4. Выборка контента

Триггер — ежедневная джоба (см. §5). За один запуск по **каждому** сработавшему сегодня
`AdvertisementSchedule` делаем **ровно одну** отправку. Для расписания:

1. **Кандидаты.** Для `SingleHotRole`/`HotRolesDigest` — горячие роли из публичных проектов; если
   канал привязан к игре — только из неё (для привязанного канала `HotRolesDigest` тоже допустим —
   это дайджест горячих ролей одной игры). Для `OpenVacanciesDigest` — «игры с открытыми
   вакансиями»: `IsAcceptingClaims` **и** `IsPublicProject` **и** есть хотя бы одна открытая роль.
2. **Anti-repeat — жёсткий**: роль, уже присутствующая в `AdvertisementLog` для этого канала со
   `Status = Sent`, **никогда** не рекламируется в нём повторно (`WHERE NOT EXISTS`). Аналогично для
   игр в `OpenVacanciesDigest`. Роль, которая перестала быть горячей и снова стала, **тоже** больше
   не показывается: правило трактуется как «показана однажды = больше никогда». Записи со
   `Status = Failed` при этом **не** блокируют — провал доставки равнозначен «роль ещё не
   рекламировалась» (см. §7), и в следующий запуск она снова кандидат.
3. **Ранжирование** среди оставшихся кандидатов — по убыванию веса игры:

   ```
   вес(игра) = ActiveClaimsCount(игра) / КОЛ-ВО_РАЗ_РЕКЛАМЫ_ВАКАНСИЙ(игра)
   ```

   Числитель — то же число активных заявок, по которому ранжируются игры на главной
   (`ProjectListManager` сортирует `OrderByDescending(p => p.ActiveClaimsCount)`), — переиспользуем
   его, а не сырой `COUNT` всех `Claim`. Знаменатель — число записей `AdvertisementLog` по этой игре
   (по всем каналам). Формула даёт преимущество более крупным играм (больше активных заявок) и
   одновременно поднимает наверх редко рекламированные. Игру, которую ещё ни разу не рекламировали
   (знаменатель = 0), считаем максимально приоритетной (вес = +∞).
4. **Выбор роли внутри игры** (для `SingleHotRole`/`HotRolesDigest`): среди горячих ролей игры берём
   те, что рекламировались наименьшее число раз (по `AdvertisementLog`, все каналы), и из них
   выбираем **случайную**. Так реклама не залипает на одной роли крупной игры.
5. По способу:
   - `SingleHotRole` — top-1 роль (из игры с наибольшим весом).
   - `HotRolesDigest` — до `MaxRolesInDigest` ролей.
   - `OpenVacanciesDigest` — до `MaxGamesInDigest` игр.

   Лимиты дайджеста — **хардкод-константы** в коде (`MaxRolesInDigest = 5`, `MaxGamesInDigest = 5`),
   не настройка канала/расписания. Если подходящих кандидатов меньше лимита (например, у привязанного
   к игре канала мало горячих ролей) — шлём **неполный** дайджест, запуск не пропускаем; пропускаем
   только когда кандидатов нет вовсе.
6. Пишем в `AdvertisementLog` по строке на каждую вошедшую роль/игру.

Так как anti-repeat жёсткий, множество кандидатов для канала со временем исчерпывается — это ожидаемо
(роль либо закрыли, либо она перестала быть горячей, либо её уже показали). При появлении новых
горячих ролей они попадают в выборку автоматически.

### 5. Секрет бота и безопасность

Секрет бота **хранится в БД** (в `SettingsJson` канала), потому что каналы (и в перспективе — сами
мастера) настраивают собственных ботов; общего бота из конфигурации приложения недостаточно. Это
чувствительные данные:

- никогда не логировать `SettingsJson`/секрет (в отличие от `NotificationServiceImpl`, который логирует
  сообщение целиком) — в лог идут только Id и вид канала;
- не отдавать секрет в UI/API после сохранения (write-only поле: показываем «задан/не задан»);
- **шифровать секрет прикладным Data Protection.** В проекте уже настроен ASP.NET Core Data
  Protection (`AddJoinDataProtection` в `JoinRpg.Common.WebInfrastructure`, ключи в БД через
  `DataProtectionDbContext`). Секрет оборачиваем через `IDataProtector` (purpose
  `"AdvertisementChannel.BotSecret"`): `Protect()` перед сохранением, `Unprotect()` в джобе; в БД
  лежит шифртекст. Чтобы проект рекламы не зависел от `WebInfrastructure`, прячем это за интерфейсом
  `ISecretProtector` в низком слое, реализация через `IDataProtector` регистрируется в composition
  root (Portal). Шифрование прикладное — не зависит от СУБД (проект поддерживает и PostgreSQL, и SQL
  Server). Дополнительную защиту самих DP-ключей (`ProtectKeysWith…` через сертификат/KeyVault) на
  этой итерации **откладываем**: DP-ключи и шифртекст лежат в одной БД — принимаем как осознанный
  компромисс MVP.

Джоба выполняется под роботом-админом (`JobRunner` подставляет `RobotUser`, см. ADR009 и память
«джобы работают под роботом-админом») — админ-проверки в сервисах проходят сами собой.

**Тип джобы.** Одна **ежедневная** джоба (`DailyJob`/`MidnightJobBackgroundService`, ADR002),
запускаемая **каждый день в 12:00 по МСК** (время в конфиге джобы). Она перебирает активные расписания,
чей `DaysOfWeekMask` включает сегодняшний день недели и у которых `LastRunDate` не сегодня,
выполняет по одной отправке на каждое и проставляет `LastRunDate` (at-most-once в сутки,
идемпотентность по ADR002). Отдельное время суток на расписание не нужно.

### 6. Формирование сообщений

Каждый `AdvertisementMethod` — свой билдер текста. Требования:

- строки, видимые пользователю, — на **русском** (CLAUDE.md); локализуемые строки — в
  `JoinRpg.Portal`/`JoinRpg.Services.Email`, в проекте рекламы — `TODO[Localize]`;
- ссылки на игру/роль строить через `IProjectUriLocator`/`ICharacterUriLocator`, не хардкодить
  (память «URL строить через IUriLocator»);
- для телеграма отдавать HTML, переживающий телеграм-санитайзер (как `TelegramSenderJobService`);
- данные о датах игр — через существующую интеграцию КогдаИгра (`IKogdaIgraSyncClient`), как в
  `AdminHotRolesList`.

Трассировка — через `ActivitySource`, как в `NotificationServiceImpl`.

### 7. Обработка ошибок доставки

Провал отправки эквивалентен «роль/игру никогда не рекламировали»: пишем запись со `Status = Failed`
(для диагностики), но anti-repeat её игнорирует — учитываются только `Status = Sent`. Значит в
следующий запуск роль снова кандидат, отдельного механизма ретраев не требуется. Для дайджеста
статус проставляется по факту отправки сообщения целиком (все вошедшие роли/игры получают одинаковый
статус этой отправки).

### 8. UI

Только администраторская часть (в этом ADR): CRUD каналов и расписаний. По образцу существующих
админ-страниц (`AdminHotRolesList`) — Razor Page под `[AdminAuthorize]` или Blazor-остров. При
островах помнить: Portal на **Bootstrap 3** (память проекта). Секрет бота — write-only поле
(см. §5). Модерации/предпросмотра перед отправкой в этой итерации нет — джоба формирует и сразу
отправляет.

## Последствия

- Гибкость по видам каналов (JSON) и способам (enum + билдеры) без переписывания ядра.
- Лог с гранулярностью «строка на роль/игру» — единственный источник и для anti-repeat, и для
  балансировки эфира; выборки остаются SQL `GROUP BY`/`NOT EXISTS`.
- Отдельный конвейер не смешивается с персональными уведомлениями и не тянет их модель получателя.
- Секрет бота в БД поддерживает будущий сценарий «мастер заводит свой канал», но требует аккуратности
  с логами/UI и, желательно, шифрования колонки.

## Валидация на уровне сервиса

- Комбинация «канал + способ» проверяется в `IAdvertisementChannelService`. `HotRolesDigest`
  допустим и для общего, и для привязанного к игре канала; ограничения на прочие сочетания —
  по мере надобности (например, осмысленность `OpenVacanciesDigest` для привязанного канала).
- Настройки вида канала обязаны соответствовать `Kind` при десериализации `SettingsJson`.
