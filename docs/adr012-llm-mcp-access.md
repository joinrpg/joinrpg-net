# ADR012. Доступ к данным проекта из LLM: MCP-сервер и OAuth 2.1

## Контекст

Мастер игры хочет работать с базой своего проекта через LLM-ассистента: задавать вопросы
(«кто из чиновников относится к партии синих») и отдавать команды («придумай и добавь
персонажа по таким-то данным»). Клиент — не обязательно Claude: Cursor, VS Code, OpenCode,
ChatGPT и прочие.

Сегодня это невозможно:

1. **Нет протокола.** MCP (Model Context Protocol) в репозитории отсутствует полностью.
   Существующий `x-game-api` — это REST для внешних игровых систем; модель им пользоваться
   не может, потому что не знает ни о его существовании, ни о его семантике.
2. **Нет пригодной авторизации.** Единственный способ получить токен для внешнего API —
   `POST /x-api/token` (`Controllers/XGameApi/XApiLoginController.cs`) в обмен на **логин
   и пароль мастера**: ROPC, JWT на 30 дней, без scope, без возможности отзыва. Вставлять
   такой токен в стороннее приложение недопустимо.
3. **Данные отдаются не в том виде.** `CharacterApiController.CreateCharacter` создаёт
   персонажа с захардкоженным пустым списком групп; структура групп и метаданные полей
   не собраны в форму, по которой модель может ориентироваться.

Спецификация MCP ([Authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization),
[Security Considerations](https://modelcontextprotocol.io/specification/draft/basic/authorization/security-considerations))
предъявляет к серверу жёсткие требования:

- **MUST** реализовать OAuth 2.0 Protected Resource Metadata (RFC 9728):
  `/.well-known/oauth-protected-resource` и `WWW-Authenticate: Bearer resource_metadata="…"`
  в ответе 401;
- **MUST** проверять, что токен выписан именно для этого ресурса (audience, RFC 8707),
  и отклонять любые другие;
- авторизационный сервер **MUST** быть OAuth 2.1 с обязательным PKCE (`S256`), сверять
  `redirect_uri` точной строкой, отдавать метаданные (RFC 8414 или OIDC Discovery);
  `redirect_uri` — только https или loopback.

Это один контракт для всех клиентов: отдельной работы «под ChatGPT» или «под Gemini» нет,
есть соответствие спецификации.

## Решение

### 1. Remote MCP внутри JoinRpg.Portal

Эндпоинт `/mcp` в `JoinRpg.Portal` на официальном C# SDK (`ModelContextProtocol`,
`ModelContextProtocol.AspNetCore`). Инструменты живут в новом проекте `JoinRpg.Mcp`
(слой Portal) и вызывают доменные сервисы напрямую, без HTTP-хопа.

Между инструментами и доменом — слой view-сервисов `JoinRpg.WebPortal.Managers/Llm/`
с DTO в `JoinRpg.Web.Llm`. Он вынесен отдельно намеренно: те же методы позже можно
выставить как `x-game-api`-контроллеры без дублирования логики, и в него же добавятся
вводные следующей итерацией.

Отдельный процесс не заводим: инструментам нужен весь граф зависимостей Portal
(репозитории, `ProjectInfo`, доменные сервисы), а выигрыш от изоляции не окупает
дублирования хостинга и конфигурации.

Важно: `/mcp` **не проходит** через `DiscoverProjectMiddleware` — первый сегмент пути
не парсится как `projectId`, — поэтому атрибут `[RequireMaster]` там не работает.
Права проверяет каждый view-сервис самостоятельно
(`ProjectInfo.HasMasterAccess(userId, permission)`), что соответствует правилу
[structure.md](structure.md): «Services.Impl проверяют права самостоятельно, не доверяя
входным данным». На запись права дополнительно проверяет `CharacterServiceImpl`.
Сегмент `mcp` добавляется в `ApiPathHelper.IsApiPathSegment`.

### 2. Только OAuth 2.1 через IdPortal; personal access token не заводим

Авторизационный сервер — существующий `JoinRpg.IdPortal` (ADR004, OpenIddict). Он получает
вторую роль: не только логин на сайт, но и AS для сторонних приложений.

Долгоживущие токены, привязанные к пользователю, **не делаем**. Это был бы второй контур
аутентификации — своя таблица, свой `AuthenticationHandler`, UI выпуска и отзыва, второй
путь проверки scope — ради сценариев, которых у нас нет: все целевые клиенты водят
пользователя через браузерный флоу. Дополнительно это ровно тот копируемый руками секрет,
от которого уходит OAuth 2.1.

Отсюда следует отказ от **серверных агентов без пользователя в цикле**. В частности,
Yandex Cloud AI Studio MCP Hub подключает внешние MCP-серверы указанием значения заголовка
авторизации, то есть статическим токеном; интерактивного пользователя там нет
и authorization code неприменим. Такие сценарии не поддерживаются. Условие пересмотра —
появление реального спроса на агента, работающего без человека.

Для локальной разработки в `Development` регистрируется дополнительная схема, принимающая
заголовок с id пользователя (`AuthenticationConfigurator` уже ветвится по
`environment.IsDevelopment()`); в production она не попадает. Интеграционные тесты
авторизуются через существующий `ImpersonationHelpers`, без браузерного флоу.

### 3. Регистрация клиентов: CIMD основной, pre-registration запасной, DCR не реализуем

Спецификация определяет три механизма: Client ID Metadata Documents (**SHOULD**),
pre-registration и Dynamic Client Registration (**MAY**, помечена deprecated —
«новым реализациям следует использовать CIMD»). Приоритет
`pre-registration → CIMD → DCR` в спецификации — это порядок выбора **на стороне клиента**;
какие механизмы поддерживать, сервер решает сам.

Проверено по документации вендоров:

| Клиент | Готовый `client_id` | CIMD |
|---|---|---|
| claude.ai (web/desktop/mobile) | да, Advanced settings | вероятно |
| ChatGPT connectors | да, predefined OAuth clients | да |
| Cursor | да, `auth: { CLIENT_ID, CLIENT_SECRET?, scopes? }` в `mcp.json` | нет, в планах |
| OpenCode | да, `oauth: { clientId, clientSecret, scope }` | не заявлен |
| VS Code | **нет** — только DCR либо встроенный client id | да, по сообщениям добавлен |
| Claude Code | не документирован | да, на пользовательских путях |

CIMD покрывает VS Code, Claude Code и ChatGPT; pre-registration добирает Cursor и OpenCode.
Вместе — все проверенные клиенты, и DCR не нужна.

Почему именно так:

| | DCR | CIMD |
|---|---|---|
| Анонимная запись в нашу БД | да — нужны rate limit, TTL, GC, алерты | нет, записей не создаётся |
| Идентичность на экране согласия | строка, которую написал регистрирующийся | HTTPS-домен, с которого сервер сам забрал метаданные |
| Новая поверхность атаки | публичный эндпоинт создания записей | SSRF — сервер ходит по URL, присланному клиентом |
| Портируемость `client_id` | нет, привязан к конкретному AS | да, self-hosted URL |
| Статус в спецификации | MAY, deprecated | SHOULD |

Риск не исчезает, а меняет форму: вместо защиты от спама регистраций нужна защита от SSRF.
Но поверхность уже, и на экране согласия виден проверяемый домен, а не произвольная строка.
Опасение про спам регистраций не теоретическое: у Cursor известен баг с новым DCR-вызовом
на каждом переподключении.

**Реализация CIMD.** В OpenIddict не поддержана, поэтому вклиниваемся в разрешение клиента
на authorize- и token-эндпоинтах: если `client_id` — HTTPS URL с path-компонентом,
забираем по нему JSON и валидируем. Обязательно целиком:

- `client_id` в документе совпадает с URL, по которому он получен;
- `redirect_uri` из запроса присутствует в `redirect_uris` документа;
- обязательные поля: `client_id`, `client_name`, `redirect_uris`;
- кэш по HTTP-заголовкам ответа;
- **защита от SSRF**: резолв только в публичные адреса, запрет приватных диапазонов
  и loopback, запрет редиректов на них, таймаут, лимит размера тела и числа редиректов;
- на экране согласия — `client_name` и домен документа; для клиентов
  с loopback-only `redirect_uris` — дополнительное предупреждение (спецификация прямо
  отмечает, что CIMD сам по себе не защищает от подмены localhost);
- `client_id_metadata_document_supported: true` в метаданных AS.

**Pre-registration** — через существующий механизм IdPortal: секция `OAuthServer:Clients[]`,
применяется `OAuthRegistrator`. Для каждого клиента фиксируются точные `redirect_uris`,
grant types (`authorization_code`, `refresh_token`) и явный список разрешённых scope.
У Cursor два callback'а: `https://www.cursor.com/agents/mcp/oauth/callback`
и `http://localhost:8787/callback` — регистрировать оба.

`registration_endpoint` **не публикуется**. В OpenIddict 7.6 DCR всё равно не реализована
([openiddict-core#2404](https://github.com/openiddict/openiddict-core/issues/2404)),
то есть её пришлось бы писать самим — в контуре безопасности.

**Цена решения, явно.** Поддержка CIMD в VS Code подтверждена вторичными источниками,
а не документацией Microsoft. Если проверка покажет, что VS Code через CIMD не проходит,
а pre-registration он не умеет, — VS Code остаётся неподдерживаемым клиентом.

### 4. Scope и ограничение доступной поверхности

Регистрируются два scope:

- `joinrpg.read` — чтение всего, что отдаёт MCP-сервер;
- `joinrpg.characters.write` — создание и правка персонажей.

Чтение сделано одним широким scope сознательно: дробить его на `joinrpg.characters.read`,
`joinrpg.plots.read` и так далее — это гранулярность, которую пользователь на экране
согласия всё равно не различает, а границей доступа служит выбор проектов (ниже).
Запись, наоборот, узкая и предметная: будущий `joinrpg.plots.write` будет отдельным scope
и потребует нового согласия.

> **Следствие, которое надо держать в голове.** Когда появится итерация по вводным,
> токен, выданный сегодня с `joinrpg.read`, автоматически получит доступ и к ним, без
> повторного согласия. 

Два ограничения, без которых одно нажатие «Разрешить» отдаёт слишком много:

1. **MCP-клиенты не получают OIDC-скоупы.** В OpenIddict у клиента задаётся список
   разрешённых scope (`Permissions.Scopes`); для MCP-клиентов туда входят только
   `joinrpg.*` — без `email`, `phone`, `profile`. Токен для `/mcp` не должен открывать
   `connect/user_info`.
2. **Согласие даётся на конкретные проекты.** `joinrpg.read` глобален, поэтому на экране
   согласия мастер отмечает, к каким своим проектам даёт доступ. Выбор сохраняется
   в записи authorization и попадает в токен отдельным claim; view-сервисы фильтруют
   по нему **в дополнение** к проверке `HasMasterAccess`. Без этого одно «Разрешить» =
   все игры, где человек мастер.

Экран согласия показывает: имя приложения, домен или хост redirect_uri, запрошенные права
и выбор проектов.

При отсутствии `joinrpg.characters.write` write-инструменты отвечают 403 с
`WWW-Authenticate: Bearer error="insufficient_scope", scope="joinrpg.characters.write"`,
чтобы клиент мог выполнить step-up authorization.

### 5. Portal как resource server: интроспекция, а не локальная валидация

`OpenIddict.Validation.AspNetCore` в режиме интроспекции; Portal — confidential-клиент
IdPortal. Проверка `aud == https://joinrpg.ru/mcp` обязательна (требование спецификации:
принимать только токены, выписанные для себя).

Документация OpenIddict рекомендует локальную валидацию только когда API живёт в одном
приложении с AS — ей нужен доступ к БД сервера авторизации. Portal и IdPortal — разные
приложения, для них рекомендована интроспекция. Дополнительный и более важный аргумент:
интроспекция даёт **мгновенный отзыв**. При локальной валидации по JWKS отозванное
разрешение продолжало бы работать до истечения токена, и страница «Подключённые
приложения» обещала бы больше, чем делает.

Обратная сторона — сетевой вызов на запрос и зависимость `/mcp` от доступности IdPortal;
включается кэш ответов интроспекции с коротким TTL. Этот TTL и есть фактическая задержка
отзыва — выбирать его с учётом этого.

Шифрование access-токенов остаётся включённым; `DisableAccessTokenEncryption()` не нужен.
Если интроспекция окажется дорогой по задержке, запасной вариант — локальная валидация
по JWKS с отключением шифрования. Это не «небезопасно»: RFC 9068 определяет
JWT-access-токены как подписанные, шифрование опционально, и так работает большинство AS.
Но тогда обязательны условия: в claims нет персональных данных (только `uid`, scope,
id проектов, `exp`), короткий TTL, токены не попадают в логи, — и отзыв перестаёт быть
мгновенным.

Protected Resource Metadata отдаёт сам SDK:
`AddAuthentication().AddMcp(o => o.ResourceMetadata = new ProtectedResourceMetadata { … })`.
Если задаётся кастомный `ResourceMetadataUri`, `Resource` надо выставить явно — автовывод
работает только для дефолтного пути.

### 6. Объём первой итерации: только персонажи

Инструменты чтения: `list_projects`, `get_project_overview`, `list_characters`,
`get_characters`, `search_characters`. Инструменты записи: `create_character`,
`update_character_fields`.

Работа с вводными (`PlotFolder` / `PlotElement`) отложена: их нет во внешнем API вообще,
а поиск по текстам пришлось бы делать с нуля — `ISearchService` ищет только по заголовкам
папок и именам персонажей. Это следующая итерация поверх той же инфраструктуры:
авторизация, MCP-сервер и слой view-сервисов от предметной области не зависят.

**`create_character` создаёт персонажа с пустым списком родительских групп.** Явное
размещение по группам через MCP не выставляется — мастер делает это на сайте. Это
сохраняет текущее поведение `CharacterApiController.CreateCharacter` и убирает целый
класс ошибок: модель не может переложить роль в чужую ветку дерева.

Важная деталь: «пустой список групп» относится только к явно задаваемым родительским
группам. Значения полей всё равно приводят персонажа в спецгруппы вариантов —
`CharacterExistsStrategyBase.UpdateSpecialGroups` пересобирает `ParentCharacterGroupIds`
как объединение обычных и спецгрупп. Так что персонаж, созданный с заполненными полями,
сразу оказывается в соответствующих спецгруппах, и вопросы вида «кто относится к партии
синих» по нему работают.

Намеренно не выставляются: `DeleteCharacter`, `MoveCharacter`, `ICharacterGroupService`,
`IFieldSetupService`, финансы, заявки, рассылки.

**У персонажа нет состояния черновика — это отличие от будущей итерации по вводным.**
У вводных «создать, но не опубликовать» — свойство модели данных (`PlotElement.Published`).
Созданный персонаж сразу становится частью проекта, и `AddCharacterRequest` не позволяет
создать его скрытым (в записи нет `IsPublic`). Поэтому защита держится на трёх вещах,
и все три обязательны:

- `joinrpg.characters.write` выдаётся отдельным осознанным согласием;
- правило «показать пользователю и дождаться подтверждения до записи» в инструкциях
  для модели — это не рекомендация, а единственный интерактивный барьер;
- аудит: `Character.CreatedById` / `UpdatedById` заполняются владельцем токена, так что
  видно, что роль заведена через интеграцию.

### 7. Инструкции для модели вместо отдельного «скилла»

Словарь предметной области, порядок работы с инструментами и правила записи отдаются
клиенту в `ServerInstructions` при `initialize` (`JoinRpg.Mcp/McpInstructions.cs`).
Мастеру не нужно ничего устанавливать, и это работает одинаково во всех клиентах —
в отличие от файла-скилла, привязанного к конкретному вендору.

Ключевые пункты инструкций:

- сначала `get_project_overview` (даёт дерево групп и id всех полей и вариантов), затем
  `list_characters` по группе или `search_characters`, и только потом `get_characters`
  пачкой по отобранным id — не выгружать всех персонажей проекта;
- у каждого поля и каждого варианта значения есть спецгруппа
  (`ProjectField.CharacterGroupId`, `ProjectFieldDropdownValue.CharacterGroupId`), поэтому
  «кто относится к партии синих» — это `list_characters` по группе варианта, а не
  выгрузка всех и фильтрация в контексте;
- внутренние ссылки в markdown — `%персонаж123`, `%группа45` (см. `MarkDownRendererFacade`);
- значения полей брать из `get_project_overview`, не выдумывать.

### 8. Язык описаний инструментов — русский

Описания инструментов и параметров пишутся по-русски. Это осознанное исключение из правила
[structure.md](structure.md) о том, что видимые пользователю строки живут только
в `JoinRpg.Portal` и `JoinRpg.Services.Email`: описания читает модель, а не пользователь,
и предметная область вместе со всеми данными игры — русская. Маркер `TODO[Localize]`
в `JoinRpg.Mcp` не ставится.

## Последствия

- Изменений в `JoinRpg.DataModel` не требуется: ни новых сущностей, ни миграций. Всё
  состояние авторизации живёт в хранилище OpenIddict в IdPortal.
- IdPortal становится полноценным AS для сторонних приложений. Появляется страница
  «Подключённые приложения» поверх `IOpenIddictAuthorizationManager`: список выданных
  разрешений (приложение, проекты, scope, когда выдано и когда использовалось) и отзыв.
- Portal получает рантайм-зависимость от доступности IdPortal на каждом запросе к `/mcp`,
  смягчённую кэшем интроспекции.
- Появляется исходящий HTTP-трафик из IdPortal по URL, которые присылает клиент (CIMD).
  Это новая поверхность, требующая SSRF-ограничений и, вероятно, отдельного правила
  на egress в манифестах.
- Слой `JoinRpg.WebPortal.Managers/Llm` и DTO в `JoinRpg.Web.Llm` переиспользуемы: следующая
  итерация по вводным добавляет туда методы и инструменты, не трогая этапы авторизации,
  MCP-хостинга и инструкций.
- Размер ответов инструментов — предмет постоянного внимания. ADR011 описывает, как сетка
  ролей (те же самые персонажи) отдавала 18 МБ; в контексте модели это дороже, чем в браузере.
  Отсюда: `DefaultIgnoreCondition = WhenWritingNull`, только заголовочные поля в индексе,
  лимит на количество id в `get_characters`.
- Фактическая таблица совместимости клиентов дополняется по результатам проверки
  подключений; ключевой открытый вопрос — VS Code через CIMD.
