# Спайк P3 (ADR015): контракт «первая EF Core-миграция пустая» — результаты

Исследовательский спайк к [ADR015](adr015-efcore-migration.md), раздел
«P3. Контракт „первая EF Core-миграция пустая“ (parity)».

**Ветка:** `spike-efcore-parity` (от `upstream/master`). Выбрасываемая, в прод не идёт.
**Дата:** 25.09.2026.

## Что делалось

1. На локальный SQL Server (docker compose) накачена **эталонная боевая схема**
   настоящими EF6-миграциями: `dotnet run --project src/Joinrpg.Dal.Migrate`
   с `Initial Catalog=joinrpg_spike`. Получилось 45 таблиц, 395 колонок,
   110 внешних ключей, 112 индексов, 73 DEFAULT-констрейнта.
2. Заведён отдельный прототипный проект
   [`src/JoinRpg.Dal.Impl.EfCorePrototype`](../src/JoinRpg.Dal.Impl.EfCorePrototype)
   — EF Core 10 + SqlServer поверх того же `JoinRpg.DataModel`.
   Рабочий `MyDbContext`, EF6-миграции и `Joinrpg.Dal.Migrate` **не трогались**.
3. Вся конфигурация из EF6 `OnModelCreating` перенесена в EF Core fluent API
   (`PrototypeDbContext.OnModelCreating`).
4. Сгенерирована настоящая начальная EF Core-миграция
   (`dotnet ef migrations add Initial`), её SQL накатан на пустую БД
   `joinrpg_efcore`, после чего схемы обеих БД сняты одним и тем же
   SQL-запросом по `sys.*` и сравнены построчно.
   `dotnet ef migrations has-pending-model-changes` — **зелёный**
   («No changes have been made to the model since the last migration»).

Итераций сверки — 4.

## Главный результат

**Контракт достижим.** После переноса конфигурации из 662 объектов схемы
расходятся:

| Категория | Объектов | Расхождений (по структуре) | Расхождений (с учётом имён констрейнтов) |
|---|---|---|---|
| Колонки | 395 | **4** | 4 |
| Первичные ключи | 45 | 0 | 45 |
| Индексы | 112 | 0 | 1 |
| Внешние ключи | 110 | **1** | 110 |
| DEFAULT-констрейнты | 73 | **73** | 73 |
| Фильтры индексов | 0 | 0 | 0 |

По структуре (типы, nullability, состав ключей, каскады, состав индексов)
модель сошлась с боевой схемой **полностью**, кроме пяти позиций — и **все пять
оказались уже существующим расхождением между EF6-моделью и боевой схемой**,
а не различием EF6 и EF Core.

## Таблица расхождений

### A. Различия конвенций EF6 и EF Core (чинятся в модели, все починены)

| Что разъехалось | Почему (различие EF6 и EF Core) | Чем чинится | Сложность / открытые вопросы |
|---|---|---|---|
| **Имена таблиц** (все 45) | EF6 плюрализует имя типа (`Character` → `Characters`), EF Core — нет, берёт имя `DbSet`-свойства или имя типа | 45 явных `ToTable("...")` | Тривиально, но забыть нельзя ни одну. Исторические имена не выводятся конвенцией: `GameReport2DTemplate` (без `s`), `ProjectDetails`, `FinanceOperationBankDetails` |
| **`DateTime` → тип колонки** (~35 колонок) | EF6 отображает `DateTime` в `datetime`, EF Core — в `datetime2(7)` | `ConfigureConventions`: `c.Properties<DateTime>().HaveColumnType("datetime")` (+ для `DateTime?`) | Тривиально, одна строка на весь контекст. `DateTimeOffset` совпал |
| **Nullability строк** (~28 колонок) | EF6 не знает про NRT и делает любую `string`-колонку NULL без `[Required]`. EF Core читает NRT-аннотации, а в `JoinRpg.DataModel` включено `<Nullable>annotations</Nullable>` → `string` становится NOT NULL | Проход по модели: всем `string`-свойствам без `[Required]` выставить `IsNullable = true` | **Ключевое решение для ADR.** Либо оставить такой проход навсегда (модель врёт про NRT), либо проставить `?` в ~28 местах `JoinRpg.DataModel` — но это уже изменение схемы (ALTER COLUMN NOT NULL) и отдельная миграция с чисткой данных. Рекомендация: на переключении — проход, чистку выносить отдельными PR после |
| **`[ComplexType]`** (`IntList`, `MarkdownDbValue`, 17 свойств) | В EF Core атрибута нет | `OwnsOne(...)` + явное `HasColumnName("{Свойство}_{Поле}")` | **Оказалось легче, чем ожидал ADR.** Owned type с table splitting дал ровно ту же схему. Имена колонок совпали после явного указания. Complex types EF Core 8+ не понадобились |
| **Many-to-many без явной таблицы** (4 связи, не 1: `PlotFolder.PlotTags`, `PlotElement.TargetCharacters`, `PlotElement.TargetGroups`, `KogdaIgraGame.Projects`) | Разные конвенции имени join-таблицы и колонок | `UsingEntity("ИмяТаблицы", l => …HasForeignKey("X_Xid"), r => …, j => j.HasKey(...))` | Механически, но ADR недосчитал: таких связей **четыре**, а не одна. Порядок колонок в составном PK join-таблицы задаётся явно и важен |
| **Индекс под каждый FK** (13 индексов) | EF6 создаёт индекс под каждый внешний ключ, даже если колонки уже совпадают с (префиксом) PK — например `ProjectDetails.IX_ProjectId`, `CommentTexts.IX_CommentId`, `PlotElementTexts.IX_PlotElementId`. EF Core такие индексы не создаёт | Проход по модели: добавить индекс под каждый FK, если ещё нет индекса, начинающегося с тех же колонок | Не влияет на работу приложения. Но если не добавить — первая миграция будет непустой (13 × `DropIndex`) |
| **Фильтр уникального индекса** (2 индекса) | EF Core делает уникальный индекс по nullable-колонке фильтрованным (`WHERE [X] IS NOT NULL`), EF6 — нет | `.HasFilter(null)` | Тривиально. Касается `ProjectItemTags.TagName` и `IX_UserExternalLogin_UserId_Provider` |
| **Именование PK** (все 45) | EF6: `PK_dbo.Claims`; EF Core: `PK_Claims` | См. раздел «Именование констрейнтов» ниже | См. ниже |
| **Именование FK** (все 110) | EF6: `FK_dbo.Claims_dbo.Users_PlayerUserId`; EF Core: `FK_Claims_Users_PlayerUserId` | То же | То же |
| **Именование индексов** (все 99 неявных) | EF6: `IX_{Колонка}`; EF Core: `IX_{Таблица}_{Колонка}` | То же | То же |

### B. Уже существующее расхождение EF6-модели и боевой схемы (не различие ORM)

Эти пять позиций EF6 **молча терпит** — `NullDatabaseInitializer` отключает
проверку модели против БД, и EF6 никогда не сверяется со схемой. EF Core на них
тоже не упадёт при работе, но **парити-проверка их покажет**, и это как раз то,
ради чего контракт и нужен.

| Что разъехалось | Почему | Чем чинится | Сложность / открытые вопросы |
|---|---|---|---|
| `AccommodationInvites.IsGroupInvite` — колонка есть в БД, в модели нет | Добавлена миграцией `201801280756568_InviteUpdate`, потом свойство удалили из сущности, колонку не дропнули | Либо миграция `DropColumn`, либо явное игнорирование | Надо решить до переключения. Скорее всего — дропнуть отдельной EF6-миграцией **заранее** (см. рекомендации) |
| `Claims.ResponsibleMasterUserId` — в БД `NULL`, в модели `int` (NOT NULL) | Колонка добавлена в 2015 как `c.Int()` (nullable), позже свойство сделали non-nullable без миграции | EF6-миграция `AlterColumn` на NOT NULL (данных с NULL быть не должно — проверить) | Требует проверки данных на проде |
| `Claims.ResponsibleMasterUserId` — FK в БД `NO_ACTION`, модель просит `CASCADE` | Тот же 2015 год: FK создан для nullable-колонки (→ SQL Server поставил NO_ACTION), модель с тех пор объявляет связь обязательной | Тот же `AlterColumn` + пересоздание FK, **или** явное `.OnDelete(DeleteBehavior.Restrict)` в EF Core-модели | Решить: чей вариант правильный. Каскадное удаление пользователя вместе с заявками звучит опасно — вероятно, правильный вариант `Restrict` |
| `ProjectFieldDropdownValues.PlayerSelectable` — в БД `NULL`, в модели `bool` | Миграция `201801111633386` добавила `c.Boolean(nullable: true)` | `AlterColumn` на NOT NULL | Проверить данные |
| `UserAuthDetails.AspNetSecurityStamp` — в БД NOT NULL, в модели `string` без `[Required]` | Миграция `201904181355184` явно поставила `nullable: false`; на самом свойстве атрибута нет | Поставить `[Required]` на свойство (безопасно, аннотация одинаково читается EF6 и EF Core) | Тривиально, можно сделать заранее на EF6 (задача P2) |

### C. DEFAULT-констрейнты — 73 штуки, отдельный риск

| Что разъехалось | Почему | Чем чинится | Сложность / открытые вопросы |
|---|---|---|---|
| В боевой схеме 73 DEFAULT-констрейнта, EF Core-модель не создаёт ни одного | Они появились из `AddColumn(..., defaultValue: …)` в EF6-миграциях — как способ заполнить колонку на существующих строках. В модели их нет, EF6 их тоже не «знает»: они живут только в БД | Ничего, **если** боевую БД не пересоздавать: миграция не применяется, констрейнты остаются | **Самый недооценённый пункт.** Ломается там, где БД **создаётся с нуля** — интеграционные тесты (P0, `JoinApplicationFactory` + Testcontainers) после перевода на EF Core-миграции получат схему **без** дефолтов. Любой `INSERT`, не заполняющий такую колонку, поведёт себя иначе |

Отдельная мелочь: два дефолта содержат «зашитую» дату генерации миграции
(`Projects.CharacterTreeModifiedAt`, `UserAuthDetails.RegisterDate` — значение
`DateTime.Now` на момент создания миграции), то есть в БД каждого окружения они
разные. Воспроизвести их в EF Core-модели нельзя и не нужно.

### D. Именование констрейнтов — 155 объектов

EF6 и EF Core именуют PK, FK и индексы по-разному, и это **нельзя вывести
конвенцией полностью**, потому что часть имён историческая — они пережили
переименования таблиц:

- `FK_dbo.ProjectCharacterFieldDropdownValues_dbo.ProjectCharacterFields_ProjectCharacterFieldId`
  (таблицы давно называются `ProjectFieldDropdownValues` / `ProjectFields`),
- `IX_ProjectCharacterFieldId` на `ProjectFieldDropdownValues.ProjectFieldId`,
- `FK_dbo.FinanceOperations_dbo.Comments_FinanceOperationId` (колонка `CommentId`).

Индексы удалось привести к EF6-именам конвенцией (`IX_{Колонка}`) — осталось
одно историческое имя из 112. PK и FK конвенцией не приводятся.

**Почему это важно, хотя на данные не влияет.** Первая (пустая) миграция
не применяется — значит имена в БД остаются EF6-шными. Но **вторая** миграция,
которая захочет что-то изменить, будет генерировать `DROP CONSTRAINT
[FK_Claims_Users_PlayerUserId]` — по EF Core-имени, которого в БД нет.

**Рекомендация: разовый rename-скрипт на прод** (`sp_rename` для 45 PK + 110 FK
+ 1 индекса) в момент переключения, вместо попытки заставить EF Core
воспроизводить EF6-имена. Скрипт генерируется автоматически сравнением двух
схем — тем же инструментом, что и вся эта сверка.

## Что это меняет в плане ADR015

1. **Посылка подтверждается.** Контракт пустой первой миграции достижим, и цена
   — не переписывание модели, а конечный список из ~10 механических правил.
   Ни одна позиция не потребовала менять `JoinRpg.DataModel`.
2. **`[ComplexType]` оказался не проблемой.** ADR ставил его первым кандидатом
   на непустую миграцию; `OwnsOne` + явные имена колонок закрыли вопрос
   полностью. Риск можно понизить.
3. **Many-to-many: не одна связь, а четыре.** ADR говорит «единственная связь без
   явной таблицы связи» про `PlotFolder.PlotTags`; на деле их четыре
   (`PlotElement.TargetCharacters`, `PlotElement.TargetGroups`,
   `KogdaIgraGame.Projects`). Формулировку в ADR стоит поправить.
4. **NRT-нуллабельность — новый пункт, в ADR его нет.** Это самое массовое
   различие (~28 колонок) и оно не следует ни из чего в тексте ADR. Нужно
   зафиксировать решение (проход по модели против расстановки `?`).
5. **DEFAULT-констрейнты — новый пункт, в ADR его нет.** Прямо бьёт по P0:
   интеграционные тесты на EF Core-миграциях получат другую схему, чем прод.
   Нужен явный пункт в шаге 7 «Сама миграция».
6. **Именование констрейнтов — новый пункт, в ADR его нет.** Без rename-скрипта
   контракт пустой миграции даёт ложное чувство безопасности: первая миграция
   пустая, а вторая упадёт.
7. **Инструмент проверки в ADR назван неточно.**
   `dotnet ef migrations has-pending-model-changes` сравнивает модель со
   **снапшотом миграций**, а не с базой. В прототипе он зелёный — и при этом
   не поймал ни одного из пяти расхождений раздела B, потому что они живут
   ровно между моделью и БД, а снапшоту про БД ничего не известно.
   Формулировка «первая EF Core-миграция пустая» тоже вводит в заблуждение:
   первая миграция по определению непустая (она создаёт все 45 таблиц), пустой
   она была бы только если бы генерировалась поверх уже существующего снапшота.
   Реальный контракт — «схема, которую создаёт первая миграция, совпадает
   с тем, что создали EF6-миграции». Правильная проверка — та, что построена
   в этом спайке: накатить EF Core-миграцию на пустую БД, накатить
   EF6-миграции на другую пустую БД, сравнить `sys.*`. Её и стоит зафиксировать
   автотестом (SQL Server в Testcontainers уже поднимается для P0).
   Формулировку контракта в ADR стоит поправить.
8. **Подготовительная работа, которую можно и нужно сделать заранее, на EF6:**
   дропнуть `AccommodationInvites.IsGroupInvite`; выровнять nullability
   `Claims.ResponsibleMasterUserId` и `ProjectFieldDropdownValues.PlayerSelectable`;
   поставить `[Required]` на `UserAuthDetails.AspNetSecurityStamp`. Это четыре
   маленькие EF6-миграции, каждая релизится отдельно, и они убирают из
   переключения весь раздел B. Логично добавить их в P2.

## Грабли инструментария

`dotnet ef migrations has-pending-model-changes --no-build` **врёт**, если
проект не пересобран после `migrations add`: снапшот живёт в сгенерированном
`.cs`, которого ещё нет в собранной сборке, и команда видит «пустую» исходную
модель — отвечает «Changes have been made», а `migrations add` заново создаёт
все 45 таблиц. После `dotnet build` та же команда отвечает «No changes».
Для автотеста из P3 это значит: сборка перед проверкой обязательна, иначе тест
будет красным всегда и по ложной причине.

## Что не доделано

- **Не проверялся засев baseline-строки** в `__EFMigrationsHistory` на БД,
  созданной EF6 (шаг 5 раздела «Сама миграция» в ADR). Сверка делалась на
  отдельной пустой БД; механика «применить миграции к боевой БД, пометив
  начальную как выполненную» осталась за рамками.
- **Не проверялись**: collation колонок, computed columns, триггеры, sequences
  (в схеме их нет, но сверка на них не смотрела); поведение `IntList`/
  `MarkdownDbValue` при чтении и записи данных (спайк про схему, не про данные).
- Прототип сознательно не реализует `IUnitOfWork` и репозитории — это M2/M3
  из ADR, к контракту парити отношения не имеет.

## Как воспроизвести

```bash
docker compose up -d
# эталон: боевая схема из EF6-миграций
cd src/Joinrpg.Dal.Migrate
ConnectionStrings__DefaultConnection="Data Source=127.0.0.1;User Id=sa;Password=MsSqlPass1!;Initial Catalog=joinrpg_spike;TrustServerCertificate=True" dotnet run
# схема из EF Core-модели (быстрая итерация, без миграций)
dotnet run --project src/JoinRpg.Dal.Impl.EfCorePrototype -- artifacts/proto.sql
# или через настоящую миграцию
dotnet build src/JoinRpg.Dal.Impl.EfCorePrototype
dotnet ef migrations has-pending-model-changes --project src/JoinRpg.Dal.Impl.EfCorePrototype --no-build
dotnet ef migrations script --project src/JoinRpg.Dal.Impl.EfCorePrototype --no-build -o artifacts/initial-migration.sql
# дальше SQL накатывается на пустую БД и обе схемы снимаются запросом по sys.columns /
# sys.indexes / sys.foreign_keys / sys.default_constraints и сравниваются построчно
```

Важно: применять скрипт нужно с `SET QUOTED_IDENTIFIER ON` (`sqlcmd -I`) —
иначе фильтрованные уникальные индексы EF Core падают с Msg 1934.
