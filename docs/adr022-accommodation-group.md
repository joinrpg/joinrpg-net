# ADR022: Группа проживающих — ссылка из заявки и снимок из плана поселения

Проблема:
==

`AccommodationRequest` — это **группа проживающих**: одна строка на всех соседей, которые купили
один тип проживания и живут (или будут жить) вместе. В строке тип, комната и состав (`Subjects`,
обратная сторона `Claim.AccommodationRequest_Id`).

[ADR018](adr018-room-category-plan.md) перенёс на доменный агрегат `RoomCategoryPlan` страницу
комнат и заселение. Там группа уже доменная — `AccommodationGroupInfo`. Остальной контур поселения
по-прежнему читает и решает по EF-сущности:

| Где | Что делает с сущностью |
|---|---|
| `ClaimAccommodationViewModel`, `_ClaimAccommodation*.cshtml` | тип, комната, соседи, свободные места — навигациями |
| `AccommodationInviteViewService` + `IAccommodationRequestRepository` | кандидаты в соседи и свободные места — EF-сущностями `Claim` с `Include` |
| `AccommodationTypeViewService` | «комната назначена», «есть соседи» — навигациями |
| `ClaimListBuilder`, `ClaimFeeViewModel` | тип и имя комнаты цепочкой `claim.AccommodationRequest?.Accommodation?.Name` |
| `AccommodationListViewModel`, `IdExtensions.GetAccommodationTypeIdOrDefault`, `AccommodationExtensions.GetAccommodationType(Claim)` | тип группы — навигацией, хотя он уже есть в `CharacterClaimInfo.AccommodationTypeId` |
| `AccommodationExtensions.GetRoomFreeSpace`, `GetClaimNeighbours`, `GetAllInhabitants` | второй расчёт свободного места рядом с `RoomCategoryPlan.GetFreeSpace` |
| `IClaimService.SetAccommodationType`, `LeaveAccommodationGroupAsync` | возвращают EF-сущность наружу |
| `ClaimServiceImpl`, `AccommodationInviteServiceImpl`, `AccommodationTypeService` | решения («хватит ли мест», «уже соседи») принимаются по навигациям трекаемых сущностей |
| `IAggregateMutationScope.LoadAccommodationGroup*`, `IRoomCategoryPlanWriteRepository.Groups` | EF-сущность в интерфейсах `Data.Interfaces`; второе — территория ADR018, здесь не меняется |

Следствия: ленивые загрузки на странице заявки и в виджете приглашений (#4964), два расчёта
свободного места, которые обязаны совпадать и держатся только тестами, и EF-сущность в публичном
контракте сервиса.

Решение:
==

### 1. Где живёт группа

Рассмотрены четыре варианта.

**Группа целиком внутри агрегата персонажа** (`CharacterClaimInfo` несёт состав и комнату).
Отвергнуто. Группа общая для нескольких персонажей: один факт лежал бы в N снимках, и приём
приглашения менял бы снимки чужих персонажей — агрегат перестал бы быть границей согласованности.
Комната вернулась бы в `CharacterInfo` вопреки [ADR013](adr013-character-info.md), а свободные места
всё равно не посчитать без соседей по комнате, то есть без плана. И каждая загрузка `CharacterInfo`,
включая сетку ролей ([ADR011](adr011-roles-grid-payload.md)), стала бы дороже.

**Собственный агрегат группы со своим props-сервисом.** Отвергнуто: третья машинерия хэндлов, а
почти все изменения состава вызваны жизненным циклом заявки (отказ, смена типа, приём приглашения)
и стали бы межагрегатными в обратную сторону.

**Владение составом группы переходит к `RoomCategoryPlan`.** Отвергнуто: смена типа между
категориями трогает два плана, а отказ от заявки — операция над персонажем — должен был бы менять
план.

**Принято: заявка ссылается на группу, снимок группы берётся из плана поселения, запись остаётся в
контуре персонажа.** Это продолжение таблицы ADR018 §4: состав и тип группы по-прежнему меняет
character-агрегат, комнату — план. Меняется только то, *по чему* принимаются решения и *что* видят
потребители.

### 2. Ссылка из заявки — обязательная

`CharacterClaimInfo` получает поле `AccommodationGroupId` типа `AccommodationGroupIdentification`,
**не опциональное**. Значение знаковое — тот же приём, что у нынешнего
`AccommodationTargetIdentification`:

- положительное — `ClaimId`: у заявки нет группы, она сама себе группа из одного человека;
- отрицательное — `AccommodationRequestId`: заявка состоит в группе.

Поэтому `AccommodationTargetIdentification` переименовывается в `AccommodationGroupIdentification`
и используется в обоих местах: «в какой группе заявка» и «кого приглашаем» — это один и тот же
вопрос, и сравнение «уже соседи?» становится сравнением двух ссылок. Строковая форма содержит имя
типа (`AccommodationTargetId(1--42)` → `AccommodationGroupId(1--42)`) и ходит между островом и
сервером в обе стороны: в адресе `CreateInvite` и в JSON ответа `GetInviteTargets`. Старые префиксы
остаются в `AdditionalPrefixes`, так что запрос старого клиента сервер разберёт. Обратное не
лечится: ответ уже в новой форме, и открытая до релиза вкладка не сможет разобрать список целей
приглашения до перезагрузки. Это принято осознанно — выдавать старую форму ещё релиз ради
открытых вкладок одного виджета не стоит.

«Проживание не выбрано» по-прежнему выражает `AccommodationTypeId == null`, а не пустая ссылка.
Конструктор `CharacterClaimInfo` проверяет инвариант: **тип задан ⇔ ссылка указывает на группу**. В
БД он держится конструкцией — тип хранится только в строке группы, а `SetAccommodationType`
заводит строку даже для одиночки.

Комнаты в `CharacterClaimInfo` по-прежнему нет (ADR013).

### 3. Снимок группы — из `RoomCategoryPlan`

Отдельного загрузчика «группа с соседями» не заводим. Всё, что касается групп, уже есть в плане
категории, из которой селится тип группы: комната группы, её жильцы, вместимости типов и
нерасселённые группы того же типа. План — один запрос с проекцией, без `Include`
(ADR018 §9), и правило свободного места в системе остаётся одно.

План получает методы под потребителей:

- группа по `AccommodationGroupIdentification` заявки (или `null` для одиночки без типа);
- свободное место **для группы**: у расселённой — `GetFreeSpace(комната, тип группы)`, у
  нерасселённой — вместимость типа минус состав. Это нынешний `GetRoomFreeSpace` с двумя
  отличиями: результат не бывает отрицательным (переполненная комната даёт 0, как и
  `GetFreeSpace`), и после ADR020 он ограничен ещё физической вместимостью пула — на
  непереполненных данных результат тот же (ADR020 §2). После переноса EF-версия удаляется;
- соседи заявки: жильцы её комнаты, а если группа не расселена — её состав; без самой заявки.

Чего в плане нет — одиночек без типа: они не состоят ни в одной группе, значит ни в одном плане.
Кандидатов «ещё не выбрал тип проживания» для виджета приглашений даёт отдельный запрос —
утверждённые заявки проекта без группы, идентификаторами и заголовками, не EF-сущностями.

Имена, статусы и персонажи соседей и кандидатов план не несёт (ADR018 §5) — их догружают пачкой
доменными репозиториями заявок (`ICharacterInfoRepository`, или `IClaimInfoRepository` из
[ADR021](adr021-claim-info.md), если он влит к этому шагу; заголовки игроков — через `GetClaimHeadersWithPlayer`). ~~Фильтр
сегодняшних запросов виджета «только `Approved`» сохраняется и применяется по этим статусам:
группа попадает в кандидаты, если в ней есть утверждённая заявка.~~ Для групп фильтр по статусу
снят по ревью #5377: в группу проживающих попадает только утверждённая заявка, а при отклонении
она из группы выбывает. Одиночки без типа по-прежнему берутся только `Approved`. Размер группы при этом
считается **полным составом**, а не числом утверждённых в ней, — так же, как его считает приём
приглашения, который переселяет всех. Сегодня список и приём расходятся, и список предлагает
группу, на которой приём откажет. На снимке прода (2026-05-08) в группах лежат только
`Approved` и `CheckedIn`, так что расхождение касается групп с уже зарегистрированными игроками.

Имя комнаты в списках заявок и в финансах — тем же способом, что уже работает в печати конвертов
(`PrintViewService`): `GetAllPlans` одним запросом на страницу и `FindRoomByClaim`.

### 4. Запись — по снимкам, EF по внешнему ключу

Сервисы записи остаются в контуре `ICharacterPropsService` (ADR014), меняется способ принятия
решений:

- проверки («хватит ли мест», «уже живут вместе», «у приглашающего нет типа») — по доменным
  снимкам: `CharacterClaimInfo` и плану поселения. План внутри мутации берётся новым именованным
  загрузчиком `IAggregateMutationScope` на `ProjectInfo` хэндла, чтобы инвариант ссылочного
  равенства ADR013 не ломался;
- изменение состава — внешним ключом `Claim.AccommodationRequest_Id`, без опоры на
  `Subjects`/`Inhabitants` и relationship fixup EF6;
- `SetAccommodationType` и `LeaveAccommodationGroupAsync` возвращают `Task` без результата.
  Сегодняшний результат — EF-сущность, у новой группы её `Id` до `SaveChanges` равен нулю, а
  вызывающие результат и так отбрасывают.

### 5. Что вне скоупа

- **Схема БД не меняется.** Колонка `AccommodationRequests.IsAccepted` в домен не переносится: в
  коде она ставится только в `Accepted`, на снимке прода от 2026-05-08 все 5401 строка —
  `Accepted`, а единственное чтение (`GetInviteTargets`) фильтрует по этому же значению. Удаление
  колонки — изменение DataModel, отдельное согласование.
- **Легаси-финансы поверх EF** (`Claim.ClaimAccommodationFee` через
  `AccommodationExtensions.GetAccommodationType(Claim)`) остаются на навигации и уходят вместе с
  переводом финансов на `CharacterInfo`. `[Obsolete]` из PR 7 их пометит — это и есть счётчик.
- **Приглашения** (`AccommodationInvite`) остаются EF-сущностями; здесь меняется только то, как
  сервис приглашений читает группы.
- **Отчёт по поселению** (`GetClaimAccommodationReport`) — плоские строки, агрегат ему не нужен.
- **Переход на EF Core** ([ADR016](adr016-efcore-migration.md)) ортогонален.

### 6. План

   префиксы как алиасы. Поведение не меняется.
2. **PR 2**: `CharacterClaimInfo.AccommodationGroupId` с инвариантом §2, маппинг в
   `CharacterInfoLoader`; методы плана из §3 с юнит-тестами, включая совпадение с
   `GetRoomFreeSpace` на тех же данных.
3. **PR 3**: виджет приглашений и диалог выбора типа (`AccommodationInviteViewService`,
   `AccommodationTypeViewService`) — на план, запрос одиночек и доменные репозитории. Закрывает
   #4964.
4. **PR 4**: панель «Проживание» на странице заявки (`ClaimAccommodationViewModel` и оба
   `_ClaimAccommodation*.cshtml`).
5. **PR 5**: тип и имя комнаты в списках заявок и финансах, `AccommodationListViewModel` — тип из
   `CharacterClaimInfo`, комната через `GetAllPlans`.
6. **PR 6**: сервисы записи по §4; `IClaimService` без EF-результатов.
7. **PR 7**: удаление `IAccommodationRequestRepository`, `GetRoomFreeSpace`, `GetClaimNeighbours`,
   `GetAllInhabitants`, `IAggregateMutationScope.LoadAccommodationGroup*`; `[Obsolete]` на
   оставшиеся навигации группы.

Последствия
==

- Правило свободного места живёт в одном месте — `RoomCategoryPlan`.
- Странице заявки и виджету приглашений нужен план категории целиком. Это один запрос с
  проекцией; на категории в сотни человек — килобайты, и это дешевле нынешних `Include` и ленивых
  загрузок.
- `CharacterClaimInfo` растёт на одно поле, проекция `CharacterInfoLoader` — на одну колонку.
- Ссылка на группу общая для заявки и для цели приглашения: один тип, одна строковая форма.
