# Контроль ленивых загрузок в интеграционных тестах

Ленивые загрузки EF6 — источник N+1 на страницах (#4670). Раньше их находили постфактум в логах
прода, чинили одно место, и ничто не мешало им вернуться. Механизм ниже превращает это в измеримый
burndown с защитой от регрессий (#4914).

## Как это работает

1. `LazyLoadCounter` (`JoinRpg.Dal.Impl`) — амбиентный (`AsyncLocal`) счётчик, живущий внутри блока
   `LazyLoadCounter.BeginScope()`. Поле в `MyDbContext` не подошло бы: контекст транзиентен, за
   запрос их создаётся несколько. Scoped-регистрация в DI тоже не подошла: она сделала бы
   `MyDbContext` scoped-зависимым, и валидация скоупов в IdPortal отвергла бы синглтоны, которые
   его потребляют.
2. `EF6LoggerToMSExtLogging` инкрементит счётчик там же, где пишет метрику
   `joinrpg.mydbcontext.lazy_loads` — по той же подписи запроса (единственный параметр
   `EntityKeyValue1`). В проде счётчик никто не читает.
3. `LazyLoadObservingMiddleware` (только в тестовом хосте, ставится через `IStartupFilter`)
   заводит счётчик на время запроса и после отработки пайплайна записывает пару
   «маршрут → число ленивых загрузок».
   Ключ — шаблон маршрута (`GET /{projectId}/plots/Edit`), а не URL: в URL сидят идентификаторы.
4. `LazyLoadAssertingHandler` — `DelegatingHandler` на всех клиентах `JoinApplicationFactory`.
   Помечает запрос заголовком `X-Test-Request-Id`, после ответа забирает свой замер и сверяет
   со снапшотом.

Поскольку счёт живёт в ветке `ExecutionContext` своего запроса, параллельный прогон тестов
механизму не мешает.

**Подключать в тесте ничего не нужно.** Любой тест, который дёргает страницу через
`factory.CreateClient()`, проверяется автоматически.

Сценарии, работающие через сервисы напрямую (без HTTP), заводят счётчик сами:

```csharp
using var counter = LazyLoadCounter.BeginScope();
// ... вызов репозитория/сервиса ...
counter.Count.ShouldBe(0);
```

## Снапшот

`src/JoinRpg.IntegrationTest/TestInfrastructure/lazy-loads-baseline.json` — зафиксированное число
ленивых загрузок по маршрутам.

- **По умолчанию требуется ноль.** Маршрута нет в файле — ленивых загрузок на нём быть не должно.
- В файле перечислены только маршруты, где долг по #4670 ещё есть. Тест падает при росте
  относительно записанного.
- Задача — гнать этот список вниз, пока он не опустеет. Пустой файл `{}` — цель.

## Если тест упал

Сообщение называет маршрут, было/стало. Почти всегда это означает, что в запрос вернулся N+1:
добавьте `Include` или проекцию (см. [linq-queries.md](linq-queries.md)).

Если рост осознанный (например, в запрос добавилась новая сущность) — пересоберите снапшот.

## Как пересобрать снапшот

```bash
JOINRPG_LAZYLOAD_BASELINE=update dotnet test src/JoinRpg.IntegrationTest
```

Прогон перезапишет json в исходниках измеренными значениями — в том числе **опустит** те, где
стало лучше, и **уберёт строчку совсем**, если ленивых загрузок не осталось. Маршруты, не
затронутые прогоном, сохраняются как были, поэтому обновлять снапшот имеет смысл только полным
прогоном. Изменения файла надо закоммитить.
