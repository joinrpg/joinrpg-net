# Контроль ленивых загрузок в интеграционных тестах

Ленивые загрузки EF6 — источник N+1 на страницах (#4670). Раньше их находили постфактум в логах
прода, чинили одно место, и ничто не мешало им вернуться. Механизм ниже превращает это в измеримый
burndown с защитой от регрессий (#4914).

Весь долг собран в зонтичном эпике **#5095**, правила ведения задач — в разделе
[Где живут задачи по долгу](#где-живут-задачи-по-долгу).

## Как это работает

1. `LazyLoadCounter` (`JoinRpg.Dal.Impl`) — амбиентный (`AsyncLocal`) счётчик, живущий внутри блока
   `LazyLoadCounter.BeginScope()`. Поле в `MyDbContext` не подошло бы: контекст транзиентен, за
   запрос их создаётся несколько. Scoped-регистрация в DI тоже не подошла: она сделала бы
   `MyDbContext` scoped-зависимым, и валидация скоупов в IdPortal отвергла бы синглтоны, которые
   его потребляют.
2. `EF6LoggerToMSExtLogging` инкрементит счётчик там же, где пишет метрику
   `joinrpg.mydbcontext.lazy_loads` — по той же подписи запроса (единственный параметр
   `EntityKeyValue1`). В проде счётчик никто не читает.
3. `LazyLoadObservingMiddleware` (только в тестовом хосте, ставится через `IStartupFilter`)
   заводит счётчик на время запроса и после отработки пайплайна записывает пару
   «маршрут → число ленивых загрузок».
   Ключ — шаблон маршрута (`GET /{projectId}/plots/Edit`), а не URL: в URL сидят идентификаторы.
4. `LazyLoadAssertingHandler` — `DelegatingHandler` на всех клиентах `JoinApplicationFactory`.
   Помечает запрос заголовком `X-Test-Request-Id`, после ответа забирает свой замер и сверяет
   со снапшотом.

Поскольку счёт живёт в ветке `ExecutionContext` своего запроса, параллельный прогон тестов
механизму не мешает.

**Подключать в тесте ничего не нужно.** Любой тест, который дёргает страницу через
`factory.CreateClient()`, проверяется автоматически.

Сценарии, работающие через сервисы напрямую (без HTTP), заводят счётчик сами:

```csharp
using var counter = LazyLoadCounter.BeginScope();
// ... вызов репозитория/сервиса ...
counter.Count.ShouldBe(0);
```

## Откуда в снапшоте берутся маршруты

Механизм знает только те маршруты, куда тесты реально сходили, поэтому за покрытие отвечает
отдельный сценарий — `AllGetPagesSmokeScenario` (#4956). Он берёт все GET-эндпоинты приложения из
`EndpointDataSource` уже поднятого хоста, подставляет в шаблоны маршрутов значения из
сид-проекта (`SmokeProjectFixture`) и открывает каждую страницу под мастером, проверяя код ответа.
Сценария на каждую страницу не нужно: параметры заполняются **по имени**, поэтому новая страница с
привычным `projectId`/`characterId` попадает под смоук сама.

Что важно знать, если смоук упал:

- **Молча ничего не пропускается.** Эндпоинт, до которого смоук не смог дойти, валит тест с именем
  маршрута. Дальше выбор: досеять данные в `SmokeProjectFixture` или записать маршрут в
  `SmokeExpectations.Skipped` с причиной. Записи про исчезнувшие маршруты тоже валят тест — чтобы
  списки не превращались в свалку.
- **Ожидается ровно 200.** Клиент смоука намеренно не ходит по редиректам: иначе 302 на страницу
  входа выглядел бы как честный 200. Легаси-редиректы перечислены в
  `SmokeExpectations.ExpectedStatus`.
- **Один экшен может дать два ключа в снапшоте.** Ключ — шаблон маршрута, а `CharacterController.Details`
  навешан двумя атрибутами (`/{projectId}/character/{characterid}/` и `.../details`). Код один,
  поэтому и число ленивых загрузок одинаковое — просто строчек в файле две.
- **Страницы аккаунта и профиля смоук не обходит.** Они висят на конвенциональном маршруте
  `{controller}/{action}`, то есть в снапшоте слились бы в одно ведро с максимумом по всем экшенам.
  Чтобы их покрыть, ключ снапшота надо нормализовать до пары «контроллер+экшен» — отдельная задача.

Отдельно стоит помнить, что **число в снапшоте не измеряет масштаб долга**. На сид-проекте N+1
даёт единицы ленивых загрузок, на живом проекте то же место разворачивается по числу персонажей и
игроков: у страницы персонажа в снапшоте стояла единица, пока в логах прода она была самым тяжёлым
маршрутом окна — 1443 ленивых загрузки (#4956). Снапшот — защита от регрессий, а не оценка по #4670,
и «1» в файле не значит «почти починено».

И наоборот: **ноль в замере может означать «в сиде нет данных», а не «N+1 нет».** Маршрут
`rooms/{roomTypeId}/details` смоук честно обходил и честно мерил в ноль, потому что у типа
поселения в сиде не было ни одного жильца — цикл по жильцам не делал ни одной итерации. На проде
тот же код давал 296 ленивых загрузок за окно, больше четверти всех (#5070). Поэтому, если страница
показывает список, сид должен наполнять этот список: догруженный сид расселением сразу подсветил
долг ещё на 18 маршрутах, которые до этого измерялись в ноль по той же причине.

## Где живут задачи по долгу

Зонтичный эпик — **#5095** («Эпик: искоренить ленивые загрузки (N+1) — burndown
lazy-loads-baseline»). Раньше родителем был #4670, он закрыт; ссылаться теперь надо на #5095.

- Новая находка — **отдельный issue, подзадачей к #5095** (GitHub sub-issue), а не комментарий в
  эпик. В подзадаче: замер (окно, прод-сборка, таблицы и числа), маршрут, где смотреть в коде,
  чего ждём после фикса.
- Если одна и та же таблица догружается на нескольких не связанных маршрутах — это общий корень, и
  ему нужна своя подзадача («починить в одном месте проверки прав»), а точечные при этом остаются.
  Так сделано в #4987 для `ProjectDetails` и в #4989 для `ProjectAcls`.
- В подзадаче сразу указывается, **ловится ли долг интеграционниками**: есть ли маршрут в
  `lazy-loads-baseline.json` с ненулевым числом. Если маршрута там нет, замер равен нулю: ни
  регрессию, ни успех фикса тест не покажет, и в подзадаче нужен отдельный пункт про покрытие —
  сид, HTTP-тест на POST-ручку или `LazyLoadCounter.BeginScope()` в сервисном сценарии.
- Definition of done эпика — пустой `lazy-loads-baseline.json` (`{}`).

## Снапшот

`src/JoinRpg.IntegrationTest/TestInfrastructure/lazy-loads-baseline.json` — зафиксированное число
ленивых загрузок по маршрутам.

- **По умолчанию требуется ноль.** Маршрута нет в файле — ленивых загрузок на нём быть не должно.
- В файле перечислены только маршруты, где долг по #4670 ещё есть. Тест падает при росте
  относительно записанного.
- Задача — гнать этот список вниз, пока он не опустеет. Пустой файл `{}` — цель.

## Если тест упал

Сообщение называет маршрут, было/стало. Почти всегда это означает, что в запрос вернулся N+1:
добавьте `Include` или проекцию (см. [linq-queries.md](linq-queries.md)).

Если рост осознанный (например, в запрос добавилась новая сущность) — пересоберите снапшот.

## Как пересобрать снапшот

```bash
JOINRPG_LAZYLOAD_BASELINE=update dotnet test src/JoinRpg.IntegrationTest
```

Прогон перезапишет json в исходниках измеренными значениями — в том числе **опустит** те, где
стало лучше, и **уберёт строчку совсем**, если ленивых загрузок не осталось. Маршруты, не
затронутые прогоном, сохраняются как были, поэтому обновлять снапшот имеет смысл только полным
прогоном. Изменения файла надо закоммитить.
