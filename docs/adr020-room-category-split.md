# ADR020: Разделение типа проживания и категории комнат

Проблема:
==

Сейчас тип проживания и набор комнат — одно и то же: комнаты принадлежат типу
(`ProjectAccommodation.AccommodationTypeId`). Мастеру нужно другое: категория комнат «Люкс» с
комнатами 101 и 102 и несколько типов проживания поверх неё — «Люкс с пятницы», «Люкс с четверга»,
«Люкс на одного». У каждого типа своя цена, а селятся они из общих комнат.

[ADR018](adr018-room-category-plan.md) (§2, «Задел на разделение») подготовил к этому доменную
модель, но схему БД намеренно не трогал:

- `RoomCategoryPlan` — агрегат **пула** комнат, внутри коллекция типов, а не один тип;
- `AccommodationTypeInfo.RoomCategoryId` — пул типа узнаётся только из метаданных;
- правило свободного места рассчитано на комнату, где живут группы разных типов;
- `AccommodationGroupInfo` знает свой тип.

Своей таблицы у категории пока нет. Её id совпадает с id типа, и это допущение живёт в нескольких
местах DAL: в маппере метаданных, в загрузчике и write-репозитории плана, в колонке комнаты.
Кроме того, его держит тест-страж `RoomCategoryId_TodayEqualsAccommodationTypeId`. Этот ADR
заменяет допущение настоящей категорией, причём самым простым из работающих способов.

Решение:
==

**Категория комнат — отдельная настройка проекта.** Комнаты принадлежат категории, тип проживания
ссылается на категорию. При создании типа мастер выбирает: завести новую категорию (и задать ей
имя) или взять существующую.

### 1. Схема

| Таблица | Изменение |
|---|---|
| `ProjectRoomCategories` | новая: `Id`, `ProjectId`, `Name` |
| `ProjectAccommodationTypes` | + `RoomCategoryId` (FK, NOT NULL) |
| `ProjectAccommodations` | `AccommodationTypeId` → `RoomCategoryId` (FK, NOT NULL) |

`AccommodationRequests` не меняется: группа по-прежнему покупает **тип**, а живёт в **комнате**.
Категория группы выводится из её типа.

Существующие данные переносятся одной миграцией. Для каждого типа заводится категория **с тем же
`Id`** (`SET IDENTITY_INSERT`) и тем же именем, после чего колонки заполняются копированием:
`type.RoomCategoryId = type.Id`, `room.RoomCategoryId = room.AccommodationTypeId`. Поэтому на старых
данных никакие идентификаторы не меняются и пересчитывать ничего не нужно. Identity-счётчик
категорий SQL Server после явной вставки сдвигает за наибольший `Id` сам.

Каскады: проект → категория и проект → тип без каскада (как у соседних таблиц, иначе SQL Server
отвергнет несколько каскадных путей). Категория → комнаты с каскадом. Тип → категория без каскада.

### 2. Физическая вместимость — максимум по типам пула

ADR018 §2 развёл две вместимости: физическую (сколько мест в комнате, свойство категории) и
продаваемую (скольких селим по этому типу, свойство типа). Отдельной колонки под физическую **не
заводим**: `RoomCategoryPlan.RoomCapacity` = максимум `Capacity` типов пула.

Правило свободного места ADR018 от этого не меняется:

```
effective(room)       = min(RoomCapacity, min по типам жильцов)
freeSpace(room, type) = min(effective(room), type.Capacity) − occupancy(room)
```

Максимум по типам никогда не ограничивает сильнее, чем `type.Capacity` того, кого селят, поэтому
`freeSpace` получается тем же, что и без физической вместимости вообще. Остаётся она только в
сводных цифрах («сколько всего мест» = комнаты × `RoomCapacity`). Взамен мастеру не нужно вводить и
согласовывать второе число «вместимость» в форме. Если в будущем понадобится комната, физически
большая любого из продаваемых типов, колонка добавляется отдельно, без пересмотра этого решения.

### 3. Метаданные

`ProjectAccommodationSettings` получает коллекцию `RoomCategories` с элементами
`RoomCategoryInfo(RoomCategoryIdentification Id, string Name)`. По критерию
[ADR015](adr015-accommodation-types-in-project-info.md) это настройка мастера: она меняется редко и
нужна в формах и заголовках. Поэтому категория лежит в `ProjectInfo`, а меняется через
`IProjectPropsService`. Имя `RoomCategoryInfo` ADR018 зарезервировал именно для неё.

Комнаты в метаданные по-прежнему не входят: это оперативные данные агрегата `RoomCategoryPlan`.

### 4. Операции

- **Создание типа**: `AccommodationTypeRequest` получает выбор категории — существующий
  `RoomCategoryIdentification` или имя новой. Новая категория создаётся в той же мутации
  метаданных, что и тип.
- **Изменение типа**: категорию не меняет. Перенос типа в другой пул означал бы переселение его
  групп, это отдельная задача.
- **Переименование категории**: отдельная операция метаданных.
- **Удаление типа**: нельзя, пока есть *расселённые группы этого типа* (раньше проверялось «есть
  занятые комнаты типа», при 1:1 это одно и то же). Если тип в категории последний, вместе с ним
  удаляется и категория, а каскадом её комнаты. Так ведёт себя и нынешнее удаление типа. Если
  нет, комнаты остаются у сестринских типов.
- **Выселение типа** (`UnOccupyRoomType`) уже выселяет только группы этого типа, соседи из
  сестринских типов остаются в комнатах. Код не меняется.

### 5. UI

- Форма создания типа: переключатель «Новая категория комнат» (поле имени, по умолчанию имя типа)
  или «Существующая категория» (список). При редактировании категория только показывается.
- Страница комнат (`/{projectId}/rooms/{roomTypeId}/details`) показывает **весь пул**: все комнаты
  и все нерасселённые группы категории. Если типов в пуле больше одного, у групп подписан тип.
  Маршрут по-прежнему открывается по типу: это внешний URL, а мастер приходит на страницу через тип.
- Сводка `/{projectId}/rooms`: у типа подписана категория. Счётчики комнат (всего, свободных,
  заполненных) считаются по категории, итоги по проекту не учитывают одни и те же комнаты дважды.
  «Комната заполнена» — `occupancy >= effective(room)` из правила свободного места, а не сравнение
  с вместимостью одного типа.

### 6. Что вне скоупа

- перенос типа между категориями;
- удаление категории отдельно от типов и отдельная страница категорий;
- физическая вместимость отдельной колонкой (§2);
- автозаселение (`OccupyAll`), как и в ADR018.

Последствия
==

- Временное допущение ADR018 §2 исчезает: id категории и id типа совпадают только на данных,
  созданных до миграции, и ни один код на это больше не опирается.
- `ProjectInfo` растёт ещё на одну настройку.
- Физическая вместимость пула вычисляется, а не хранится. Пока типы продаются не больше
  физических мест, разницы нет. Комнату «на шестерых, продаваемую по двое» выразить нельзя, но и
  по нынешней формуле лишние места в ней никому не достались бы.
