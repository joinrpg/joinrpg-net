# big-task §5: реализация субагентами-исполнителями — план внедрения

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Заменить в скилле big-task критерий делегирования «по файлам» на координаторскую схему: каждый PR пишет субагент-исполнитель в чистом контексте, главный агент координирует.

**Architecture:** Документационная правка одного markdown-файла. §5 «Реализация» переписывается по каркасу из дизайна; существующие защиты (границы файлов, проверки на выходе, «дефект — описать, не править», грабли) сохраняются и адресуются брифу исполнителя. §1 получает одну согласующую строчку. Кода и тестов нет.

**Tech Stack:** Markdown, git.

**Spec:** `docs/superpowers/specs/2026-11-04-big-task-subagent-implementation-design.md`

## Global Constraints

- Канонический файл — `.agents/skills/big-task/SKILL.md`; `.claude/skills` — симлинк, отдельно не править.
- Стиль: русский язык, существующий тон и форматирование скилла (длина строк ~100, заголовки `##`/`###`, жирные ключевые слова).
- §2, §3, §4, §6–8 и «Когда остановиться»/«Разбор сессии диалогом» не меняются.
- CRLF: файл с переводами строк как в репо (git сам нормализует; править через Edit, не потоковыми утилитами).
- Коммит — по правилам репо: `-m`, без `--edit`, подпись не нужна (коммит, не сообщение GitHub).

## Review Focus

```markdown
## 5. Реализация

Реализация идёт в чистых контекстах: **каждый PR пишет отдельный субагент-исполнитель**,
главный агент остаётся координатором — держит план, разбирает ревью, публикует и
мониторит стек (§6–8), код сам не пишет. Исключение — мелкая связная правка, которая
влезает в один заход (ориентир — до получаса): собрать бриф для такого объёма дороже,
чем сделать самому.

Почему так. Контекст главного агента растёт с каждым PR, и каждый его запрос платит
за весь накопленный контекст: замер сессии ADR029 дал 91% cache_read на два хода
реализации в одном контексте, выросшем до 440k токенов на запрос. Субагент-исполнитель
начинает с чистого листа — его контекст это только бриф и прочитанный код.

### Бриф исполнителя — самодостаточный, собирается из плана, а не из памяти о чате

Исполнитель не видел разведки и обсуждений. Бриф обязан содержать:

- **цель PR и ссылку на план-файл** (§2): какой шаг стека делается, из какого состояния
  в какое переходит код;
- **worktree** (§4): собственный, имя по конвенции `joinrpg-net.<тема>`;
- **границы файлов**: какие файлы можно менять, какие нельзя (перечислить смежные,
  которые правит координатор или соседние PR);
- **осознанные решения**: что принято и почему, что осознанно не делается;
- **проверки на выходе**: `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes
  --severity warn` — все зелёные, результат привести в отчёте;
- **что делать с найденным дефектом**: не править production-код, а описать в отчёте и
  оставить тест `[Fact(Skip = "причина")]`. Иначе субагент «починит» то, чего не понимает;
- **запрет на git-операции**: ни коммитов, ни переключения ветки, ни ребейза — git
  делает координатор, чтобы PR оставался в одном коммите (§3).

Критерий применимости: если решение нельзя передать текстом — этот кусок координатор
делает сам, а не натягивает бриф. Бриф дешевле раздутого контекста, но не бесплатен.
```
