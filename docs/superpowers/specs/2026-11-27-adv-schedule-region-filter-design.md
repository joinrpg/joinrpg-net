# Дизайн: фильтр расписаний рекламы (AdvSchedule) по регионам

Дата: 2026-11-27
Статус: предложено
Зависит от: PR #6316 (ветка `region-data`) — enum'ы `Region`/`MacroRegion` в `JoinRpg.Common.PrimitiveTypes`

## Зачем

Расписания рекламы (`AdvSchedule`) публикуют игры во внешних каналах (Telegram-каналы сообществ).
Каналы региональных сообществ должны показывать игры своего региона. Сегодня фильтрации по
региону нет — кандидаты выбираются из всех публичных проектов.

Задел уже есть: поле `AdvertisementScheduleEntity.RegionsFilter` (string?, nvarchar(max))
создано миграцией `AddAdvertisementChannelsAndSchedules` и проброшено в домен
(`AdvertisementScheduleInfo.RegionsFilter`), но нигде не используется. Регион у игры сегодня —
только строковое `KogdaIgraGame.RegionName` из КогдаИгры, числового id в БД нет.

## Поведение

- У расписания есть список регионов (фильтр).
- Пустой или отсутствующий фильтр — текущее поведение: все регионы. Это гарантирует
  обратную совместимость со всеми существующими расписаниями (`RegionsFilter = NULL`).
- Фильтр задан: кандидатами являются только проекты, у которых есть активная привязанная
  игра КогдаИгры с `RegionId`, входящим в список. Проекты без карточки КогдаИгры или с
  неизвестным регионом (`RegionId = NULL`, в т.ч. id вне enum'а) исключаются.
- Семантика точная: регион должен совпадать у **той карточки КогдаИгры, которая будет
  показана в рекламе** (`NearestFutureOkKogdaIgraCard`), а не у любой игры проекта.
  Иначе проект с прошлой игрой в регионе X и будущей в регионе Y пройдёт фильтр канала
  X, но покажет игру региона Y. Реализация: предикат в репозитории с критериями
  выбора карточки (Active + будущая `Begin` + статус Ok + в регионе) для формирования
  пула кандидатов, плюс страхующая проверка в джобе, что регион фактически выбранной
  карточки входит в фильтр (случай двух будущих карточек в разных регионах).
- Фильтр применяется ко всем методам выбора кандидатов по пулу проектов: `SingleHotRole`
  (общий канал) и `NewlyOpenedProjectsDigest`. Каналы с `BoundProjectId` не фильтруются:
  там рекламируется один привязанный проект, региональный фильтр к нему неприменим.

## Цели

- Надёжная фильтрация по региону через числовые id enum'а `Region`, а не строковые имена.
- Семантика «пустой фильтр = все регионы».
- Фильтрация на уровне запросов кандидатов в репозитории, а не пост-валидацией в джобе —
  иначе ранжирование (`AdvertisementGameRanking`) и кулдаун считаются по неотфильтрованному пулу.

## Вне целей

- UI редактирования фильтра: значения проставляются в БД напрямую (как и сами расписания
  сегодня — они создаются миграцией, админский UI только читает).
- Макрорегионы в фильтре: храним и матчим плоский список `Region`.
- Показ бейджа региона на страницах портала (отдельная задача из #6316, здесь не нужен).

## Анти-цели

- Матчинг по display-именам регионов (имена — показные строки КогдаИгры, могут меняться).
- Ломающие изменения существующих расписаний или публичных API пакетов без необходимости.

## Принятые решения (подходы)

1. **Механика матчинга**: по enum `Region` из #6316, а не по строке `RegionName` и не гибрид —
   надёжность. Побочное следствие: регион надо дотащить из API КогдаИгры до БД (PR A ниже).
2. **Ветвление**: стек поверх ветки `region-data`, а не ожидание вливания #6316 — снимает
   зависимость от скорости ревью; дифф фичи будет включать изменения #6316, пока тот не влит.
3. **Уровень применения фильтра**: в LINQ-запросах `ProjectRepository` — см. «Цели».
4. **UI**: без формы редактирования.
5. **Макрорегионы**: не поддерживаем в фильтре.

## Разрез на PR

Стек: `region-data` (#6316) → PR A «Регион в данных КогдаИгры» → PR B «Фильтр AdvSchedule по регионам».
Каждый следующий ребейзится по мере вливания предыдущего.

### PR A: регион в данных КогдаИгры

- `JoinRpg.Common.KogdaIgraClient`: добавить в JSON-запись `kogda_igra_game_data` поле
  `sub_region_id` (int?) и пробросить в `KogdaIgraGameInfo.SubRegionId`. Пакет IsPackable —
  CHANGELOG («Не выпущено») и PublicAPI (`scripts/Update-PublicApi.ps1`).
- `JoinRpg.DataModel`: `KogdaIgraGame.RegionId` (`Region?`, nullable enum из
  `JoinRpg.Common.PrimitiveTypes`; EF6 маппит enum в int-колонку). Согласовано с @leotsarev.
- EF6-миграция (`src/JoinRpg.Dal.Impl/Migrations/`, порядок — `docs/ef-migrations.md`):
  `AddColumn RegionId` + бэкфилл из уже хранимого сырого ответа КогдаИгры
  (`UPDATE … SET RegionId = TRY_CAST(JSON_VALUE(JsonGameData, '$.sub_region_id') AS int)`, по образцу
  миграции `AddKogdaIgraGameStatus`). Ручной полный ресинк не нужен. NULL остаётся у записей без
  `sub_region_id` в JSON (удалённые игры с `JsonGameData="{}"`, заглушки). Id вне справочника `Region`
  бэкфилл записывает как есть — он не совпадёт ни с одним фильтром, а ближайшая синхронизация игры
  приведёт его к NULL.
- Синхронизация: `KogdaIgraSyncService` заполняет `RegionId` при каждом обновлении карточки.
- Домен: `KogdaIgraGameData.RegionId` (`Region?`).
- Обновить `docs/db-schema.md` (секция KogdaIgraGames; сверяется `DbSchemaDocumentationScenario`).

### PR B: фильтр AdvSchedule по регионам

- **Формат хранения**: `RegionsFilter` — строка с id регионов через запятую (например
  `"1,2,33"`); пустая или `NULL` = нет фильтра. Парсинг — чистая функция в
  `JoinRpg.Services.Advertisement` (рядом с `AdvertisementGameRanking`), без regex,
  на выходе `IReadOnlySet<Region>?`.
- **Домен**: `AdvertisementScheduleInfo` — добавить распарсенное `Regions`
  (`IReadOnlySet<Region>?`); сырая строка остаётся в маппере (`AdvertisementEntityMapper`).
- **Предикаты**: `GetPublicProjectsOpenForHotRoleAdvertisement` и
  `GetPublicProjectsOpenedForClaimsInLastWeek` принимают набор регионов (nullable =
  без изменений); LinqKit-предикат в `ProjectPredicates` по критериям карточки
  (Active + будущая `Begin` + статус Ok + `RegionId` в списке; `RegionId` в DataModel
  уже типа `Region?`, cast не нужен) — по аналогии с `HasFutureKogdaIgraGame`.
- **Джоба**: `AdvertisementJob` распарсивает фильтр расписания один раз, передаёт
  в запросы и после выбора карточки проверяет, что её регион входит в фильтр
  (точная семантика, см. «Поведение»).
- **Админская сетка** (`AdvertisementSchedulesGrid.razor`): вместо сырой строки — имена
  регионов (`RegionDisplay`, короткие имена через запятую), пусто = «Все регионы».
- **Тесты**: парсер фильтра, предикаты (`ProjectPredicatesTest`), маппер
  (`AdvertisementEntityMapperTest`); интеграционный сценарий по аналогии с
  `AdvertisementProjectRankingScenario` (прогон в CI, локально — нет).

## Оставлено билдеру

- Подтверждено: значения enum'а `Region` равны `sub_region_id` из API КогдаИгры
  (документировано в `Region.cs` на ветке `region-data`, снапшот-тесты значений).
  Прямое сравнение id корректно, маппинг-таблица не нужна.
- Точные имена полей JSON API КогдаИгры (сверить `sub_region_id` с реальным ответом/API
  репозитория kogda-igra).
- Детали бэкфилла: маппинг имён, разбор конфликтов и нераспознанных имён, логирование.
- Незначительные решения по форме кода — по существующим конвенциям проекта.
