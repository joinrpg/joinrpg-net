# Гостевое поселение: вернуть «бесконечное число мест»

Дизайн + план реализации для issue [#1945](https://github.com/joinrpg/joinrpg-net/issues/1945).

**Статус: реализовано (подход A), 10.11.2026.** Фактическая реализация по коммитам ветки
plan1945; документ сохранён как история принятия решений.

## Intent

Вернуть «гостевое поселение» — тип проживания, в который игрок селится без комнаты
и без ограничения по местам (например «своя палатка» / «проживание с самостоятельным
выбором условий»). Требования из issue:

1. Не привязано ни к какой категории (функционально — не требует пула комнат).
2. Нет количества мест в комнате (вместимость бесконечна).
3. Нельзя никого приглашать (приглашения бессмысленны — мест всегда хватает).
4. Сумму (стоимость) выбирать можно — мастер задаёт цену типа как обычно.
5. Добавляется по умолчанию при создании нового проекта.

## Почему сейчас

Колонка `IsInfinite` в `ProjectAccommodationType` существует с 2018 года
(миграция `201801270954367_Accommodation`), но функциональность не была доделана:
коммит `d125c716a` (PR #1955, 2022-10-11) перестал ставить флаг при создании
проекта и пометил его «Not implemented yet». ADR015 и ADR018 закрепили заглушку
`AccommodationTypeInfo.IsInfinite => false` с явным обещанием: «когда функциональность
реализуют, свойство станет настоящим параметром записи, читаемым из колонки, и
потребителей менять не придётся». Задача — выполнить это обещание.

## Цели

- Мастер может создать тип проживания с режимом «бесконечное число мест» (гостевое).
- Игрок выбирает такой тип в заявке; расселение в комнату не требуется и не предлагается.
- Для таких типов не действуют ограничения вместимости (ни лимит типа, ни лимит комнат).
- Приглашения (invites) и групповое заселение с обязательной комнатой недоступны
  для заявок с гостевым типом.
- При создании проекта-конвента гостевой тип создаётся по умолчанию.
- Стоимость гостевого типа задаётся мастером (поле Cost работает как обычно).

## Не-цели

- Nullable `RoomCategoryId` / отказ от обязательной категории комнат (ADR020).
  Функционально гостевой тип «не привязан к категории», но физически категория
  создаётся как и для любого типа — просто в ней нет комнат и ей не пользуются.
- «Цена от игрока» (игрок сам вводит сумму). Issue читается как «мастер может
  назначить стоимость», а не как свободный ввод суммы игроком.
- Миграция существующих проектов: мастера добавят гостевой тип вручную, если нужно.
- `IsAutoFilledAccommodation` — второй нереализованный флаг, в рамках задачи не трогаем.

## Анти-цели

- Ломающие изменения в `RoomCategoryPlan`/правиле свободного места для обычных типов.
- Новые колонки в БД (не нужны — `IsInfinite` уже есть).

## Подходы (и выбор)

### Подход A: оживить флаг `IsInfinite` (выбран)

Колонка, часть UI-развязки (`FreeCapacity == null` в `AccommodationListViewModel.cs:60`,
бейдж «Бесконечное» в `RoomTypeListRow.razor`) и доменная заготовка уже существуют.
Изменения: метаданные → запросы → валидации → UI → дефолт при создании проекта.
Миграция БД не нужна.

### Подход B: `RoomCategoryId == null` как третий вариант выбора

Предложен в комментарии к issue (2026-10-25), но принят до него ADR020 (октябрь 2026,
миграция `202610072300087_AddRoomCategories`) сделал категорию обязательной на уровне
схемы (NOT NULL FK в двух таблицах), доменной модели (`AccommodationTypeInfo.RoomCategoryId`
не-nullable) и плана поселения (конструктор `RoomCategoryPlan` требует совпадения id).
Вариант B потребует nullable FK + миграцию + развилки в плане/удалении/свободных местах —
существенно дороже и конфликтует с недавним ADR. Функционально эквивалентен A.

Выбран подход A. Если лео предпочтёт семантически «настоящую» отвязку от категории —
это отдельное обсуждение и отдельный объём работы.

## Ключевые изменения

### 1. Домен и метаданные

- `src/JoinRpg.DomainTypes/ProjectMetadata/Accommodation/AccommodationTypeInfo.cs`:
  убрать заглушку `IsInfinite => false`, сделать `IsInfinite` параметром записи
  (по аналогии с `IsPlayerSelectable`), читаемым из колонки. Убрать комментарий
  «Not implemented yet» из `src/JoinRpg.DataModel/ProjectAccommodationType.cs:21`.
- Обновить `src/JoinRpg.DomainTypes.Test/ProjectMetadata/AccommodationTypeInfoTest.cs`
  — там три места жёстко закрепляют `IsInfinite == false` (строки 23, 44, 58).

### 2. Сервисный слой

- `AccommodationTypeRequest` (`src/JoinRpg.Services.Interfaces/ProjectMetadata/IAccommodationTypeService.cs:11`):
  добавить `IsInfinite`. При `IsInfinite = true` Capacity не валидируется/игнорируется
  (DataModel `Capacity` обязателен — в схеме оставить, при создании записывать
  значение по умолчанию, например 1, но не показывать в UI).
- `AccommodationTypeService` (`src/JoinRpg.Services.Impl/Projects/Metadata/AccommodationTypeService.cs`):
  прокинуть флаг при создании/обновлении.
- Правило свободного места (`src/JoinRpg.DomainTypes/Accommodation/RoomCategoryPlan.cs`):
  группы с `IsInfinite`-типом не ограничиваются вместимостью —
  `GetFreeSpaceForGroup` / `GetEffectiveCapacity` для них возвращают «бесконечно».
  Это автоматически снимает блокировки в `AccommodationInviteServiceImpl` и
  `MergeAccommodationGroups`.
- Приглашения: запретить создание приглашений **из** заявок с гостевым типом
  (`AccommodationInviteServiceImpl.CreateAccommodationInvite`, ~строка 21) — по
  требованию issue «нельзя никого приглашать». Принимать приглашения в гостевой
  тип не требуется, так как группа с гостевым типом — всегда одиночная.
- `ClaimServiceImpl.SetAccommodationType` (`src/JoinRpg.Services.Impl/Claims/ClaimServiceImpl.cs:865`):
  убедиться, что выбор гостевого типа не требует/не пытается занять комнату
  (сейчас создаёт одиночную группу без комнаты — скорее всего работает как есть,

10. Ревью субагентом (`pr-reviewer`) → PR с `Closes #1945` и подписью инструмента.

## Допущения (проверить с @leotsarev)

1. **Терминология UI**: «Гостевое поселение» — название типа по умолчанию и
   подпись режима в форме (строки UI на русском).
2. **«Сумму выбирать можно»** трактуется как «мастер назначает стоимость гостевого
   типа обычным полем Cost» (не свободный ввод суммы игроком).
3. **«Нельзя никого приглашать»** = запрет создания приглашений из заявок с
   гостевым типом; гостевой тип всегда одиночный (без групп/сожителей).
4. **Существующие проекты не мигрируются** — гостевой тип появляется только в
   новых проектах и по ручному добавлению мастером.
5. **Capacity при IsInfinite** не удаляется из схемы (не-цель), в UI скрывается.
