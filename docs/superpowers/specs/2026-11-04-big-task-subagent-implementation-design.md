# Дизайн: big-task — связные PR пишут субагенты-исполнители

Дата: 2026-11-04
Статус: утверждён

## Намерение и почему

Скилл big-task (§5 «Реализация») сейчас рекомендует связную правку делать самому
главному агенту, делегируя субагентам только куски, отделяющиеся по файлам. На стеке
из нескольких PR это приводит к монотонному росту контекста главного агента: каждый
API-запрос платит cache_read за весь накопленный контекст.

Эмпирика (разбор сессии «Claude Code ADR029», отчёт
`~/.superpowers/diagnosing-superpowers/ebf8987f-f339-4238-9b1b-150b9e57e375/report.md`):

- 91% дедуплицированного cache_read сессии (~85M токенов) пришлось на два хода
  реализации, где один контекст вырос с ~50k до 440k токенов на запрос;
- ревью субагентами (те же субагенты, маленькие контексты) суммарно дали ~4% cache_read
  основной сессии и при этом поймали блокер (случайно сломанный URL → 404) плюс ~15
  дефектов до пуша.

Вывод: главный агент должен оставаться координатором (план, разбор ревью, публикация,
мониторинг), а код каждого PR писать субагент-исполнитель в чистом контексте. Решения
по задаче к этому моменту уже зафиксированы в плане (§2 скилла), то есть бриф исполнителя
собирается из артефакта, а не из памяти о чате.

## Цели

- Каждый PR реализуется в чистом контексте субагента-исполнителя; контекст главного
  агента между PR не растёт.
- Бриф исполнителя — самодостаточный и собирается из плана механически.
- Мелкая связная правка (влезает в один заход, ~полчаса) по-прежнему делается самим —
  сборка брифа для такого объёма дороже работы.

## Не-цели

- Не менять §6 (ревью субагентами на каждый PR) — оно окупилось и остаётся.
- Не менять §3 (нарезка стека), §4 (worktree), §7–8 (публикация, мониторинг, ребейз).
- Не вводить жёсткий числовой порог «с N PR обязательно субагенты»: выбор делается
  критерием самодостаточности брифа + оценкой объёма.
- Не трогать AGENTS.md.

## Анти-цели

- «Всё делегировать субагентам» — плохой бриф заставит исполнителя заново грепать
  репозиторий, и экономия сгорит. Поэтому самодостаточный бриф — условие применения
  схемы, а не пожелание.
- Потеря существующих защит §5 (границы файлов, «дефект — описать, не править», грабли
  BOM/CRLF/--no-incremental/снапшоты) — они сохраняются, теперь адресованы брифу.

## Подходы

1. **Заменить критерий в §5** (выбран): «связность → самодостаточность брифа» +
   координаторская схема. Минимальная правка одного раздела, сохраняет весь остальной
   текст скилла.
2. Добавить новый §5a, оставив старый §5 — отвергнуто: два противоречащих совета в
   одном скилле хуже одного ясного; старый текст станет ловушкой.
3. Вынести исполнение в отдельный скилл — отвергнуто: усложняет навигацию, логика
   неразрывна с нарезкой (§3) и ревью (§6).

## Как (по частям, как утверждено)

- §5 «Реализация»: новая вводная — каждый PR пишет субагент-исполнитель, главный агент —
  координатор; исключение — мелкая связная правка (~полчаса, один заход).
- Самодостаточный бриф — обязательный минимум: цель PR и ссылка на план-файл, worktree,
  границы файлов, осознанные решения и осознанно-не-делаемое, проверки на выходе
  (build/test/format), запрет git-операций. Критерий «решение нельзя передать текстом →
  делаешь сам».
- Существующие требования §5 (границы, проверки, дефект-описать-не-править, грабли)
  сохраняются, адресованы брифу исполнителя.
- §1: синхронизировать формулировку про делегирование разведки (терминология).
- Файл: `.agents/skills/big-task/SKILL.md` (`.claude/skills` — симлинк туда же).
  Распространение — через git в остальные worktree; старые сессии не затрагиваются.

## Что оставлено исполнителю

- Точные формулировки русского текста в духе существующего стиля скилла.
- Решить, оставлять ли абзац про сборку MSB3027/dev/null в текущем месте или переносить
  к граблям (незначительно, влияет только на порядок текста).
