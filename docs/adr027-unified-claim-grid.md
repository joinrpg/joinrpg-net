# ADR027: Грид заявок мастера на основе кабинета капитана (UnifiedGrid)

Статус: предложен.

Проблема:
==

Мастер видит заявки через `ClaimListController` (`src/JoinRpg.Portal/Controllers/ClaimListController.cs`):
около двадцати экшенов, у каждого свой фильтр — по статусу, по группе, по ответственному, по проблемам,
«ждут взноса», «не заполнены поля», «оплатили и отклонены», по типу поселения, по заполненности поля,
по игроку. Все рисуют одну таблицу `_ClaimList.cshtml`. Фильтры не комбинируются: «проблемные в этой
группе» или «обсуждаемые у этого мастера в этой группе» получить нельзя. Строка — заявка, свободных
ролей в списке не видно.

Под каждым списком лежат два представления сразу: EF-`Claim` (`ClaimsRepositoryImpl.GetClaimsImpl`
с `Include` и SQL-предикатами отбора) и доменный `ClaimInfo` (`IClaimInfoRepository.GetClaimInfos`,
[ADR021](adr021-claim-info.md)). Для строки и выгрузки EF нужен только ради автора последнего
комментария (`ClaimListBuilder.GetLastComment`), а для отбора — на страницах по заполненности поля
(`Claim.GetSingleField`). На страницах «проблемные» проблемы (`IClaimProblemValidator.Validate`)
считаются дважды: в фильтре и при построении строки.

Рядом уже есть другой грид — кабинет капитана (`/{projectId}/captain`, `CaptainClaimsGrid`,
`UnifiedGridViewService`, `ItemBuilder`). Он устроен так, как хотелось бы видеть грид мастера:

- стоит на агрегате `CharacterInfo` ([ADR013](adr013-character-info.md)), без EF-сущностей;
- строка — персонаж, его заявки идут строками под ним (rowspan), вакансии видны;
- остров WASM, фильтр по статусу переключается без перезагрузки.

Но он умеет только капитанский скоуп и один фильтр, а проблем и пейджинга у него нет.

Попутно найдено:

- **Фильтр «Архив» капитана не совпадает со своим описанием.** По описанию `UgStatusFilterView.Archive`
  это «удалённые персонажи, отклонённые и отозванные заявки». Код же грузит только удалённых персонажей,
  у которых есть хотя бы одна неактивная заявка. Удалённые без заявок не видны, а отклонённые заявки
  живых персонажей капитан не видит нигде. Так было и до перевода на `CharacterInfo` (#4823): старый
  `CharacterPredicates.ByUgStatus` отбирал так же. Чинится шагом 0 (#5984).
- `UgCharacterForCaptainViewModel.Groups` (после шага 1 — `UgCharacterViewModel.Groups`) всегда пустой (`// TODO` в `ItemBuilder`), а
  `CreateDate`/`CheckInDate` заявки уходят на клиент и не рисуются.
- `ItemBuilder` ставит `IsCapitan = true` в `AccessArguments`. Из-за этого `CanViewCharacterName` там
  всегда истинно, и ветка «имя скрыто» недостижима.
- `CaptainAccessRule.CanApprove` нигде в гриде не используется.

Решение:
==

### 1. Один грид, два скоупа

Грид один — UnifiedGrid. Мастерский и капитанский отличаются **скоупом**. Какой скоуп нужен, решает
страница (`UgScopeView`: мастерский грид или кабинет капитана), а права на него проверяет сервер:

| Кто | Скоуп | Что видно сверх общего |
|---|---|---|
| мастер проекта (`ProjectInfo.HasMasterAccess`) | весь проект | колонка «Проблемы», бейдж непрочитанных, фильтры по группе, ответственному и проблемам, Excel и массовые операции |
| капитан (есть `CaptainAccessRule`) | поддеревья групп из его правил (`GroupTree.GetChildGroupIdsIncludingThis`) | — |
| остальные | пусто | — |

Проблемы видит только мастер: среди них финансовые и мастерские («не ответили», «нет ответственного»),
капитану они ни к чему. Фильтры по группе и ответственному пока тоже только мастерские:
`CharacterGroupSelector` и `MasterSelector` ходят в webapi под `[RequireMaster]`, а для капитана группы
пришлось бы ещё и ограничивать его поддеревьями. Капитанский источник групп — отдельная задача, если
понадобится.

Скоуп задаёт страница, а не права пользователя, потому что человек бывает и мастером, и капитаном. В
кабинете капитана он видит свою команду, а не весь проект. Мастерский скоуп без доступа мастера и
капитанский без правил капитана дают пустой грид.

Контракт `IUnifiedGridClient` (`JoinRpg.Web.Claims/UnifiedGrid`) — один метод вместо `GetForCaptain`:

```csharp
Task<UgPageViewModel> GetGrid(ProjectIdentification projectId, UgScopeView scope, UgFilterView filter, int page);
```

Компонент тоже один. Мастерские части рисуются по nullable-полям в ответе сервера
(`IReadOnlyCollection<ProblemViewModel>? Problems` и `int? UnreadCommentsCount` на заявке, `null` у
капитана), без bool-флагов режима и без двух компонентов.

### 2. Фильтр

`UgFilterView` — record из независимых полей, условия объединяются через «И»:

| Поле | Значения | Где отбирается |
|---|---|---|
| `Status` | см. таблицу ниже | удалён персонаж или нет — SQL (`CharacterStatusSpec`), остальное — в памяти |
| `Group` | группа или пусто (вместе с подгруппами) | SQL (`GetCharacterInfosByGroups`) |
| `Responsible` | мастер или пусто | в памяти, по заявкам |
| `OnlyWithProblems` | `bool` | в памяти, см. ниже |

Статусы — пара правил «какие персонажи» и «какие их заявки»:

| Статус | Персонажи | Заявки в строке |
|---|---|---|
| Активные | живые | активные (`IsActive`) |
| Вакансии | живые, без принятой заявки, не NPC | активные |
| Обсуждаются | живые, без принятой заявки, с активными заявками | активные |
| Приняты | живые, с принятой заявкой | принятая |
| Лист ожидания | живые, с заявками в листе ожидания | `OnHold` |
| Архив | удалённые (в том числе без заявок) и живые с отклонёнными/отозванными | у удалённого — все, у живого — `DeclinedByMaster`/`DeclinedByUser` |
| Все | все, включая удалённых | все |

`OnHold` неактивна (`ClaimStatusExtensions.IsActive`), но в «Архив» живого персонажа не попадает: она
в своём статусе.

Отбор по статусу и ответственному — чистые функции над `CharacterInfo`, их место в
`JoinRpg.DomainTypes`: туда переехали правила над агрегатом по ADR013, а `JoinRpg.Domain` устаревший
(`docs/structure.md`). Сейчас это private-методы `MatchesFilter`/`SelectClaims` в сервисе. Доменная
пара фильтра тоже лежит в DomainTypes, а `UgFilterView` в `Web.Claims` только отображается на неё.

Проблемы считает `IClaimProblemValidator` (`JoinRpg.Domain`), и вызывает его сервис. Валидатору нужен
`ClaimInfo`, то есть профиль игрока (`UserInfo`, на нём стоят `ClaimContactsMissingFilter` и проблемы
полей профиля). Поэтому в мастерском скоупе сервис догружает профили игроков одним
`IUserRepository.GetRequiredUserInfos` и собирает `new ClaimInfo(new ClaimInCharacter(character, claim), userInfo)`.

Проблемы считаются **один раз на заявку**, с порогом `Hint`, как сейчас в колонке. В строку попадают все,
а `OnlyWithProblems` отбирает по `Any(p => p.Severity >= Warning)`, как сейчас в фильтре.

Персонаж попадает в выдачу, если под фильтр подошла хотя бы одна его заявка или он подходит по статусу
и без заявок (вакансия, удалённый в архиве). При фильтре по ответственному или по проблемам персонажи
без подходящих заявок отпадают.

### 3. Пейджинг и сортировка на сервере

Страница считается **по персонажам**, а не по заявкам, чтобы rowspan не рвался на её границе. Размер
страницы фиксированный, 100 персонажей.

Сортировка переезжает на сервер (сейчас она в `CaptainClaimsGrid.razor`) и идёт **по дате обновления**,
как в старом гриде мастера. У персонажа это самая поздняя `UpdateDate` среди показанных заявок, по
убыванию. Персонажи без показанных заявок идут в конце, по имени. Последний ключ — `CharacterId`, чтобы
порядок был детерминированным и страницы не теряли и не дублировали строки. При смене фильтра номер
страницы сбрасывается на первую.

Ответ сервера:

```csharp
record UgPageViewModel(
    IReadOnlyList<UgItemViewModel> Items,   // текущая страница
    int Page,                               // отданная страница: запрошенная, прижатая к диапазону
    int TotalPages,
    int TotalCharacters,
    IReadOnlyCollection<ClaimIdentification> OperationClaimIds,         // весь результат фильтра,
    IReadOnlyCollection<CharacterIdentification> OperationCharacterIds); // см. §5; у капитана пусто.
                                                                         // Оба — с шага 6
```

Пейджинг сокращает ответ и время рендера на клиенте, **но не нагрузку на БД**. Отбор по проблемам и по
ответственному идёт в памяти, поэтому скоуп загружается целиком вместе с профилями игроков — так же, как
сейчас на `/claims/problems` через `GetClaimInfos`. Если это упрётся в БД, следующим шагом будет
SQL-предфильтр (например, по `ResponsibleMasterUserId`), но в этот ADR он не входит.

Пагинация — offset (`page`), а не keyset. Главный выигрыш keyset — индексный `WHERE (ключ) < (курсор)`
без сканирования пропущенных строк, а у нас отбор идёт в памяти по целиком загруженному скоупу, так что
выигрывать нечего. Ключ сортировки (максимум `Last*CommentAt` по заявкам, показанным под фильтр) в SQL
считается тяжело. Стабильности keyset тоже не даёт: новый комментарий меняет сам ключ, и персонаж
уезжает наверх при любом способе. Вдобавок курсор в URL хуже номера страницы для ссылок и редиректов
(§6), и без номеров нельзя перейти на N-ю страницу. К keyset стоит вернуться вместе с SQL-предфильтром,
когда отбор и ключ сортировки уйдут в базу.

### 4. Строка заявки

- **Обновлено.** Дата — `ClaimListBuilder.GetLastCommentTime` по скалярам `Last*CommentAt` агрегата.
  «Кто обновил» выводится из того, какая из меток позже: «игроком» или «мастером». Значения «мной» и
  имени автора больше нет, ради них понадобился бы EF.
- **Непрочитанные комментарии** — бейдж, как в старом гриде, только у мастера. Нужна перегрузка
  `GetUnreadDiscussionsForClaims` по id заявок страницы (сейчас метод считает по статусу всего проекта)
  на общем выражении непрочитанного из [ADR026](adr026-comment-discussion.md) §2.
- **Проблемы** — `ProblemBadge`, только у мастера.

### 5. Страница, URL, экспорт и массовые операции

Мастерский грид — новая Razor Page `/{projectId}/claims` (`Pages/GamePages`, как кабинет капитана
`/{projectId}/captain`). Маршрут свободен: старый `ClaimListController` живёт на
`{ProjectId}/claims/[action]`, где экшен обязателен, так что его страницы становятся «подстраницами»
грида и редиректят в корень с параметрами (§6). На странице остров WASM,
тот же, что у капитана. Фильтр и номер страницы лежат в query string: страница передаёт их острову
параметрами, а остров при смене фильтра переписывает URL. Остров отрисован без Blazor `Router`, поэтому
надо проверить, что `NavigationManager.NavigateTo(…, replace: true)` не вызывает полную перезагрузку.
Если вызывает — переписывать URL через `history.replaceState` (JS interop). URL строятся через локатор
(`IProjectUriLocator`/`ICharacterGroupUriLocator`), реализованный и на сервере, и на клиенте. Имена
параметров и значения enum фиксируются до первого редиректа (§6), потому что 301 браузер кеширует.

**Excel — старым пайплайном.** Колонки не меняются: по их заголовкам разбирает выгрузку мастера DRP
(`JoinRpg.Services.Drp/MasterExports/MasterExportColumns.cs`). На той же странице `?export=xlsx`:
сервер пересчитывает фильтр без пейджинга и передаёт id заявок в существующий
`ClaimListItemViewModelExporter` через `ClaimListBuilder.BuildItemForExport`. Для этого нужны:

- `IClaimsRepository.GetClaims(IReadOnlyCollection<ClaimIdentification>)` с теми же `Include`, что в
  `GetClaimsImpl` (иначе ленивые загрузки);
- сборка выгрузки в сервисе `WebPortal.Managers`, а не в контроллере: `LoadClaimInfos`, `LoadRoomNames` и
  `ExportWithCustomFrontend` сейчас private в `ClaimListController`, и старые экшены переходят на тот же
  сервис. Заголовок файла строится из фильтра.

**Рассылка и печать** (`ListOperationsButtons`) работают по `OperationClaimIds`/`OperationCharacterIds`
всего результата фильтра. В печать попадают только персонажи с показанными заявками, вакансии — нет, как
и сейчас (`ClaimListViewModel.CharacterIds`). Счётчик над списком считает заявки. Капитану коллекции
отдаются пустыми.

### 6. Старые маршруты — редиректами, по одному

Новая страница появляется рядом со старыми. Ссылки в UI переводятся сразу на локатор грида:
`MasterMenu.cshtml`, `Acl/Manage.cshtml`, шапка группы (`DisplayTemplates/CharacterGroupDetailsViewModel.cshtml`),
`GroupEditMenu.razor`, `GroupReport.razor`, `ICharacterGroupUriLocator.GetClaimListUri`/`GetDiscussingClaimListUri`
в обеих реализациях (`UriServiceImpl`, `Blazor.Client/UriLocatorExtensions`), а с ними
`UriLocatorConsistencyTests` и фейки локаторов в тестах. Старый экшен становится 301-редиректом на грид
с параметрами и пробрасывает `export`, потому что на выгрузки бывают закладки. Каждый такой маршрут
добавляется в `SmokeExpectations.ExpectedStatus` как `MovedPermanently`.

| Старый маршрут | Грид |
|---|---|
| `ActiveList`, `Discussing`, `OnHoldList` | Активные / Обсуждаются / Лист ожидания |
| `Problems` | Все + `OnlyWithProblems` (старый брал `ClaimStatusSpec.Any`: проблемы отклонённых заявок и удалённых персонажей, например `BrokenClaimsAndCharacters`, не должны пропасть) |
| `~/roles/{G}/claims`, `DiscussingForGroup` | `Group` = G + Активные / Обсуждаются |
| `for-master/{M}`, `ResponsibleDiscussing`, `ResponsibleOnHold` | `Responsible` = M + Активные / Обсуждаются / Лист ожидания |
| `problems-for-master/{M}` | `Responsible` = M + Все + `OnlyWithProblems` |

До своей очереди остаются на старой странице: `DeclinedList` (это «Архив + Лист ожидания» сразу, одним
статусом не выражается), `ForPlayer`, `by-roomtype`/`without-roomtype`, `WaitingForFee`, `PaidDeclined`,
`SomeFieldsToFill`, `ByAssignedField`/`ByUnAssignedField`. Когда последний из них переедет или будет признан
ненужным, `_ClaimList.cshtml` и `ClaimListBuilder.BuildItem` удаляются.

### 7. Изменения поведения для мастера

- Строка — персонаж, а не заявка. «Активные» показывают и свободные роли без заявок. Поэтому число в
  ссылке из отчёта группы (`GroupReport`, там считаются заявки) может не совпасть с числом строк грида.
- «Кто обновил» показывает «игроком / мастером», без «мной» и имени (§4).
- Над списком группы (`~/roles/{G}/claims`) больше нет шапки группы с навигацией
  (`GroupNavigationPage.ClaimsActive`). Ссылка из меню группы ведёт в грид с фильтром.

План миграции:
==

Каждый шаг — отдельный PR, который собирается и проходит тесты сам.

0. **Фикс «Архива» капитана** (#5984) — по таблице §2. От остального не зависит.
1. **Доменный фильтр и `GetGrid`.** Правила статусов из §2 — в DomainTypes с тестами. Затем `UgFilterView`,
   скоуп «мастер/капитан», кабинет капитана переходит на `GetGrid`. Поведение капитана не меняется.
   Попутно проверить, что смоук (`SmokeParameterValues`/`SmokeUrlBuilder`) умеет заполнять составной
   `[FromQuery]` фильтр.
2. **Пейджинг и сортировка** на сервере, `UgPageViewModel`. Компонент пейджера в
   `JoinRpg.Common.WebComponents` — это NuGet-пакет, поэтому нужны bUnit-тест, CHANGELOG, `PublicAPI`
   (`scripts/Update-PublicApi.ps1`) и при необходимости README.
3. **Проблемы.** Профили игроков, колонка и фильтр, только в мастерском скоупе.
4. **Группа и ответственный** — фильтры в мастерском скоупе, заполненные `Groups` в строке.
5. **Статусы** «Приняты», «Лист ожидания», «Все»; фильтр в query string.
6. **Мастерская страница.** `/{projectId}/claims`, бейдж непрочитанных (перегрузка по id), Excel
   (`GetClaims` по id, сервис выгрузки) и `ListOperationsButtons` по всему результату фильтра.
7. **Ссылки и редиректы** из §6 — по PR на группу маршрутов.
8. **Снос легаси**, когда не останется вызывающих.

Не делаем:
==

- **Колонки Excel не меняем** и экспорт «как в гриде» не делаем (§5).
- **Настраиваемые колонки и сортировку пользователем.** Сортировка фиксированная, на сервере.
- **Фильтры по финансам, полям, поселению, игроку, непрочитанному и поиск по имени.** Для них остаются
  старые страницы (§6).
- **Детальный фильтр по проблемам** (тип, серьёзность) — только «есть проблемы».
- **Фильтры по группе и ответственному для капитана** (§1).
- **SQL-предфильтр под проблемы и ответственного** — пока не упрёмся (§3).
- **Новые поля в DataModel** не нужны.
