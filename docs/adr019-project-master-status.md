# ADR019: Статус, публичность и профиль мастера проекта

Статус: предложен. Issue #5226.

Проблема:
==

Мастер проекта — это строка `ProjectAcl` (`src/JoinRpg.DataModel/ProjectAcl.cs`): пользователь,
проект и 11 булевых прав. В домене ей соответствует `ProjectMasterInfo` внутри
`ProjectInfo.Masters`. Больше о мастере ничего не известно, и из этого растут четыре проблемы.

1. **Удаление мастера стирает историю.** `ProjectAccessService.RemoveAccess` делает
   `RemovePermanently(acl)` — физическое удаление строки. После этого факт «этот человек был мастером
   проекта» остаётся только косвенно: в `Comment.IsCommentByPlayer = false` у его комментариев.
   На проде таких людей без записи `ProjectAcl` — 150 пар «проект — пользователь» в 103 проектах.

2. **Мастера нельзя скрыть от игроков.** Главная страница проекта (`GameController.Details`,
   `[AllowAnonymous]`) показывает анониму всех мастеров (`ProjectHomePanel.razor`), и так же — веб-API
   `ProjectInfoController`. Мастер, который помогает проекту, но не хочет светиться (техподдержка,
   бухгалтер, админ сайта, получивший доступ через `force-admin-access`), этого не может.

3. **У мастера нет роли.** Игроку не видно, кто главный мастер, а кто отвечает за боёвку или
   экономику, — только список имён в порядке, в каком их вернул EF.

4. **Страница мастеров закрыта для игроков.** `AclController` стоит под `[RequireMasterOrAdmin]`, а
   игроку она нужна больше всех: понять, кому писать.

### Дефекты рядом

- **Передача владения при уходе владельца может уйти на него самого.**
  `ProjectAccessService.cs:103`: если владелец удаляет себя, `IsOwner` получает
  `ProjectAcls.OrderBy(a => a.UserId).First()` — а это может оказаться удаляемая запись, если у
  владельца наименьший `UserId`. Проект остаётся без владельца. Self-contained фикс, PR 0 плана.
- **`MastersListViewModel` падает для админа, который не мастер.** `Masters.Single(acl => acl.UserId
  == currentUser.UserId)` при `[RequireMasterOrAdmin]`. Чинится сам собой в PR 7: страница становится
  публичной, и `Single` по текущему пользователю там больше невозможен.

Решение:
==

### 1. Статус вместо удаления

В `ProjectAcl` появляется статус:

```csharp
public enum ProjectAclStatus
{
    Active = 0,
    Removed = 1,
}
```

Колонка `int not null default 0` — все существующие строки становятся `Active`, поведение не
меняется. Задел на будущие статусы (`Invited`) — сам enum; в этом ADR их нет.

**`RemoveAccess` перестаёт удалять строку.** Вместо `RemovePermanently` он:

- ставит `Status = Removed`;
- **сбрасывает все права и `IsOwner` в `false`** — защита в глубину: проверка, которая забыла про
  статус, но спрашивает конкретное право, всё равно откажет. Голой проверки «вообще мастер»
  (`Permission.None` → `acl => true`) это не спасает — поэтому §2;
- всё остальное делает, как сейчас: переназначает ответственного по заявкам и группам, передаёт
  владение, снимает подписки.

`Role`, `Description`, `IsPublic` (§3–§4) при удалении сохраняются: если мастера вернут, описание и
публичность вернутся вместе с ним, а роль задаст заново форма добавления.

**Повторная выдача доступа реактивирует строку.** `GrantAccess` уже ищет существующую запись
(`SingleOrDefault`) и делает upsert; он начинает искать среди записей **любого** статуса и ставить
`Active`. Так на пару (проект, пользователь) всегда не больше одной строки, и это фиксируется
**уникальным индексом `(ProjectId, UserId)`** — на проде дублей нет (проверено 2026-10-04, 7148 строк).
Сегодня уникальность держится только кодом (`Single`/`SingleOrDefault` у читателей).

**Токен мастера.** `ProjectAcl.Token` открывает анонимную финансовую сводку
(`FinancesController.SummaryByMaster`). При физическом удалении токен умирал вместе со строкой; при
мягком — продолжил бы работать. Поиск по токену начинает требовать `Active`.

### 2. Доступ — только у активных

Инвариант: **запись не в статусе `Active` не даёт никакого доступа и не делает человека мастером ни
для одной проверки.** Проверок — около двухсот, и правило нельзя размазывать по ним. Оно держится в
трёх точках, по числу путей, которыми сегодня читаются ACL:

1. **Домен (`ProjectInfo`) — большинство проверок.** `ProjectInfo.Masters` содержит **только
   активных** мастеров. Тогда `HasMasterAccess`, `RequestMasterAccess`, `GetMasterById`,
   `GetDefaultResponsibleMaster`, рассылки по `Masters`, селекторы ответственного — всё корректно без
   единой правки. Бывшие мастера лежат отдельной коллекцией `ProjectInfo.FormerMasters`, в которую
   никакая проверка доступа не смотрит. `ProjectMasterInfo` получает поле `Status` — чтобы элемент
   был самоописывающим, но фильтровать по нему на местах не нужно.

   Почему не «все в `Masters`, фильтр у потребителей»: тридцать с лишним потребителей `Masters`, и
   каждый, кто забудет фильтр, раздаст доступ бывшему мастеру. Разделение коллекций делает
   безопасный вариант умолчанием.

2. **EF-сущности (`entity.Project.ProjectAcls`, `user.ProjectAcls`)** — legacy-путь через
   `[Obsolete]` расширения (`ProjectEntityExtensions`, `ClaimAcccessExtensions`, `CommentExtensions`,
   `SubscribeExtensions`, `FinanceOperationsImpl`, view-модели форума и финансов и т. д.). Глобального
   фильтра в EF6 нет, поэтому:
   - в `ProjectAcl` появляется `IsActive => Status == ProjectAclStatus.Active`;
   - `PermissionExtensions.GetPermssionExpression` для **каждого** права, включая `None`, требует
     `IsActive` — через неё идёт большая часть entity-проверок;
   - оставшиеся прямые обходы `ProjectAcls` перечисляются через `find_references` на навигации
     `Project.ProjectAcls` и `User.ProjectAcls` и получают фильтр. Список — в описании PR 2.

3. **SQL-предикаты** — `ProjectPredicates.MasterAccess` и ветки `BySpecification` (`MasterAccess`,
   `MasterOrActiveClaim`, `ForCloning`, `MasterGrantAccess`, `MasterManageClaimsAccess`),
   `ProjectRepository.GetProjectPersonalizedListInternal`, `UserInfoRepository` (`ActiveProjects` /
   `AllProjects`). Это «мои проекты», меню, MCP, consent-страница OAuth. Фильтр — в самих предикатах.

**Шов совместимости.** Пока `RemoveAccess` удаляет физически, строк `Removed` в базе нет, и все
фильтры выше — no-op. Значит читателей можно переводить независимыми PR в любом порядке, а писателя
(`RemoveAccess` → мягкое удаление, джоба §6) переключать последним, когда все читатели готовы.

### 3. Публичность мастера

`ProjectAcl.IsPublic`, `bool not null default 1` — все текущие мастера остаются видны, как сейчас.
Новый мастер (создатель проекта, добавленный мастер) — тоже публичен по умолчанию.

Попадает в `ProjectMasterInfo.IsPublic` — потому что нужен главной странице проекта, которая и так
читает `ProjectInfo`.

Правило одно: **непубличного мастера видят только мастера проекта.** Для всех остальных его нет:

- панель «Мастера» на главной странице проекта;
- веб-API `ProjectInfoController` / `ProjectInfoViewService`;
- публичная страница мастеров (§7);
- панель «нет доступа» (`ErrorNoAccessToProjectViewModel`) — она показывает мастеров с
  `CanGrantRights` тому, у кого доступа нет, то есть немастеру. Если ни одного публичного мастера с
  `CanGrantRights` нет, панель не показывает никого.

Публичность — не про доступ: на права, рассылки, ответственного мастера она не влияет. Игрок, у
которого непубличный мастер ответственный за заявку, видит его в заявке, как и сейчас.

### 4. Роль и описание мастера — вне `ProjectInfo`

Два новых поля `ProjectAcl`:

- `Role` — `nvarchar(100) not null`, **обязательный** свободный текст: «Главный мастер», «Мастер по
  боёвке». Не enum: набор ролей у каждой игры свой, логики на роли нет. В домене — типизированная
  непустая строка `MasterRoleTitle` по [ADR007](adr007-string-value.md), чтобы пустую роль нельзя
  было собрать в принципе, а не проверять на местах.
- `Description` — `MarkdownDbValue`, длинный рассказ о том, за что мастер отвечает и по каким
  вопросам ему писать.

**В `ProjectInfo` они не попадают** (требование issue и правило
[project-entities.md](project-entities.md): редко нужное и объёмное в слепок не кладём). Нужны они
только странице мастеров, поэтому у неё свой загрузчик:

```csharp
public record ProjectMasterProfile(UserIdentification UserId, MasterRoleTitle Role, MarkdownString? Description);

public interface IProjectMasterProfileRepository
{
    Task<IReadOnlyCollection<ProjectMasterProfile>> GetMasterProfiles(ProjectIdentification projectId);
}
```

Отдаёт профили только активных мастеров. Имя, статус, публичность и порядок страница берёт из
`ProjectInfo` и склеивает с профилями по `UserId`.

**Значения по путям создания `ProjectAcl`.** Роль обязательна, поэтому у каждого пути она своя и
задаётся явно — умолчания на уровне `ProjectAcl` нет.

| Путь | `Role` | `Description` | `IsPublic` |
|---|---|---|---|
| Создание проекта, тип `Larp`, `EmptyProject` | «Главный мастер» | пусто | да |
| Создание проекта, тип `Convention`, `ConventionProgram` | «Главный организатор» | пусто | да |
| Клонирование проекта (`CopyFromAnother`) | «Главный мастер» — ACL не копируются, создатель становится владельцем | пусто | да |
| Добавление мастера (`GrantAccess`, форма `Acl/Add`) | **из формы, поле обязательное**, предзаполнено «Мастер» | пусто | да |
| Повторная выдача (`GrantAccess` по `Removed`-строке) | из формы — перезаписывает прежнюю | сохраняется | сохраняется |
| `force-admin-access` (`GrantFullAccess`) | «Техподдержка joinrpg.ru» | пусто | **нет** — админ сайта, зашедший помочь, не член команды |
| Бэкфилл (§6) | «Мастер» | пусто | да (неважно: строка `Removed`) |
| Миграция существующих строк | «Мастер» всем, включая владельца | пусто | да |

Тип проекта известен только в `CreateProjectService.CreateProject` (`ProjectTypeDto`), а запись ACL
создаёт `ProjectService.AddProject` через `CreateRootAcl`. Поэтому `AddProject` и `CreateRootAcl`
получают роль параметром, а выбирает её `CreateProjectService`. Существующим строкам миграция ставит
«Мастер» всем без исключений — роли уточнят руками на странице мастеров.

Все эти строки — видимый пользователю текст в сервисном слое (и в SQL миграции), рядом с ними
ставится `TODO[Localize]` (CLAUDE.md).

### 5. Порядок мастеров

Порядок хранится строкой `ProjectDetails.MastersOrdering` и разбирается `VirtualOrderContainer` —
так же, как `FieldsOrdering` и `PlotFoldersOrdering`. `ProjectAcl` уже реализует `IOrderableEntity`
(`Id => ProjectAclId`). Новый мастер без записи в строке встаёт в конец, перестановка — одна запись.

Порядок применяется в `ProjectInfo`: `Masters` отдаётся уже отсортированным (как поля через
`VirtualOrderContainerFacade.CreateLazy`). Главная страница проекта и страница мастеров показывают
мастеров в одном и том же порядке. Строка короткая, слепок не раздувает. Для этого
`ProjectMasterInfo` получает идентификатор, пригодный для `IOrderableEntity` (`ProjectAclId`).

### 6. Бэкфилл бывших мастеров — ежедневная джоба

`FormerMastersBackfillJob` (`JoinRpg.Services.Impl`, по [ADR002](adr002-dailyjobs.md)) находит пары
(проект, пользователь) по следам мастерства, у которых нет строки `ProjectAcl` ни в каком статусе, и
создаёт им строку `Removed` без прав. Следы, пережившие физическое удаление ACL:

1. комментарии **в заявках** (не форума: запрос начинается от `Claims`) с `IsCommentByPlayer = false`;
2. своя касса — тип оплаты мастера (`PaymentTypes.UserId`), кроме онлайн-оплат: они оформлены на
   служебного пользователя `payments@joinrpg.ru`. Финансовые операции ссылаются на тип оплаты, так что
   принимавший деньги мастер находится через него;
3. переводы между мастерами (`MoneyTransfers`): отправитель, получатель, создавший и менявший.

На проде (2026-10-04) это 162 пары в 109 проектах; деньги добавляют 12 пар к 150 из комментариев.

- **Критерий по комментариям — `IsCommentByPlayer = false`.** Флаг пишется при создании комментария
  как `!ProjectInfo.HasMasterAccess(автор)` (`CommentHelper.cs:96`), то есть это ровно «в момент
  написания был мастером». Сравнение `AuthorUserId <> Claim.PlayerUserId` хуже: оно записало бы в
  мастера игрока, который писал в чужую заявку как капитан или через общий доступ. Из 150 пар 26 —
  когда автор сам игрок заявки; по флагу он в тот момент был мастером, такие пары берём.
- **Запись — через `IProjectAccessService`**, новым методом `RegisterFormerMasters(projectId,
  userIds)` поверх `ChangeProjectProperties`: `Permission.CanGrantRights`,
  `ProjectActiveRequirement.AllowInactive` (почти все такие проекты в архиве). Джоба работает под
  роботом-админом, admin-bypass проверки прав срабатывает сам (ADR009). Одна операция — один проект.
- **Идемпотентна**: повторный прогон не находит пар без ACL. Падение посередине оставляет часть
  проектов обработанными, следующий прогон доделывает.
- **Временная.** После того как `RemoveAccess` перешёл на мягкое удаление, новых пар не появляется.
  Когда джоба отработала на проде (проверяется по логам и повторным запросом), она удаляется
  отдельным PR — последним в плане.

Почему джоба, а не SQL в EF-миграции (так делались все прошлые бэкфиллы): вставка идёт через
доменный сервис с логированием каждой операции, а не мимо него; при объёме в 150 строк разница в
стоимости несущественна.

### 7. Страница мастеров — для всех

Маршрут остаётся `{projectId}/masters`. Страница открыта всем, включая анонимов, — как главная
страница проекта, которая уже показывает анониму мастеров.

- **Публичная часть** — ~~read-only Blazor-остров по [view-pages-guide.md](view-pages-guide.md)~~
  статический Razor-компонент `ProjectMastersPanel` (`render-mode="Static"`, как `ProjectHomePanel`
  на главной проекта): список только для чтения, интерактивности нет, поэтому WebAPI и HTTP-клиент
  острову не нужны. Лежит в игроцком проекте `JoinRpg.Web.Games` (не в `ProjectMasterTools`). Для
  каждого активного мастера в порядке §5: имя (`UserLink`), роль, описание. Немастер видит только
  публичных; мастер проекта — всех, непубличные помечены.
- **Мастерская часть** — то, что есть сейчас: права, счётчики заявок, правила ответственного,
  подписки, кнопки управления. Показывается только мастерам проекта (и админу), видимые ей данные
  (email, права) немастеру в модель не попадают вовсе — фильтр в билдере, а не в разметке.
- **Редактирование** роли, описания, публичности — в существующей форме `Acl/Edit`; порядок —
  кнопками «выше / ниже» в мастерской части. Права:
  - свой профиль (роль, описание, публичность) мастер правит сам — `Permission.None`;
  - чужой профиль и порядок — `Permission.CanGrantRights`;
  - всё через `ChangeProjectProperties`, `ProjectActiveRequirement.AllowInactive`: страница мастеров
    архивной игры — её «титры», их правят и после игры.
- Ссылка «Мастера» появляется в `PlayerMenu.cshtml`.

Других ограничений доступа к проекту для немастеров в коде нет: `IsPublicProject` управляет только
попаданием в списки, а не доступом к страницам, глобального «скрыть проект» нет. Поэтому «с учётом
всех ограничений доступа» сводится к §3: немастер не видит непубличных мастеров и мастерских данных.

### 8. Что не делаем

- **Статусы кроме `Active`/`Removed`** (`Invited` и т. п.) — вне скоупа issue.
- **Показ бывших мастеров** где-либо в UI (на странице мастеров, в профиле пользователя «был мастером
  в…»). Решено пока нигде не показывать: бэкфилл и мягкое удаление только сохраняют факт, чтобы
  показ можно было добавить позже без потери истории.
- **Перевод legacy-проверок с EF-сущностей на `ProjectInfo`.** Они получают фильтр по статусу (§2),
  но не переписываются: это отдельная, давно идущая миграция.
- **Уведомление мастеру о снятии доступа** — сейчас его нет, и мягкое удаление этого не меняет.

### 9. Альтернативы

- **Отдельная таблица бывших мастеров** вместо статуса. Отвергнуто: повторная выдача доступа
  превращается в перенос строки между таблицами с потерей профиля, а будущий `Invited` потребует ещё
  одну таблицу.
- **`Masters` со всеми статусами и фильтр у потребителей.** Отвергнуто в §2: небезопасное умолчание.
- **`Ordering` int-колонкой в `ProjectAcl`.** Отвергнуто: перестановка правит несколько строк, новому
  мастеру нужно вычислять `max + 1`; у проекта уже есть устоявшийся механизм порядка строкой.
- **Роль enum-справочником.** Отвергнуто: роли у игр разные, логики на них нет.
