# P5 (ADR015): дрейф боевой схемы относительно наката EF6-миграций

Исследование к [ADR015](adr015-efcore-migration.md), раздел
«P5. Сверка боевой схемы со свежесобранной базой». Продолжение спайка
[spike-efcore-parity-findings.md](spike-efcore-parity-findings.md), в котором
эталоном считалась база, собранная накатом миграций.

**Ветка:** `spike-schema-drift` (от `upstream/master`). Ничего не меняет в коде.
**Дата:** 26.09.2026.

## Вопрос

Спайк P3 неявно считал, что «схема, собранная накатом EF6-миграций на пустую
базу» = «боевая схема». На примере `Claims.ResponsibleMasterUserId` это
допущение опровергнуто. Здесь проверяется, насколько далеко зашёл дрейф:
полный список расхождений между **продом** и **свежесобранной базой**, плюс
третья точка отсчёта — **снапшот модели EF6** из `.resx` последней миграции.

## Методика

Три эталона, снятые одним и тем же инструментом:

**А — прод.** Схема снята через скилл `prod-db-readonly`: `sqlcmd`, логин
`claude_joinrpg_readonly` (роль `db_datareader`), хост и пароль из переменных
окружения. Читались только каталоги `sys.*`: `tables`, `columns`, `types`,
`computed_columns`, `key_constraints`, `foreign_keys`, `foreign_key_columns`,
`indexes`, `index_columns`, `default_constraints`, `check_constraints`,
`triggers`, `identity_columns`, `extended_properties`, `objects`, `databases`.
**Ни одной строки данных прочитано не было.**

**Б — свежая база.** Локальный SQL Server из `docker compose` (тот же образ и
та же серверная коллация `Cyrillic_General_CI_AS`, что на проде), пустая база,
накат настоящих EF6-миграций: `dotnet run --project src/Joinrpg.Dal.Migrate`
с `ConnectionStrings__DefaultConnection`, указывающей на неё.

**В — снапшот модели EF6.** Из `.resx` последней миграции
(`202609060939494_DefaultProjectRolesList.resx`) распакован base64+gzip блок
`Target`, из него взята SSDL-часть (store-модель): таблицы, колонки, типы,
nullability, PK, аннотации индексов `customannotation:Index`, ассоциации
с `OnDelete`.

Снятое нормализуется в текстовые строки вида
`COLUMN|dbo.Claims|ResponsibleMasterUserId|int|NOT NULL|ident=0|...`
и сравнивается построчно (`Compare-Object`). Объём: **45 таблиц, 395 колонок,
110 внешних ключей, 150/157 индексов, 73 DEFAULT-констрейнта, 45 PK.**

### Что не удалось проверить (ограничения)

- **Тела DEFAULT-констрейнтов на проде замаскированы.** Под `db_datareader`
  `sys.default_constraints.definition` возвращает `NULL` — видны только имена.
  Сверить удалось только **состав** (таблица + колонка): он совпал полностью,
  73 против 73. Совпадают ли сами значения по умолчанию — **не проверено**.
  Заведомо не совпадают два дефолта с зашитой датой генерации миграции
  (`Projects.CharacterTreeModifiedAt`, `UserAuthDetails.RegisterDate`).
- **Имена DEFAULT-констрейнтов не сравнивались по существу**: EF6 создаёт их
  безымянными, SQL Server даёт автоимена с хеш-суффиксом
  (`DF__Accommoda__IsGro__6E01572D`), которые различны в каждой базе
  по построению. Это не дрейф.
- **Данные не проверялись вообще.** Утверждения вида «NULL-ов в колонке нет»
  в отчёте не делаются; для выравнивающей миграции это придётся проверить
  отдельно (одиночным `COUNT(*)`).
- **Статистика, фрагментация, партиционирование, права, файловые группы**
  не сравнивались — к схеме в смысле EF отношения не имеют.
- Триггеров, CHECK-констрейнтов, вычисляемых колонок, представлений,
  процедур, функций и extended properties **нет ни в одной из баз** — сверять
  было нечего.

## Главный результат

Гипотеза о множественных ручных правках **подтверждается, но масштаб
оказался умеренным**. Дрейф структуры — **10 объектов** (одна колонка
и девять индексов), все объясняются двумя эпизодами ручной работы на проде.
Дополнительно найдены **два расхождения уровня самой базы данных**, которые
спайк P3 не искал и которые важнее для ADR, чем сам список индексов.

Отдельно и крупнее: **24 расхождения между снапшотом EF6 и реальностью обеих
баз** — то есть EF6-скаффолдер уже сейчас считает выполненной работу, которая
не сделана ни на проде, ни на свежей базе.

| Категория | Объектов |
|---|---|
| Прод ≠ свежая база (структура) | **10** |
| Прод ≠ свежая база (уровень БД) | **2** |
| Снапшот EF6 ≠ обе базы | **24** |
| Косметика (не дрейф): имена DEFAULT, дыры в `column_id` | — |

## Разбивка по характеру

### 1. Ручные правки прода в обход миграций — 10 объектов, два эпизода

**Эпизод «ResponsibleMasterUserId» (2021 → неизвестно когда).** Колонка
переведена в NOT NULL руками, при этом снесён индекс
`IX_ResponsibleMasterUserId` — он же был препятствием для `ALTER COLUMN`.
Индекс не восстановлен: на проде **внешний ключ без поддерживающего индекса**
(`Claims` — крупная таблица), это не только расхождение схемы, но и
потенциальная деградация при удалении/обновлении пользователей и при
`JOIN` по ответственному мастеру. Из того же эпизода косвенно видно, что
на `Claims` существовали и были удалены рукотворные покрывающие индексы
`Claim_Cover_index` и `nci_wi_Claims_…` (они упомянуты в закомментированном
коде миграции, но на проде их нет).

**Эпизод «чистка индексов + тюнинг».** Семь индексов, дублирующих кластерный
PK один в один, удалены как бесполезные — правка разумная, но нигде не
зафиксированная. В обратную сторону добавлен один покрывающий индекс
`nci_wi_Characters_…` на `Characters(ProjectId) INCLUDE (…10 колонок…)`,
которого нет ни в модели, ни в миграциях.

**Отдельно: таблицы прода были перестроены.** В свежей базе `column_id`
содержит дыры от `DropColumn` (например, `Comments`: 1,2,4,6,7,8,9,10,12,13),
на проде нумерация сплошная (1..10). SQL Server никогда не переиспользует
`column_id` при `ALTER TABLE`, значит таблицы прода в какой-то момент были
пересозданы целиком — типичный след переезда через export/import (bacpac),
согласуется с переездом на Yandex Cloud Managed SQL Server. На EF это не
влияет никак, но это объясняет, почему уровень совместимости базы застрял
на 110: он унаследован от исходной базы и не поднимался с тех пор.

### 2. Миграции с закомментированным или отредактированным `Up()`

Просмотрен весь каталог `src/JoinRpg.Dal.Impl/Migrations` — 141 миграция.

| Миграция | Что с ней | Последствие |
|---|---|---|
| `202110241232502_RequireClaimResponsible` | `Up()` **закомментирован целиком** (бэкфилл, снос индексов, `AlterColumn`, пересоздание FK с каскадом). История в git: `a9f3370c4 disable migration` → `53d292ed4 reenable migration` → `07508db91 add cover index` → `c62addbda Disable all migration`, всё 30.11.2021 | `.resx` утверждает NOT NULL; свежая база получает NULL; прод выровнен руками. **Единственный источник дрейфа колонок** |
| `202607151732073_SetkaTree` | `Up()` переписан руками (`RenameColumn` + `AlterColumn` вместо сгенерированных `AddColumn`+`DropColumn`, чтобы сохранить данные) | Правка корректная, дрейфа не породила — прод и свежая база совпадают |
| `201604171516480_SelectiveFields`, `201702121018582_Forums`, `201703222039312_RepairForumThreads`, `201801270954367_Accommodation` | в `Up()` вручную дописан `cascadeDelete: false` | 9 из 20 FK, где снапшот обещает каскад, а в базе его нет |

Автоматический признак «закомментированная DDL-операция в `Up()`» даёт ровно
два файла, и опасен из них один. Остальной дрейф пришёл не из миграций.

### 3. Расхождения снапшота с реальностью — 24 объекта

Разобраны в таблице В. Общая механика одна: **снапшот `.resx` скаффолдится
из текущей модели, а не из того, что реально сделал `Up()`.** Как только
`Up()` отредактирован руками (или закомментирован), снапшот начинает врать,
и с этого момента EF6-скаффолдер считает работу выполненной — расхождение
замораживается навсегда. Из 24 позиций скаффолдер не сгенерирует **ни одной**
исправляющей операции.

Дополнительный вывод: инструмент проверки `dotnet ef migrations
has-pending-model-changes` (и его EF6-аналог «пустая scaffolded-миграция»)
в этой ситуации бесполезны по построению — они сравнивают модель со
снапшотом, а врут оба согласованно.

## План выравнивающей миграции

Цель — привести **свежую базу** к проду (и заодно зафиксировать в модели то,
что на проде уже есть), чтобы гарантия «накат миграций = боевая схема» стала
настоящей. Это отдельный PR на EF6, до начала переключения ORM.

### Шаг 0. Проверка данных (до написания миграции)

На проде — `COUNT(*)` по трём условиям (одиночные запросы, без выгрузки):
`Claims.ResponsibleMasterUserId IS NULL` (должно быть 0, колонка уже NOT NULL —
проверка формальная), `ProjectFieldDropdownValues.PlayerSelectable IS NULL`,
`AccommodationInvites.IsGroupInvite` — используется ли где-то в коде.

### Шаг 1. Колонка `Claims.ResponsibleMasterUserId` — доделать 2021 год

Порядок операций жёсткий и именно на нём умерла миграция 2021 года:

1. `UPDATE` бэкфилл NULL-ов (на свежей базе строк нет, на проде — уже сделано,
   операция идемпотентна).
2. `DROP INDEX IF EXISTS` для всех индексов, где колонка участвует, включая
   рукотворные покрывающие (`Claim_Cover_index`, `nci_wi_Claims_…`) — **именно
   они блокируют `ALTER COLUMN`**, и именно на этом всё встало в 2021.
   Обязательно `IF EXISTS`: на проде их уже нет, на свежей базе не было
   никогда, а `DropIndex` из EF6 падает на отсутствующем индексе.
3. `DropForeignKey` → `AlterColumn(nullable: false)` → `AddForeignKey`.
4. `CreateIndex("dbo.Claims", "ResponsibleMasterUserId")`.

**Опасность.** `ALTER COLUMN` на `Claims` — операция с полной перезаписью
таблицы под блокировкой схемы. На проде колонка **уже** NOT NULL, поэтому
SQL Server выполнит `ALTER COLUMN` как no-op метаданных, но снос и
пересоздание индекса — нет. Это самая рискованная часть релиза; делать её
в окно обслуживания. Альтернатива, если риск неприемлем: написать шаг 1
как `Sql(...)` с проверками `IF COL_LENGTH/IF NOT EXISTS`, чтобы на проде
миграция была полностью no-op, а на свежей базе — делала работу.

**Скаффолдер этого не сгенерирует**: снапшот уже считает колонку NOT NULL,
а индекс — существующим. Всё пишется руками.

### Шаг 2. Индексы

- `CreateIndex` для `Claims.IX_ResponsibleMasterUserId` — входит в шаг 1.
- Семь индексов-дублей PK: **решение человека**. Вариант «узаконить удаление»
  (`DropIndex` в миграции + `.HasIndex(...)` не объявлять) честнее и снимает
  семь бесполезных индексов со всех окружений; вариант «восстановить на проде»
  возвращает семь заведомо ненужных структур. Рекомендация — узаконить
  удаление, но для EF6 это значит ещё и снять `IndexAttribute`/
  `IndexAnnotation` с соответствующих свойств, иначе снапшот снова разойдётся.
- `nci_wi_Characters_…`: узаконить отдельной миграцией
  (`Sql("CREATE NONCLUSTERED INDEX …")` с осмысленным именем) либо сознательно
  оставить как инфраструктурный индекс вне модели — но тогда зафиксировать
  это в ADR, чтобы будущая сверка не считала его расхождением.

### Шаг 3. Догнать снапшот (уже в P2)

Эти четыре пункта спайк P3 уже предложил; сверка с продом их подтверждает
и добавляет к ним 20 каскадов:

- `AccommodationInvites.IsGroupInvite` — `DropColumn`.
- `ProjectFieldDropdownValues.PlayerSelectable` — `AlterColumn` на NOT NULL
  (после бэкфилла).
- `UserAuthDetails.AspNetSecurityStamp` — поставить `[Required]` на свойство
  (безопасно, схема не меняется).
- **20 внешних ключей с каскадом.** Здесь нужно решение, а не миграция:
  привести схему к модели (20 × пересоздание FK с `ON DELETE CASCADE` —
  опасно, каскадное удаление пользователя вместе со всеми его заявками,
  комментариями и персонажами) или привести модель к схеме
  (`WillCascadeOnDelete(false)` / `DeleteBehavior.Restrict` — схема не
  меняется вообще). По прецеденту PR #4931 (`Claim.ResponsibleMasterUser`)
  правильный ответ — **приводить модель к схеме**.

### Что скаффолдер сгенерирует сам

Практически ничего. Из всего списка EF6-скаффолдер способен сгенерировать
только последствия изменений модели, которые сделают в шаге 3
(`WillCascadeOnDelete(false)` → `DropForeignKey`/`AddForeignKey`,
удаление свойства → `DropColumn`). Всё, что касается **прода против свежей
базы** (шаги 1 и 2), пишется руками: снапшот и модель уже согласны между
собой и разошлись с реальностью.

### Порядок релиза

1. Проверка данных (шаг 0) — read-only, без релиза.
2. Миграция «индексы» (шаг 2, без `Claims`) — дешёвая, обратимая.
3. Миграция «`Claims.ResponsibleMasterUserId`» (шаг 1) — отдельным релизом,
   в окно обслуживания, с явными `IF EXISTS`.
4. Решение по каскадам + правки модели (шаг 3) — в рамках P2.
5. Повторить сверку из этого документа: диф должен стать пустым.

## Вывод для ADR015

**Гипотеза подтверждается частично.** Ручные правки прода были, их больше
одной, но их не десятки: два эпизода, 10 объектов, оба локализованы и
объяснимы. Дрейфа типов, ключей, FK и таблиц нет вообще — набор миграций
139/139 совпадает, и это важный позитивный результат: механика миграций за
десять лет не разъезжалась, разъезжалось только то, что миграции обошли.

**Оценка P3 меняется умеренно.** Пять расхождений раздела B из спайка P3
нужно перечитать так: `Claims.ResponsibleMasterUserId` на проде **уже**
NOT NULL (то есть EF Core-модель права, а свежая база нет), остальные четыре
одинаковы на обеих базах и остаются в силе. К ним добавляются 20 внешних
ключей с несовпадающим каскадом, которых спайк P3 не увидел, потому что
сравнивал EF Core-прототип с базой, а не снапшот EF6 с базой. Итоговый
контракт P3 формулируется точнее: **сравнивать надо с продом, а не со
свежей базой**, и до выравнивающей миграции эти две вещи не тождественны.

**Оценка P0 меняется существенно — и не из-за схемы.** Главное, что нашла
сверка, это не индексы, а два свойства самой базы:

- прод работает на **уровне совместимости 110**, тестовая база — на 150.
  EF Core генерирует разный SQL в зависимости от уровня совместимости, то
  есть golden-master тесты будут проверять диалект, которого на проде нет;
- прод работает с **RCSI и снапшотной изоляцией**, тестовая база — без них.

Оба параметра тривиально выставляются при создании тестовой базы в
`JoinApplicationFactory` (`ALTER DATABASE … SET COMPATIBILITY_LEVEL = 110`,
`SET READ_COMMITTED_SNAPSHOT ON`) и должны быть выставлены **до** того, как
на P0 начнут записывать эталонные снапшоты — иначе эталон будет снят не с той
среды. Это дешёвая правка с высокой ценой ошибки, и её стоит внести в P0
прямо сейчас. Заодно стоит решить, не пора ли поднять уровень совместимости
на проде — это отдельное решение с отдельным риском по планам запросов,
и делать его в одном окне с переключением ORM точно не нужно.

**Дополнительно в ADR стоит внести:** саму проверку из этого документа
(трёхсторонний диф прод / свежая база / снапшот) — как разовый инструмент
перед переключением и как повод не доверять «зелёному» скаффолдеру: из 34
найденных расхождений EF6-скаффолдер не сгенерирует исправление **ни для
одного**.

## Как воспроизвести

```bash
docker compose up -d
# эталон Б: накат EF6-миграций на пустую базу
cd src/Joinrpg.Dal.Migrate
ConnectionStrings__DefaultConnection="…;Initial Catalog=joinrpg_p5;TrustServerCertificate=True" dotnet run
```

Схема снимается одним SQL-скриптом по `sys.*` (см. раздел «Методика»);
важная деталь — в скрипте нужна **явная коллация** у каждой строковой
колонки каталога (`... COLLATE Latin1_General_CI_AS`), иначе на базе
с `Cyrillic_General_CI_AS` конкатенация и `ORDER BY` падают с Msg 451
(конфликт коллаций между `sysname` и коллацией базы).

Снапшот модели распаковывается из `.resx` последней миграции: узел
`<data name="Target">` — это base64 от gzip от EDMX; SSDL-часть внутри
(`Schema` с namespace `…/ssdl`) и есть store-модель.
