# Большая задача: план → стек PR → мониторинг

Задача «большая», если её нельзя отревьюить одним диффом: трогает несколько слоёв, меняет
механизм, который кто-то вызывает, или заканчивается удалением старого кода. Такую работу ведут
стеком PR, где каждый самостоятельно собирается, проходит тесты и объясним ревьюеру.

Порядок: **разведка → план → нарезка → worktree → реализация → ревью → публикация → мониторинг**.
Пропустить можно нарезку (если работа и правда в один PR), ADR (если архитектура не меняется) и
ревью тривиального PR (см. §6) — остальное нет.

## 1. Сначала разведка, потом план

Перед планом прочитать [docs/README.md](../../../docs/README.md) и найти ADR, который описывает
затрагиваемый контур. Это не формальность: в ADR лежат инварианты, которые диффом не видны —
границы агрегатов, «операция не выходит за границу», «одно сохранение на операцию». Нарушить их
легко, а ревью их поймает поздно.

Навигацию по коду делать через **cwm-roslyn-navigator**, а не грепом. Критично для вопроса «кто
это вызывает»: одноимённая живая перегрузка прячет мёртвую, и греп покажет «вызывают», когда
вызывают другое. `find_references` на каждый тип и член, который собираешься удалить.

Разведку с обходом многих файлов стоит делегировать (`Explore`, `general-purpose`): вернутся
выводы, а дампы файлов не осядут в контексте.

**Главное в разведке — проверить, что целевой код вообще работает.** Бывает, что переносишь то,
чего нет: тело метода закомментировано, флаг всегда false, ветка недостижима. Это полностью меняет
смысл задачи — из «перенести поведение» в «восстановить функциональность», а значит меняет и
тесты (сверять не с чем, снапшот становится единственной фиксацией), и текст описания PR.

## 2. Записать план

**ADR** — если меняется архитектура: появляется новый механизм, переезжает ответственность,
меняется граница слоя. Файл `docs/adrNNN-slug.md` + строка в `docs/README.md`. Если существующий
ADR описывает то, что ты меняешь, — правь его в том же PR, где меняешь код, и вычёркивай
устаревшее (`~~…~~` с пояснением), а не удаляй: читателю нужно понимать, что решение пересмотрено.

**Память проекта** — если архитектура та же, а план просто длинный. Тип `project`, с абсолютными
датами: так план переживёт сжатие контекста и перезапуск сессии.

План показать до кода — он дешевле переделывается. Обязательно назвать, что **не** делаешь и
почему. Если план требует новых полей в `JoinRpg.DataModel` — это вопрос человеку (@leotsarev,
см. CLAUDE.md), а не решение внутри плана.

## 3. Нарезать на стек

Правила нарезки, по приоритету:

1. **Каждый PR собирается и проходит тесты сам.** Если шаг оставляет сборку красной — это не
   граница PR. На практике это значит, что промежуточный PR иногда держит оба механизма сразу
   (новый на одном контуре, старый на остальных) — так и надо, с пометкой в описании.
2. **Self-contained улучшение — отдельным PR на `master`, а не внутри фичи.** Добавил метод в
   нижний слой (`IdExtensions`, расширение домена, кейс в `UriServiceImpl`), поменял сигнатуру
   репозитория, слил два фейка — всё это не зависит от фичи и мерджится сразу, не ожидая её
   ревью. Такой PR читается за минуту, а в фиче эти правки создают шум и тормозят мердж.
   **Искать их на этапе нарезки, не ждать, пока попросит ревьюер.**
3. **Снос легаси — последним PR.** Пока не переведён последний вызывающий, удалять нечего.
4. Порядок внутри стека — от нижнего слоя к верхнему.

Стек лежит ветками в форке (`origin`), а PR идут в `upstream` (см. CLAUDE.md). Базой кросс-форк-PR
может быть только ветка целевого репозитория, поэтому **все PR стека открываются на `master`** и
содержат коммиты предшественников. В каждом описании — пометка:

> **Стек.** Базируется на #NNNN и включает его коммит. Порядок: #A → #B → #C; смотреть стоит
> только верхний коммит.

**Draft — это защита от мерджа не в том порядке, и она обязательна.** Все PR стека открываются на
`master` и содержат коммиты предшественников, поэтому мердж верхнего PR вольёт заодно всё, что под
ним, в обход ревью. Пометка в описании от этого не спасает — кнопка остаётся зелёной.

Поэтому: **готов к мерджу (не draft) только ближайший PR стека**, у которого все предшественники
уже влиты. Остальные — draft, пока их очередь не пришла.

```bash
gh pr create --draft --repo joinrpg/joinrpg-net ...   # все, кроме ближайшего
gh pr ready <N> --repo joinrpg/joinrpg-net            # когда предшественник влит
gh pr ready --undo <N> --repo joinrpg/joinrpg-net     # вернуть в draft
```

Назад в draft — если выяснилось, что PR мерджить нельзя: нашёлся дефект, ждёт ответа на вопрос к
человеку, или решение по нему пересматривается. Лучше снять с мерджа явно, чем надеяться, что
комментарий прочитают раньше, чем нажмут кнопку.

Ближайший незакрытый PR держать **ровно в одном своём коммите**: правки по ревью делать
`git commit --amend --no-edit` (сообщение не меняется, поэтому требование CLAUDE.md про `--edit`
здесь не применяется), а не новыми коммитами. Ревьюер читает дифф, а не историю.

## 4. Работать в отдельном worktree

Большая задача живёт днями и требует десятков `git checkout` между ветками стека при каждом
ребейзе. Делать это в основном рабочем каталоге нельзя: там у человека открыта IDE, может быть
запущено приложение, и ветка под ним будет прыгать. Отдельный worktree решает это целиком —
основной каталог остаётся на `master`.

```bash
git worktree add ../joinrpg-net.<тема> -b <ветка> upstream/master
git worktree list                           # посмотреть, что уже есть
git worktree remove ../joinrpg-net.<тема>   # когда всё влито
```

Имя каталога — сосед основного репозитория, `joinrpg-net.<тема>`: так принято здесь, и по
`worktree list` сразу видно, что к чему. Субагенту можно выдать собственный worktree
(`isolation: "worktree"`) — полезно, когда он делает механический снос, а ты правишь те же
проекты рядом.

**Чего worktree НЕ изолирует.**

- **`.git` общий, значит общий и стек stash.** Никогда не делать `git stash` / `git stash pop`
  без имени: вытащишь работу из другого worktree. Правильно: `git stash push -u -m "<метка>"`,
  сразу запомнить SHA (`git stash list --format='%H %gs'`), восстанавливать `git stash apply
  <sha>` (не `pop`), затем удалить запись, найдя её по метке.
- **`git branch -f` не сработает** по ветке, выгруженной в worktree: `fatal: cannot force update
  the branch 'X' used by worktree at ...`. Если ветка выгружена в **текущем** worktree —
  `git reset --hard <sha>`. Если в другом — идти в него (`git worktree list` покажет, в какой);
  из чужого worktree не поможет и `git checkout`: `fatal: 'X' is already used by worktree at ...`.
- **Ref'ы общие.** `git fetch` в одном worktree обновляет remote-tracking для всех, а параллельная
  сессия в другом worktree может переписать ветку в форке. Не считать себя единственным, кто
  трогает `origin`.
- **Docker-демон общий.** Интеграционные тесты поднимают SQL Server через Testcontainers
  (`SharedSqlServerContainer`) — один контейнер на тестовый процесс, отдельная база на каждую
  фабрику. N одновременных прогонов в разных worktree — это N инстансов SQL Server, конкурирующих
  за память; ровно на этом тесты и сыпались (см. комментарий в `SharedSqlServerContainer.cs`).
  Инстанс из `docker-compose.yml` (PostgreSQL 5432, SQL Server 1433) — для локального запуска
  сайта, тесты его не используют.
- **`artifacts/` своя в каждом worktree** (`UseArtifactsOutput` в `Directory.Build.props`) —
  первая сборка полная, и место на диске расходуется на каждый worktree отдельно.

## 5. Реализация

Делегировать субагентам стоит то, что отделяется по файлам: написание тестов на новый класс,
механический снос, разведка. Не стоит — связную правку в тех же файлах, которую правишь сам.

В промпте субагенту обязательно:

- **границы**: какие файлы можно менять, какие нельзя (перечислить те, что правишь параллельно);
- **проверки на выходе**: `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes
  --severity warn` — все зелёные, результат привести в отчёте;
- **что делать с найденным дефектом**: не править production-код, а описать в отчёте и оставить
  тест `[Fact(Skip = "причина")]`. Иначе субагент «починит» то, чего не понимает;
- **запрет на git-операции**: ни коммитов, ни переключения ветки, ни ребейза.

Грабли, которые стоит повторять в промпте даже при том, что субагент видит CLAUDE.md, — именно их
субагенты нарушают чаще всего:

- `.cs` держать **без BOM**: `.editorconfig` требует `charset = utf-8`, и `dotnet format
  --verify-no-changes` падает на BOM с `(1,1): error CHARSET`. Обычная сборка его не ловит, так
  что обнаруживается это уже на проверке формата. Диагностика: `head -c3 <файл> | od -An -tx1`
  не должно давать `ef bb bf`.
- `.cs` **не править потоковыми утилитами** (`sed`, перезапись через редирект) — ломает CRLF.
- `dotnet build` **инкрементальный скрывает ошибки** в проектах, которые не пересобирал. Перед
  пушем — `--no-incremental`.
- Снапшоты Verify принимать **адресно**: переименовывать именно нужные `.received.txt`, а не
  маской по всем, иначе молча примешь чужой упавший снапшот.

## 6. Ревью каждого PR субагентом

Тривиальный PR (одна строка, переименование, добавленный `[Display]`) — без ревью. Всё остальное —
отдельным субагентом на каждый PR, до пуша.

Промпт ревьюеру строить так:

- **контекст**: что за изменение, из какого состояния в какое, на какие ADR опирается;
- **что осознанно** и дефектом считать не надо: перечислить принятые решения и изменения
  поведения. Без этого ревьюер утонет в «а почему не иначе»;
- **на что смотреть по существу**: корректность (конкретно: кто получатели, что в коллекциях, что
  с пустым входом), ленивые загрузки EF6 и N+1, порядок операций относительно `SaveChanges`,
  мёртвый код после изменения (через `find_references`, не греп), дырки в тестах, язык видимых
  пользователю строк (только русский) и прочие расхождения с CLAUDE.md;
- **чего не надо**: придираться к стилю, именам, объёму комментариев, предлагать переделку
  архитектуры;
- **формат находки**: `файл:строка`, что не так, **конкретный сценарий поломки**, предлагаемая
  правка. Отдельно — список «что проверил и счёл корректным»: он показывает покрытие ревью.

Находки разбирать по одной и решать осознанно. Нормальные исходы: исправить; не исправлять и
написать почему (в описании PR, чтобы человек увидел); вынести в отдельную задачу. Защитный guard
без конкретного сценария не добавлять. Если находка касается общего кода за пределами задачи —
не расширять скоуп молча, а назвать её в описании PR.

Ревью проверять, а не принимать на веру: субагент тоже ошибается в фактах. Любое его утверждение
«этого в репозитории нет» или «так не работает» — перепроверять самому, прежде чем править.

## 7. Выложить стек

Перед каждым пушем — на **вершине стека** (она содержит все коммиты):

```bash
dotnet build Joinrpg.slnx --no-incremental -c Release
dotnet test Joinrpg.slnx -c Release
dotnet format --verify-no-changes --severity warn
```

`-c Release` — потому что CI собирает и гоняет тесты в Release
(`.github/workflows/build_and_publish.yml`), и часть диагностик из `WarningsAsErrors` между
конфигурациями расходится.

```bash
git push -u origin <ветка-1> <ветка-2> <ветка-3>
gh pr create --repo joinrpg/joinrpg-net --base master --head leotsarev:<ветка> \
  --title "..." --body "$(cat <<'BODY'
...
BODY
)"
```

В описании PR, кроме «что сделано»: изменения поведения отдельным разделом (их человек должен
увидеть глазами), осознанно не сделанное с причиной, и вопросы, требующие его решения. Подпись
обязательна — см. CLAUDE.md.

## 8. Мониторинг до мерджа

Поставить цикл: `/loop 1h <что проверять>`. В промпте цикла — номера PR, ветки, путь к worktree,
время прошлого прохода и правила ниже. Когда стек продвинулся (PR влит, появился новый), **снять
цикл и поставить заново с новым промптом**, а не держать устаревший. Заодно, когда предшественник
влит:

- **снять draft со следующего PR** (`gh pr ready <N>`) — он стал ближайшим и теперь его можно
  мерджить. Пока этого не сделать, работа встанет: человек видит draft и не трогает его;
- обновить пометку о стеке в описаниях оставшихся PR (`gh pr edit <N> --repo joinrpg/joinrpg-net
  --body ...`) — после мерджа предшественника она становится ложной.

Обратное тоже часть мониторинга: если по ходу выяснилось, что PR мерджить нельзя — нашёлся дефект,
ждёт решения человека — вернуть его в draft (`gh pr ready --undo <N>`) и сказать почему.

Каждый проход: статус CI, новые комментарии и ревью, отставание и конфликты с `upstream/master`.
Если сказать нечего — не шуметь.

```bash
git fetch upstream -q
gh pr view <N> --repo joinrpg/joinrpg-net --json state,mergeable,mergeStateStatus,reviews
gh pr checks <N> --repo joinrpg/joinrpg-net
```

`mergeStateStatus`: `DIRTY` — конфликт, ребейзить; `BEHIND` — отстал от базы; `BLOCKED` — ждёт
проверок или approve, действий не требует; `CLEAN` — готов. `mergeable: UNKNOWN` бывает, пока
GitHub не посчитал мердж (например, сразу после force-push) — повторить запрос, а не делать вывод.

У PR три независимых канала обсуждения, и `gh pr view --comments` не показывает ни одного из
inline-замечаний:

```bash
gh api "repos/joinrpg/joinrpg-net/pulls/<N>/comments?since=<время прошлого прохода>"  # inline
gh api repos/joinrpg/joinrpg-net/issues/<N>/comments   # верхнеуровневое обсуждение
gh api repos/joinrpg/joinrpg-net/pulls/<N>/reviews     # тела ревью; в --json reviews они пустые
```

Без `since` каждый проход будет докладывать уже разобранное. Ответ в тред — только через API, по
`id` родительского комментария, и с подписью (CLAUDE.md):

```bash
gh api -X POST repos/joinrpg/joinrpg-net/pulls/<N>/comments/<id>/replies \
  -f body="...

🤖 Generated with [Claude Code](https://claude.com/claude-code)"
```

### Ребейз: где ломаются руки

Один раз на worktree: `git config rerere.enabled true`. Один и тот же коммит реплеится в каждой
ветке стека, и без rerere один конфликт придётся разрешать столько раз, сколько в стеке PR.

```bash
git rebase upstream/master                         # нижний PR стека
git rebase --onto <новая база> <РОДИТЕЛЬ> <ветка>  # каждый следующий
git push --force-with-lease origin <ветка>         # обычный --force не использовать
```

- Границей брать **родителя** (`<ветка>^` или прежний tip предыдущего PR). Передашь tip самой
  ветки — реплеить будет нечего, и ветка схлопнется на базу, потеряв коммит. Проверять результат
  через `git log --oneline -3` сразу после каждого ребейза.
- **Не брать границу из `origin/<ветка>`**: после локальных ребейзов без пуша она устарела и даёт
  ложные конфликты. Запоминать фактические tip'ы до начала (`git rev-parse`).
- Влитые коммиты отваливаются сами, и формулировка зависит от формы команды: плоский
  `git rebase upstream/master` пишет `warning: skipped previously applied commit <sha>`, а
  `--onto` — `dropping <sha> … -- patch contents already upstream`. И то и другое — норма, а не
  потеря. После мерджа нижнего PR следующий становится ровно одним коммитом.
- Коммит после ребейза меняет SHA при том же содержимом. Сравнивать содержимое через
  `git patch-id --stable`, а не по SHA.

### `--force-with-lease` сказал `stale info`

Не продавливать `--force` и не бежать делать `fetch --prune`. Сначала выяснить, что на remote:

```bash
git ls-remote origin refs/heads/<ветка>
```

Пустой вывод — **ветки нет**, её удалили при мердже PR. Проверить `gh pr view <N> --json
state,mergedAt`: если смерджен, пушить нечего, работа закончена. Это важный порядок: `git fetch
origin --prune` снимает `stale info`, после чего `--force-with-lease` **создаст ветку заново**
(`* [new branch]`), то есть воскресит ветку уже закрытого PR.

Если `ls-remote` коммит показал — ветку переписал кто-то ещё: сверить содержимое через
`patch-id` и только потом решать, чей вариант оставить.

### Упавший CI и упавшие тесты

Интеграционные тесты поднимают свой SQL Server в docker, и при параллельных прогонах (другой
worktree, другая сессия) контейнеры конкурируют за память — падения бывают ложными. Перед тем как
чинить, **перезапустить упавший проект целиком**: диагноз «флак» ставится повторным прогоном, а не
рассуждением. Если падение воспроизводится — чинить, и проверять не тот же тест в изоляции (он
может проходить один), а весь проект.

### Делегирование в мониторинге

Разбор содержательного ревью — субагенту: он прочитает код вокруг замечания и вернётся с выводом,
а не с дампом файлов. Так же — разбор упавшего CI: дать ссылку на job, попросить найти причину и
**не править** (правки делать самому, чтобы PR остался в одном коммите).

## Когда остановиться

Все PR влиты — сказать об этом, снять цикл и перечислить, что осталось открытым: найденные по пути
дефекты вне скоупа, вопросы, ждущие решения человека. Незакрытые вопросы проговорить явно, а не
оставить в описаниях PR, которые уже никто не откроет.
