# Мониторинг релиза на проде

Работает поверх `gh` (уже авторизован) и `yc` CLI (см. скилл **prod-logs** — конвенции по фильтрам и структуре логов). Здесь — то, что специфично именно для *мониторинга релиза*: что проверять сразу после деплоя, как отличить реальную проблему от известного фона, и как вести длительное наблюдение через `/loop`.

## 1. Найти и дождаться деплоя

```bash
gh run view <run_id> --repo joinrpg/joinrpg-net
gh run watch <run_id> --repo joinrpg/joinrpg-net --exit-status   # блокирующий — запускать в фоне (run_in_background)
```

Список последних прод-деплоев (чтобы понять, какой релиз последний известный, и заметить новый, если он появился без предупреждения):

```bash
gh run list --repo joinrpg/joinrpg-net --workflow=deploy_prod.yml --limit 5
```

Деплой идёт 2-3 минуты — не жди его вхолостую, а сними за это время **baseline «до»**: срез ERROR-логов за час-полтора перед стартом рана (как — см. п. 3). Без baseline после выката нельзя отличить «эта ошибка от релиза» от «она была и вчера тоже», а восстанавливать его задним числом дороже, чем снять сразу.

Деплой раскатывает 3 отдельных Deployment: `joinrpg-portal`, `joinrpg-idportal`, `joinrpg-componentbook`. В логе workflow-рана ищи три строки `deployment "..." successfully rolled out` — это подтверждение, что все три rollout завершились. Иногда в логе встречается побочная ошибка вида `Error: libgssapi_krb5.so.2: cannot open shared object file` из отдельного диагностического шага (проверка "last event for error") — если после неё rollout всё равно идёт и заканчивается тремя `successfully rolled out`, а сам workflow завершился зелёным (`gh run watch` вернул exit 0), это не блокер, просто шум вспомогательного шага.

## 2. Smoke-check сразу после rollout

```bash
for u in https://joinrpg.ru https://id.joinrpg.ru https://components.joinrpg.ru; do
  echo "$u"; curl -s -o /dev/null -w "  code=%{http_code} time=%{time_total}s\n" -L "$u"
done
```

Три сайта — три разных Deployment, проверять все три, не только joinrpg.ru. Первый запрос после rollout идёт 5-7 секунд — это холодный старт, а не деградация; повтори запрос, прежде чем считать это проблемой.

### `/health` — читать тело, а не код ответа

```bash
curl -s https://joinrpg.ru/health | python -m json.tool
```

У Portal есть health check с разбивкой по подсистемам (`main-sqldb`, `DataProtection-db`, `DailyJob-db`, `Notifications-db`, `Project load`, `mcp` — регистрируются в `src/JoinRpg.Portal/Startup.cs`). Это самый дешёвый способ поймать «поднялось, но наполовину».

**Важно: `curl -o /dev/null -w %{http_code}` тут бесполезен** — статус `Degraded` отдаётся с HTTP **200**, так что по коду ответа деградация не видна вообще. Всегда разбирай JSON-тело и смотри на `status` каждой записи в `entries`, а не только на общий `status`.

Что делать с находкой: `Unhealthy` у любой подсистемы — сразу инцидент, докладывать. `Degraded` — разбираться, что именно деградировало, и проверять, было ли так до релиза (health check мог быть добавлен этим же релизом и просто **показать** давно выключенную подсистему — это не регрессия, но повод спросить пользователя, так ли задумано).

### Новые эндпоинты и фичефлаги релиза

Если в релизе есть коммиты, добавляющие эндпоинт, health check или включаемую конфигом подсистему (ищи в `git log` слова `feat:`, названия эндпоинтов), — дёрни эти эндпоинты руками в smoke-check, а не полагайся на то, что «сайт открылся». Типичная находка: фича уехала в прод, но выключена, потому что в прод-конфиге не заданы её секреты, и снаружи это выглядит как обычный 404.

### Логи и HTTP-коды не видят поломок Blazor-островов

Blazor-острова (ADR001) получают данные отдельным JSON-запросом к webapi-эндпоинту. Если остров не смог разобрать ответ, сервер об этом **не узнаёт никогда**: он отдал HTTP 200 и валидный с виду JSON, а исключение случилось в WebAssembly на клиенте. В серверных логах — ни одной записи. Пользователь видит вечное «Идет загрузка...», мониторинг рапортует «тихо». То есть три основных инструмента — логи, HTTP-коды, `/health` — этот класс поломок не видят вообще, и «ноль ошибок в логах» ничего не говорит о работоспособности островов.

Прецедент (хотфикс [#4883](https://github.com/joinrpg/joinrpg-net/pull/4883), коммит `7eb80bb39`): `UserLinkViewModel.Hidden` хранил фиктивный sentinel `new UserIdentification(-1)`; модель уезжала на клиент по JSON, а парсер типизированных id (`IdentificationParseHelper.TryParse1`) неположительные значения не принимает — остров `ProjectRoleGrid` падал на десериализации с `Could not parse 'UserId(-1)' as UserIdentification` и навсегда оставался в «Идет загрузка...». Ломалась **любая** сетка ролей, где есть персонаж с `HidePlayerForCharacter` (репро: `https://joinrpg.ru/1657/roleslist/2010`). Баг приехал на прод с коммитом `aadf0bea2` ([#4855](https://github.com/joinrpg/joinrpg-net/pull/4855)) в релизе 22.09.2026 и прожил там около **двух с половиной суток под активным мониторингом**, не будучи замеченным: ERROR-срезы за все окна после выката были пусты. Это уже **второй** случай невидимой поломки именно сетки ролей — первый описан в [docs/adr011-roles-grid-payload.md](../../../docs/adr011-roles-grid-payload.md) (на крупных проектах сетка не показывалась из-за огромного несжатого payload, тоже без серверных ошибок).

**Проверять содержимое payload, а не только код ответа.** Для сетки ролей (два прецедента — проверять на каждом релизе, который её касается):

```bash
curl -s "https://joinrpg.ru/webapi/project-role-grid/get?projectId=1657&projectRolesListId=2010" -o grid.json -w "%{http_code} size=%{size_download}\n"
```

Проект 1657, сетка 2010 — рабочее репро со скрытыми игроками. Что смотреть в `grid.json`:

- **Sentinel-значения, не переживающие round-trip**: `UserId(-1)` и вообще любые неположительные типизированные id.
- У скрытых игроков (`"viewMode":2`) должно быть `"userId":null` — после фикса там `{"userId":null,"displayName":"скрыто","viewMode":2}`.
- Разумен ли размер payload (`size=`) — ADR011 ровно про его разрастание.

**Признак этого класса багов в коммитах релиза.** Если в релизе есть изменения моделей, которые едут в острова (`JoinRpg.Web.*` ViewModel, особенно с полями типизированных id) — это сигнал проверить round-trip руками. Отдельно опасны sentinel-значения (`-1`, `0`, `default`) в полях типизированных id: они компилируются, проходят серверные тесты на объектах и умирают только на JSON-границе.

**Если пользователь жалуется на «вечную загрузку»** — это почти наверняка остров. Смотреть не логи Portal (их там не будет), а payload соответствующего webapi-эндпоинта.

## 3. Проверка логов на всплеск ошибок

Смотри логи через `yc logging read joinrpg-k8s-logs --resource-types prod ...` (структура полей — в скилле **prod-logs**). Специфика именно для этого сценария:

### Гочи `yc logging read`

- **`--since` в виде относительной длительности (`20m`, `2h`) без явного `--until` может подвиснуть/не завершиться.** Всегда передавай оба параметра как абсолютные RFC-3339 таймстемпы (`--since "2026-08-28T18:29:00Z" --until "2026-08-28T18:55:00Z"`). Текущее время бери через `date -u +%Y-%m-%dT%H:%M:%SZ`.
- Всегда `--format json`, иначе структурированные поля (в т.ч. `exceptions`, `ClassName`) не видны.
- **Текст сообщения лежит в поле `message` на верхнем уровне записи, а НЕ в `json_payload.message`.** В `json_payload` его нет вовсе (виден только `"_dropped_attributes": "1"`), так что `json_payload.message` молча вернёт `None`/пусто — и лог будет выглядеть пустым, хотя он не пустой. Структура записи целиком:

  ```
  uid, resource{type,id}, timestamp, ingested_at, saved_at, level, message, stream_name,
  json_payload{ @timestamp, AppName, Level, SourceContext, MachineName, LoggedUser,
                RequestId, RequestPath, ActionName, TraceId, SpanId,
                exceptions[{ClassName, Message, StackTraceString, Depth}],
                fields{http.request.method, url.path, user_agent.original, ...},
                kubernetes{pod_name, container_name, container_image, labels{pod-template-hash}, ...} }
  ```

  То есть: человекочитаемая строка — `entry["message"]`, семантика ошибки — `entry["json_payload"]["exceptions"][0]`, «с какого пода» — `entry["json_payload"]["kubernetes"]`.
- Точного count-режима нет — считай через `grep -c '"level":'` по сохранённому JSON-файлу.
- `--limit` — это именно лимит записей на возврат; если результат равен лимиту тютелька в тютельку, вероятно упёрлись в кап и объём выше — либо сузь окно, либо подними `--limit`.
- Экспортируй `YC_CLI_INITIALIZATION_SILENCE=true`, чтобы не засорять вывод предупреждением про network connectivity.
- Фильтр по классу ошибок/контексту: `--filter 'json_payload.SourceContext="..."'`, по контейнеру: `--filter 'json_payload.kubernetes.container_name="joinrpg-portal"'`.

### Ноль ошибок сразу после rollout — это ещё не «всё хорошо»

В первые минуты после выката трафика ещё почти нет, и пустой ERROR-срез означает только «не на чем было упасть». Не докладывай «ошибок нет» по окну в пару минут — дождись хотя бы 15-20 минут накопленного трафика, а в вечерние/ночные часы и дольше. Полезный контрольный вопрос: сколько всего записей (любого уровня) попало в окно — если счёт идёт на десятки, окно нерепрезентативно.

Старые поды продолжают писать логи ещё минуту-две после `successfully rolled out` (rolling update завершает долгоиграющие запросы). Записи со старым `pod-template-hash` сразу после деплоя — норма, а не «выкат не доехал»; при разборе находки первым делом смотри хэш пода, чтобы не приписать релизу ошибку со старого кода.

### Как отличить новый деплой от старого в логах

Если видишь в `json_payload.kubernetes.pod_name` / `pod-template-hash` / `container_image` sha, отличающиеся от того, что было в предыдущей проверке, — значит между проверками прошёл ещё один деплой, который тебе не сообщили. Сверься с `gh run list --workflow=deploy_prod.yml` — если там появился новый run, доложи пользователю и обнови контекст "последний известный релиз" в дальнейших итерациях мониторинга.

## 4. Известный фоновый шум — не считать аномалией

За время сопровождения нескольких релизов накопился список повторяющихся, не связанных с текущим релизом паттернов. Проверяй новые находки на совпадение с этим списком, прежде чем докладывать как аномалию:

| Паттерн | Источник | Почему не баг |
|---|---|---|
| `WARN "SQL: Probably lazy load ..."` **только по маршрутам из baseline** | `SourceContext=JoinRpg.Dal.Impl.MyDbContext` | Маршруты, перечисленные в `lazy-loads-baseline.json`, — штатный, зафиксированный долг по [#4670](https://github.com/joinrpg/joinrpg-net/issues/4670) (частично исправлено [#4673](https://github.com/joinrpg/joinrpg-net/pull/4673)). Объём **сильно зависит от трафика** (день/ночь даёт разницу в 10-20 раз) — сравнивай не абсолютные числа, а состав маршрутов. **Маршрут, которого в baseline нет, шумом не является — это находка**, см. раздел ниже. |
| `ERROR "не получилось отправить ... [Telegram] ... помечаем как неуспешное"` | `TelegramSenderJobService` | Единичные ретраи доставки в Telegram — фоновый шум, встречался и до релизов. |
| `AuthenticationFailureException: Correlation failed` | `/signin-vkontakte` | OAuth-cookie-флейк на стороне пользователя (истёк correlation-cookie), не код-регрессия. Может приходить пачками от одного пользователя-ретраера. Логируется как Error, потому что не обрабатывается явно — см. [#4692](https://github.com/joinrpg/joinrpg-net/issues/4692). |
| `System.ArgumentException: There is already a persisted object under the same key` | `Microsoft.AspNetCore.Components.Infrastructure.ComponentStatePersistenceManager` | Известный баг Blazor SSR persistent-state (дублирующийся ключ при prerendering) — встречается регулярно, не связан с релизами. |
| `InvalidOperationException: "Project with Project(N) not found"` | `JoinRpg.Portal.Menu.MainMenuViewComponent` и `ProjectMenuViewComponent`, `ActionName=/Error/Error` | Заход (обычно бота) на URL несуществующего проекта, например `HEAD /2024`. Запрос штатно уходит на страницу ошибки, но ViewComponent'ы меню всё ещё видят projectId в `HttpContext.Items` и идут за метаданными — по **две** записи Error на каждый такой запрос. Не регрессия (видно и на старых подах), но это ровно «ожидаемая бизнес-ситуация на уровне Error» — см. раздел ниже. |
| Доменные исключения `JoinRpg.Domain.*` (`JoinRpgSlotLimitedException`, `OnlyOneApprovedClaimException` и т.п.) | контроллеры заявок | Ожидаемая бизнес-логика (пользователь пытается сделать недопустимое действие), не техническая ошибка. |

Список не исчерпывающий — пополняй его по ходу мониторинга, если нашёл новый повторяющийся неопасный паттерн.

### Ленивые загрузки: шум — только то, что перечислено в baseline

С [#4948](https://github.com/joinrpg/joinrpg-net/pull/4948) (issue [#4914](https://github.com/joinrpg/joinrpg-net/issues/4914)) ленивые загрузки контролируются интеграционными тестами: `src/JoinRpg.IntegrationTest/TestInfrastructure/lazy-loads-baseline.json` — снапшот «шаблон маршрута → разрешённое число ленивых загрузок». **По умолчанию требуется ноль**: нет маршрута в файле — ленивых загрузок на нём быть не должно; в файле только маршруты, где долг по #4670 ещё разрешён, цель — пустой `{}`. Подробности механизма — [docs/lazy-loads-baseline.md](../../../docs/lazy-loads-baseline.md).

Для мониторинга прода отсюда следует: **lazy load — не безусловный шум**. Штатен только маршрут из baseline; любой другой маршрут с lazy-load WARN — находка, на которую нужен issue.

Проверять на **каждой** итерации мониторинга:

1. Взять baseline из выкаченного кода (файл в `master` с момента мержа #4948):

   ```bash
   git fetch upstream master && git show upstream/master:src/JoinRpg.IntegrationTest/TestInfrastructure/lazy-loads-baseline.json
   ```

2. Снять WARN-срез за окно итерации и сохранить в файл — lazy-WARN в проде идут **тысячами в час**, поэтому большой `--limit` и никакого чтения построчно:

   ```bash
   yc logging read joinrpg-k8s-logs --resource-types prod \
     --since "<start>" --until "<end>" --levels WARN --format json --limit 5000 > warn.json
   ```

3. Сгруппировать по (метод, шаблон маршрута) и работать со сводкой, а не со строками. Где что лежит: текст — `message` **на верхнем уровне** записи (`SQL: Probably lazy load from '"[dbo].[Claims]"' during operation ...`), `json_payload.SourceContext` = `JoinRpg.Dal.Impl.MyDbContext`, конкретный URL — `json_payload.RequestPath`, метод — `json_payload.fields."http.request.method"`, таблица — `json_payload.fields.lazyLoadTableName`.

   Ключи baseline — **шаблоны** маршрутов (`GET /{projectId}/plots/EditElement`), а `RequestPath` — конкретный URL с идентификаторами, поэтому перед сравнением URL надо нормализовать: числовые сегменты → параметр, регистр не учитывать. Проще всего свести и то и то к одному виду (числа и `{...}` → `{}`, всё в нижний регистр) и сравнивать уже нормализованные ключи.

4. Маршрут есть в baseline → штатный долг, issue не заводить (но объём/состав всё равно смотреть — см. ниже).
5. Маршрута в baseline нет → **сначала проверить, нет ли уже issue**, и только потом заводить:

   ```bash
   gh issue list --repo joinrpg/joinrpg-net --search "lazy load <фрагмент маршрута>" --state all
   gh search issues --repo joinrpg/joinrpg-net "lazy load" --state open
   ```

   Смотреть и зонтичный [#4670](https://github.com/joinrpg/joinrpg-net/issues/4670) — часть маршрутов может быть уже перечислена там. Дублей не плодить. Issue заводить на маршрут (метод + шаблон + таблицы + счётчик за окно); мелкие редкие маршруты разумно собрать в один issue, а не заводить по штуке на каждый.

### Ожидаемая бизнес-ошибка на уровне Error — сама по себе повод для issue

Если исключение по своей природе — штатная бизнес-ветка (пользователь пытается сделать недопустимое действие, истекла OAuth-cookie и т.п.), но в логах оно всё равно levels `ERROR`, а не `WARN`/`INFO` — **это не повод молча занести его в "известный шум" и забыть**. Само по себе это подозрительно: значит, где-то в коде такое исключение не отловлено явным `case`/`catch` и падает в generic `default`-ветку с `logger.LogError(...)`. Практический эффект — двойной: шумит в error-мониторинге (маскирует реальные проблемы) и обычно показывает пользователю неинформативную "Неожиданная ошибка, обратитесь в техподдержку" вместо понятного сообщения.

- В `JoinMvcControllerBase.AddModelException` (`src/JoinRpg.Portal/Controllers/Common/JoinMvcControllerBase.cs`) есть `switch` по типам доменных исключений с дружелюбными сообщениями без логирования — это правильный паттерн (пример: `JoinRpgSlotLimitedException`, исправлено в [#4667](https://github.com/joinrpg/joinrpg-net/issues/4667)). Если встретил в логах `JoinRpg.Domain.*`-исключение на уровне Error — сверься с этим `switch`, входит ли оно туда; если нет — предложи завести issue по аналогии (пример: [#4691](https://github.com/joinrpg/joinrpg-net/issues/4691) для `OnlyOneApprovedClaimException`).
- Для внешних OAuth-провайдеров (VK, Telegram и т.п., регистрируются в `src/Joinrpg.Web.Identity/IdentityConfigurator.cs`) аналогичная защита — `options.Events.OnRemoteFailure`; если не настроена, `AuthenticationFailureException` долетает до Serilog `RequestLoggingMiddleware`, которая логирует любой 5xx как Error по умолчанию (пример: [#4692](https://github.com/joinrpg/joinrpg-net/issues/4692)).
- Как и с "структурным подпаттерном шума" (см. выше) — **не чини сходу**, предложи issue пользователю с конкретным местом в коде (файл:строка) и прецедентом, если есть.

### Не всякая находка — баг в коде: бывает незавершённый ручной шаг включения

Часть фич уезжает в прод выключенной, потому что для включения нужен ручной шаг вне кода: завести секрет в GitHub Environment, создать OAuth-клиента в админке IdPortal, проставить настройку. Снаружи «выключено» и «сломано» выглядят одинаково (404 на эндпоинте), поэтому прежде чем заводить баг — проверь конфиг:

- Не-секретные переменные окружения: `manifests/prod/.env` и `manifests/dev/.env` (configMap `joinrpg-configmap`).
- Секреты: `manifests/base/joinrpg-main.secret.env` в репозитории **пустой намеренно** — он генерируется в CI из секретов GitHub Environment с префиксом `KUBESECRET_` (`.github/workflows/deploy_reusable_workflow.yml`, шаг `secrets-to-env-action`: префикс срезается, двойное подчёркивание = разделитель секции конфигурации .NET). Отсюда следствие: **секреты подставляются только в момент деплоя**, поэтому добавление секрета требует повторного запуска workflow.
- Ручные шаги в IdPortal (например resource-server-клиент для интроспекции) делаются через админку `/admin/oauthclients`, seed/миграции для них нет.

Проверенный пример (релиз 22.09.2026): `/health` показал `mcp: Degraded — MCP выключен: не заданы Mcp:ClientId/Mcp:ClientSecret`, `/mcp` отдавал 404. Разбор показал: код готов полностью, не хватает только двух значений конфига, потому что resource-server-клиент в IdPortal ещё не заводили. Это не инцидент и не регрессия — доложить пользователю как «фича приехала, но не включена, вот шаги включения».

### "Известный шум" ≠ "не смотреть внутрь"

Категория из таблицы выше защищает только от ложной тревоги "это регрессия текущего релиза". Она не означает, что шум можно после этого игнорировать целиком:

- **Следи за изменением объёма/состава шума во времени**, не только за его наличием. Например, для lazy load (помимо сверки маршрутов с baseline — см. выше) сравнивай не просто "есть WARN или нет", а состав таблиц (`grep -o "lazy load from '\\\"\[dbo\]\.\[[A-Za-z]*\]"` по сохранённому JSON, `sort | uniq -c | sort -rn`) в разных временных окнах. Если несколько конкретных таблиц идут в логах **устойчиво равными пачками** (например `UserExternalLogins`/`UserAuthDetails`/`AllrpgUserDetails` почти всегда с одинаковыми счётчиками) — это не просто "шум", а конкретный код, который на каждый запрос грузит сущность без нужных `.Include()`. Такой паттерн стоит выцепить и явно назвать, даже если по объёму он "старый".
- **Если нашёл такой чёткий, воспроизводимый под-паттерн внутри общей категории шума, и под него ещё нет issue — предложи завести отдельный issue**, а не молчать под предлогом "это же известный фоновый шум". Не заводи автоматически без спроса (см. п. 5.5) — предложи пользователю: приложи конкретные счётчики/таблицы/окна как доказательство, обоснуй, почему это именно системная закономерность, а не разовый всплеск трафика.
- То же касается прочих категорий шума: единичные Telegram-ретраи это норма, но если вдруг ошибка **у одного и того же `NotificationId` повторяется много раз подряд** или **резко вырос процент неуспешных доставок относительно общего числа отправок** — это уже не "тот же старый шум", а достойный отдельного разбора сигнал.
- Разница между "трафик-зависимым колебанием объёма" (не повод для issue) и "устойчивым структурным паттерном" (повод предложить issue) — в том, повторяется ли **состав/пропорция** конкретных таблиц/полей в разных, несвязанных временных окнах, а не просто общее число записей.

## 5. Если нашлась реальная аномалия

1. Достань полную запись (`Read` на сохранённый JSON) — стектрейс, `RequestPath`, `LoggedUser`, `pod-template-hash`.
2. Проверь, новый ли это код относительно предыдущего известного релиза:
   ```bash
   git fetch upstream master
   git log --oneline <предыдущий_известный_коммит>..upstream/master -- <файл_из_стектрейса>
   ```
   Если файл из стектрейса не менялся — это не регрессия текущего релиза, а pre-existing проблема (можно быстро проверить частоту за последние 7 дней тем же фильтром по `ActionName`/`SourceContext`, чтобы понять, насколько она редкая).
3. Если это действительно из изменений релиза — сверься с `git show <коммит>` по соответствующему файлу, чтобы понять причину (например, LINQ-выражение, которое EF6 не может транслировать — см. issue [#4671](https://github.com/joinrpg/joinrpg-net/issues/4671) как пример).
4. Заводи issue через `gh issue create --repo joinrpg/joinrpg-net` с: стектрейсом, `RequestPath`/repro, ссылкой на коммит/файл:строку, пометкой `_Обнаружено автоматическим мониторингом после релиза_`.
5. **Не чини сходу без спроса** — доложи пользователю, что нашёл, и спроси, чинить ли сейчас (можно делегировать фоновому агенту — см. ниже) или просто задокументировать issue-ом.
6. **Прежде чем предлагать фикс — проверь, не почин ли он уже в `upstream/master`.** Релизы отстают от `master` на день-два; то, что выглядит как открытая проблема на проде, вполне может быть уже исправлено, но не задеплоено. `git fetch upstream master && git log --oneline <файл>` покажет, если так.

## 6. Длительное наблюдение через `/loop`

Для сессии мониторинга "последи, пока не скажу" — использовать `/loop` без явного интервала (self-pacing), не фиксированный cron. На каждой итерации:

1. ERROR-срез логов с прошлой проверки до сейчас (`--since <время предыдущей проверки> --until <сейчас>`).
2. `gh run list --workflow=deploy_prod.yml --limit 3` — не появился ли новый релиз.
3. Smoke-check трёх сайтов + разбор тела `/health` (п. 2) — деградация подсистемы может проявиться позже, чем сразу после выката.
4. Сверить lazy-load WARN с baseline (раздел 4) — маршруты вне baseline докладывать и заводить на них issue, предварительно проверив, что issue ещё нет.
5. Сверить найденные ошибки со списком известного шума (раздел 4) — докладывать только реальные новые аномалии, при полной тишине — короткая noop-заметка без лишнего текста.
6. Задержка следующей итерации — 1200 секунд (20 минут) стабильно подходит для этого сценария; не нужно чаще, если нет прямо сейчас разбираемого инцидента.
7. Каждый раз передавать в `prompt` для `ScheduleWakeup` полный контекст: последний известный релиз (run URL + время), актуальный список известного шума с уже заведёнными issue-номерами, чтобы не докладывать повторно об уже задокументированном.

## 7. Делегирование анализа фоновому агенту

Если во время мониторинга проявился неплохо изолированный вопрос для более глубокого разбора (например: "стал ли объём такого-то шума больше/меньше" или "можно ли по-быстрому починить эту N+1"), можно запустить **Agent** (`general-purpose`) в фоне параллельно с продолжением `/loop`-мониторинга:

- Дай агенту полный контекст находки (стектрейсы, файлы:строки, гипотезы, что уже проверено и отброшено) — агент не видит эту сессию.
- Явно скажи: маленький точечный фикс — можно применить в рабочем дереве, но **не коммитить и не пушить**.
- Для чисто исследовательских вопросов («почему фича выключена», «где читается этот конфиг») явно проси **ничего не менять** — иначе агент из лучших побуждений начнёт править код, который трогать не просили.
- После завершения агента — обязательно свериться с `upstream/master` перед тем, как докладывать результат: коллеги могут чинить то же самое параллельно, и то, что нашёл агент, может уже быть смерджено (см. п. 5.6). Если да — отменить локальные изменения (`git checkout -- <файл>`), не плодить дубликаты работы.

### Рабочее дерево общее — разводи параллельные работы по worktree

Фоновый агент правит **то же самое** рабочее дерево, в котором сидишь ты. Если параллельно с агентом-фиксером ты сам готовишь коммит (например, правку этой инструкции), его незакоммиченные изменения попадут в твой `git add -A` или уедут за тобой при `git checkout -b`. Поэтому для своей параллельной ветки заводи отдельный worktree:

```bash
git worktree add -b <ветка> ../joinrpg-net.<суффикс> upstream/master
# ... работа и коммит в новом каталоге ...
git worktree remove ../joinrpg-net.<суффикс>
```

Ответвляйся именно от `upstream/master` (не от текущей ветки мониторинга — см. CLAUDE.md про `upstream` vs `origin`).
