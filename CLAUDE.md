# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## О проекте

Joinrpg.ru — сайт для организации живых ролевых игр (LARP): связывает организаторов с игроками.
Основное приложение: ASP.NET Core 10 + Blazor WebAssembly (острова/islands).

## Документация

Индекс всей документации разработчика — [docs/README.md](docs/README.md). **Перед нетривиальной задачей сначала загляни туда**: это оглавление по архитектуре, гайдам и ADR, оттуда есть ссылки на нужный документ (например [docs/structure.md](docs/structure.md) — куда класть код и соглашения по `.csproj`).

## Команды

### Локальный запуск

```bash
dotnet tool restore                              # Локальные инструменты из .config/dotnet-tools.json (первый запуск)
docker compose up -d                             # PostgreSQL (5432) и SQL Server (1433)
dotnet run --project src/Joinrpg.Dal.Migrate     # Применить миграции БД (первый запуск)
dotnet run --project src/JoinRpg.Portal          # Основной сайт на https://localhost:5001
dotnet run --project src/JoinRpg.IdPortal/JoinRpg.IdPortal  # Портал аккаунтов
```

Первый вошедший пользователь автоматически получает подтверждённый email и роль администратора.
Email в dev-режиме не отправляется — логируется. OAuth требует ключей в `appsettings.json`.

Для тестовых пользователей (`admin@example.com`, `master@example.com`, `player@example.com`,
пароль `Test12345!`) и тестового проекта «Тестовая песочница» в локальной БД есть отдельный
скрипт — см. [docs/local-dev-test-users.md](docs/local-dev-test-users.md). Если их нет в локальной
БД и они нужны для тестирования — запусти `dotnet run --project src/JoinRpg.Tools.SeedTestUsers`.

### Коммиты

Коммитить сразу через `-m`/`-F`, без `--edit`:

```bash
git commit -m "сообщение коммита"
```

Редактор в сессии Claude Code не откроется: там выставлен `GIT_EDITOR=true`, и `--edit` молча
коммитит сообщение как есть. Поэтому не добавлять `--edit`, не выяснять, какой редактор настроен,
и не объяснять пользователю, что редактор не открылся. Сообщение пользователь правит при мердже
(PR вливаются squash'ем), а правки по ревью идут `--amend --no-edit`.

### Ребейз: upstream, а не origin

`origin` — личный форк (`leotsarev/joinrpg-net`), основной репозиторий — `upstream` (`joinrpg/joinrpg-net`).
Туда же идут PR. Поэтому ребейзить и сверяться с базовой веткой всегда через `upstream`:

```bash
git fetch upstream
git rebase upstream/master
```

`origin/master` в форке отстаёт и на «ребейзни» отвечает «уже актуально» — это ложный ответ, не верить ему.

### Не пушить в PR из очереди мерджа

Перед тем как дополнять свой PR (новый коммит, `--amend`, `push --force-with-lease`), проверить,
не стоит ли он в merge queue и не включён ли автомердж:

```bash
gh pr view N --repo joinrpg/joinrpg-net --json autoMergeRequest,mergeStateStatus,state
```

Если пользователь сказал, что вливает PR, — считать, что PR в очереди. Такой PR не трогать,
новые правки оформлять отдельным PR.

Почему: при обновлении головы PR GitHub молча снимает его из очереди. Так было с #5562: после двух
`--amend` и force-push в master не попало ничего, пока пользователь не заметил и не поставил PR заново.
Если пушить в PR, который собирались влить, всё же пришлось — сразу сказать пользователю, что PR
надо снова поставить в очередь.

### Секреты кубера — только с прямого разрешения

Не читать содержимое секретов Kubernetes (`kubectl get secret -o yaml/json`, `kubectl describe secret`
с данными, декодирование `data`, `kubectl exec ... env` и т.п.) без прямого разрешения пользователя
в текущем разговоре. Для диагностики хватает списка секретов (`kubectl get secrets`), имён ключей
и несекретных настроек из `manifests/*/.env`. Если значение действительно нужно — спросить, какой ключ и зачем.

Почему: при разборе падения аватарок на dev значения секрета декодировались с маской по имени ключа,
маска не сработала из-за регистра (`SECRETKEY`), и секретный ключ S3 попал в лог сессии.

### GitHub: создание PR после завершения issue

**ОБЯЗАТЕЛЬНО**: При работе в контексте GitHub (через claude-code-action) — после коммита кода сразу создавать PR через `gh pr create`. Не предоставлять ссылку «Create PR» — создавать PR самостоятельно. Не ждать отдельной просьбы.

```bash
gh pr create --title "feat: описание" --body "$(cat <<'EOF'
## Что сделано
- ...

Closes #НОМЕР

🤖 Generated with [Claude Code](https://claude.ai/code)
EOF
)"
```

### GitHub: всегда подписываться как фактический инструмент

**ОБЯЗАТЕЛЬНО**: любое сообщение, отправляемое в GitHub от лица пользователя (комментарий к issue или PR,
описание PR, текст ревью, тело issue), должно быть подписано — из него должно быть явно видно, что писал
инструмент/модель, а не человек. Подпись ставится последней строкой и указывает фактический генератор
сообщения — имя инструмента, которым сообщение реально написано, со ссылкой на его сайт. Она не
фиксирована: каждый инструмент подписывается собой. Например:

```
🤖 Generated with [Claude Code](https://claude.ai/code)
```

а opencode подписался бы так:

```
🤖 Generated with [opencode](https://opencode.ai)
```

Это касается всех команд `gh` (`gh pr create`, `gh pr comment`, `gh issue create`, `gh issue comment`,
`gh pr review`) и любых других способов отправки текста в GitHub. Учётная запись GitHub принадлежит человеку,
поэтому без подписи сообщение выглядит написанным им лично — это вводит собеседников в заблуждение.

### Ревью PR и ADR — отдельным субагентом

**ОБЯЗАТЕЛЬНО**: каждый PR (перед `gh pr create` и перед пушем доработок) и каждый написанный или
изменённый ADR ревьюить отдельным субагентом (инструмент `Agent`), а не перечитывать самому.
Порядок: коммит → ревью субагентом → разбор замечаний → `gh pr create`/пуш. Это касается и работы
через claude-code-action: «сразу создавать PR» из раздела выше означает «сразу после ревью».

Субагент — новый агент, не `fork`: форк наследует контекст автора, и ревью теряет смысл.
Дать ему команду для диффа (`git diff upstream/master...HEAD` — сравнивать с `upstream`, не с `origin`)
или путь к файлу ADR и задачу: найти ошибки, противоречия с кодом и другими ADR, нарушения правил
из этого файла и [docs/README.md](docs/README.md), устаревшие README и пропущенные записи CHANGELOG
затронутых NuGet-пакетов. Замечания разобрать: исправить или явно отклонить с причиной, и только
после этого отправлять PR.

Почему: автор смотрит на свой текст глазами автора и пропускает то, что видит свежий контекст.

### Тесты

```bash
dotnet test                                      # Все тесты

```

#### Интеграционные тесты (`JoinRpg.IntegrationTest`) — локально осторожно

Они поднимают базу в контейнере, накатывают миграции и стартуют приложение целиком — это долго
и съедает много ресурсов машины. По умолчанию локально их **не запускать** и полагаться на CI.
`dotnet test` без указания проекта тоже их включает — локально гонять конкретные юнит-тестовые проекты.

Запускать локально только если:

- изменение оценивается как очень рискованное, и ждать CI дороже, чем прогнать локально;
- добавлены или изменены сами интеграционные тесты — прогнать именно их через `--filter`;
- нужно пересчитать снапшот ленивых загрузок — только полным прогоном с билдом,
  см. [docs/lazy-loads-baseline.md](docs/lazy-loads-baseline.md);
- интеграционный тест упал в CI и его надо воспроизвести/отладить — тоже через `--filter` на упавший тест;
- изменилась схема БД (новая миграция) — `DbSchemaDocumentationScenario` сверяет `docs/db-schema.md`
  с реальной схемой, его можно прогнать отдельно через `--filter`.

В остальных случаях — CI.

## Инструменты анализа кода

Для понимания кода предпочитай **cwm-roslyn-navigator** (MCP) перед чтением файлов. Roslyn понимает семантику C#: типы, иерархии наследования, реальные использования символов. Используй `find_symbol`, `find_references`, `find_callers`, `find_implementations`, `get_type_hierarchy` и другие инструменты навигатора для навигации по коду. Чтение файлов — только когда нужен полный контекст, которого навигатор не даёт.

Сервер прописан в `.mcp.json` и запускается локальным инструментом из `.config/dotnet-tools.json`,
поэтому на свежем клоне нужен `dotnet tool restore` — без него сервер не поднимется. Решение
(`Joinrpg.slnx`) навигатор находит сам, аргументы не нужны. Новый MCP-сервер подхватывается при
старте сессии: если он только что появился, текущая сессия его не увидит.

Почему это важно на практике: грепом по именам **не видно мёртвых перегрузок** — одноимённый живой
метод прячет мёртвый. Так `ICharacterPropsService.ChangeCharacter<TArgs, TResult>` и
`CharacterOperationContextExtensions.MarkCreatedNow` прожили лишнее время: у второго четыре вызова,
но все они уходят в одноимённое расширение над контекстом проекта. `find_references` такое находит
сразу.

## Фикс багов

При исправлении бага **всегда рассматривать добавление юнит теста**, который воспроизводит баг до фикса и проходит после. Это предотвращает регрессии. Тест добавляется в соответствующий тестовый проект.

## Правила кода

- **Без regex** — по возможности избегать регулярных выражений.
- **Не править `.cs` потоковыми утилитами** (`sed`, `awk`, перезапись через shell-редирект). В рабочем дереве файлы с CRLF, такие правки ставят в изменённых строках LF — получается смешанный перевод строк, и `dotnet format --verify-no-changes` падает в CI. Массовые правки делать редактором/IDE, а не скриптом.
- **Язык UI**: все видимые пользователю строки (названия колонок, кнопки, заголовки, сообщения) — всегда на русском языке.
- **Локализация**: видимые пользователю строки живут в слое UI — это `JoinRpg.Portal`, razor-компоненты в `JoinRpg.Web.*` и `JoinRpg.Common.WebComponents`, плюс шаблоны писем в `JoinRpg.Services.Email`. Там пометка не нужна. Если такая строка появляется в сервисном или доменном слое (`JoinRpg.Services.*`, `JoinRpg.Domain*`, `JoinRpg.DataModel`) — ставить рядом `TODO[Localize]`: это нарушение слоёв, которое когда-нибудь придётся разбирать.
- **DI**: Autofac. Модули регистрируются в `Startup.cs`/`Program.cs` через `ConfigureContainer()`.
- **Новые поля в DataModel**: согласовывать изменения с @leotsarev.
- **Версия .NET SDK**: не обновлять вручную в `global.json`. Там прописан `"rollForward": "latestFeature"` — SDK автоматически использует последнюю доступную feature-версию. Dependabot обновляет только NuGet-пакеты, но не SDK, и это нормально.

## NuGet-пакеты

Проекты с `<IsPackable>true</IsPackable>` подключаются из других репозиториев —
[docs/nuget-packages.md](docs/nuget-packages.md). Изменение видно потребителю — запись в
«Не выпущено» `CHANGELOG.md` пакета (что писать — [там же](docs/nuget-packages.md#changelog)).
Ошибки RS0016/RS0017 — изменился публичный API: `pwsh scripts/Update-PublicApi.ps1`.
Ошибки CP* при упаковке — ломающее изменение API: см.
[Ломающее изменение](docs/nuget-packages.md#ломающее-изменение).
Поменялся способ подключения, настройки или основные типы — обновить `README.md` пакета.
Новый пакет — добавить в матрицу `nuget-publish.yml`.
